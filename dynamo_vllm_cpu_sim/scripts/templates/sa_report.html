先看结论，再看数值的含义

本报告的百分比，全部指“请求期限达标率”。

请求在自己的截止时间前返回首个 token，就算达标。它不表示带宽或计算利用率。

TTFT（Time To First Token，首 token 延迟）从请求到达到返回首 token，包含中央队列等待。

期限达标率 = 按时返回首 token 的请求数 ÷ 总请求数
截止时间 = 到达时间 + 4 × 参考独立服务时间 T₀

输入相同，资源配比和存储算法也相同

直接从 SA 的 E26f 生成器导出官方输入。保留 h/u、到达时刻、T₀ 和截止时间。本轮没有沿用之前的24请求负载，也没有用虚拟 token 标定。

C_A = A + B + C_A

C_A 不读远端 KV，每层计算时间约等于 A；SA 在该工况下主要受存储带宽限制。

C_B = A + B + C_B

C_B 不读远端 KV，每层计算时间约等于 B；增大 C 的计算量后，SA 的主要瓶颈转到计算侧。

@@INPUT_TABLE@@

h 是远端复用的前缀 token 数，u 是重算 token 数。MB / GB 均为十进制。每次 A、B、C 各120个，共360个；两种 C 不会出现在同一次实验中。

到达过程与种子
A 每簇16个同时到达，簇心间隔 Exp(16/98)；B、C 各自间隔 Exp(1/98)。每类平均98请求/秒。C_A 使用416/417/418，C_B 使用424。同一输入跨全部策略复用。
执行资源
32 Worker、8层、8192 token/step。计算使用 SA 批级利用率与 attention 公式，不再使用旧的全局线性模型。
存储资源与算法
120 GB/s 聚合池，q_max=200 GB/s，每 token 每层4096 bytes，无读取启动延迟。分配对象为整批每层流 max_min，不是 dv 原有逐块逐盘 max_min_fair。
内存、缓存与输出
每 Worker 8 GB逻辑预算：0.5 GB base、KV=8×4096 bytes/token、预留最大8192-token workspace。各格点 KV 容量相同。关闭本地前缀复用，逻辑 block=1 保留精确 h/u；输出1token，无额外 decode。

一层预取，逐层等待就绪

首层读取整批第0层申请 q_max，等待 KV 就绪。
本层开始计算使用真实 SchedulerOutput 的成员和 token 计算本层耗时。
同时预取下一层q=min(q_max,V/c_batch)。本层结束未读完，则升至 q_max。
进入下一层前层计算和本层读取都完成后，才能计算。重复至第8层结束。

存储过载时执行 max-min 分配；欠载时先按需分配，再均分剩余带宽。因此实际速率可以超过申请速率。新流到达会即时重分配全部在途流。

有意改变的系统行为

真实 Dynamo 决定路由落点，真实 vLLM Scheduler 决定组批和分块。读取、计算和输出仍为仿真，没有数值 GPU/NPU 执行；逻辑 block=1 不代表真实设备支持该配置。

四种策略，分别检验排序和重请求配额

FCFS（First Come First Served）表示先到先服务。准入策略在进入 Dynamo 之前执行。slack_only 和 quota_fcfs 来自接入技术方案，是拆分 TFS 作用的对照项；不是 Dynamo/vLLM 自带算法，也不是 SA 原实验的两个策略名称。

策略先放行谁限制重请求数配额满时放轻请求
immediate按到达顺序直接提交否不适用
slack_only剩余等待预算小的优先否不适用
quota_fcfs按到达顺序是是，跳过受限重请求
tfs剩余等待预算小的优先是是，跳过受限重请求
slack = 截止时间 − 当前时间 − T₀
重请求阈值 = 历史请求压力 V_layer/c_single 的 P75
重请求配额 = max(1, floor(参考带宽 / 重请求阈值))

V_layer 是单请求每层读取字节数，c_single 是单请求每层计算时间。P75 是历史压力的分位位置，不是存储带宽的75%。它使用下标 floor(0.75×(N−1))，包含已完成请求，不读取未来请求。P75=0时采用 SA 大配额语义。本轮关闭老化、反馈延迟为0、首 token 时释放。租约包括实例内等待。

quota_fcfs 和 TFS 到底差在哪？看一个放行名额

示意例子，不是本轮实测请求：只剩一个重请求名额。甲先到，还能等80ms；乙后到，只能等10ms。

quota_fcfs 放行甲

甲先到，按到达顺序放行。

TFS 放行乙

乙的剩余等待预算更小。

两者的配额和轻请求补位规则相同。本轮 A 类重请求形状相同，它们之间的排序通常一致。放行不保证计算先后，实际批次由 vLLM 决定。

中央准入四种策略决定何时放行。
真实 Dynamo决定请求进入哪个 Worker。
真实 vLLMScheduler / KVCacheManager 决定组批与分配。
SA 逐层模型仿真读取、计算和首 token 事件。

@@SEED_TABLE@@

seed 417 的直接提交本来就较好；seed 418 暴露了更大的迁移差异。判断收益时应同时看每个输入种子，不能只看跨种子中位数。

本轮能确认的是汇总改善。

允许组批时，C_A 的达标率从直接提交的35.3%提高到68.9%；C_B从40.0%提高到70.8%。没有证明所有输入获得相同收益，也没有证明组批比单请求计算更好。

C_A 每种子3次路由重复，共3个官方输入种子；C_B只有1个输入种子。Dynamo 同代价选择存在随机平局；重复运行不能算新增输入种子。

计算、中央等待与带宽变化

轨迹固定使用上限8、repeat0、seed416/424，不随前面结果面板的种子筛选改变。按预定规则选择，没有按成绩挑选。

图能支持什么解释？

已观察：TFS 将一部分等待留在中央队列，改善总TTFT。直接提交时实际batch较大，但本轮达标率更低。整个矩阵实际step最多5个请求，不是配置上限8。

机制解释：零读C进入混合batch后，也要等同批其他请求的层KV。相关计数保存在 mixed_steps 和 C_members_in_read_steps。

路由、队列次序和混合批同时变化；本轮未单独消融。不能把全部差异归因于混合batch，也不能把中央排队本身视为性能损失或收益。

真实代码与仿真边界

真实部分是Dynamo选择器、vLLM Scheduler与KVCacheManager。执行时间和输出为仿真；没有数值GPU执行或完整EngineCore/ModelRunner。

SA派发与DV准入仍有系统差异

SA一个请求占一个Worker。DV租约按请求计数，包括实例内排队；上限1也不等于只向空闲Worker派发。

收益归因

quota_fcfs与TFS都有轻请求补位，二者只能比较排序，不能单独证明补位贡献。排序、路由、组批有共同变化，本轮未完全隔离。
