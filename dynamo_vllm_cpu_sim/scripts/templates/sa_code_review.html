quota_fcfs 与 tfs 的代码差别

两者共用轻重门槛、重流配额、跳过被阻塞重请求、继续找轻请求，以及首 token 释放。差别在中央队列排序：quota_fcfs 按到达时间；tfs 按剩余等待预算，再按期限。

quota_fcfs: key = (arrival_s, request_id)
tfs:        key = (deadline_s − now − T0_s, deadline_s, request_id)
共同条件:   轻请求可派；重请求仅在 heavy_held < heavy_cap 时可派

其中 now 对所有候选相同。因此等待时间增加不会自动改变两条已存在请求的相对预算次序。正式实验又关闭了老化，不能据此宣称已解决所有长期饥饿问题。

结论本次审查意见依据或缺口
本轮数据可以回溯到代码与原始记录有证据支持固定提交、实现指纹、原始 SHA、逐请求重算相互对应。
这些固定工况中，TFS 比 immediate 的达标率高有证据支持汇总与逐请求记录一致。范围限本轮输入、资源和合成画像。
TFS 始终优于 quota_fcfs不支持quota_fcfs 与 TFS 很接近，部分指标相同或 quota_fcfs 更好。不能忽略重复运行波动。
DV 已逐场景复现 SA 收益不支持C_A seed418：SA TFS 71.1%；DV 上限1为64.2%，上限8为57.5%。汇总接近不能覆盖反例。
收益变化唯一来自真实组批不支持同时存在路由、实例排队、配额占用和唤醒语义差异。需要控制变量消融才能归因。
已证明生产设备收益和部署可用性不支持没有数值模型执行、真实 KV 网络、硬件内存布局或服务全栈。画像仍为 SA 合成模型。

尚未补齐的可信度证据

  1. 给真实多请求、混合类别和分块 step 增加独立参考执行器对拍。目前只重算公式与轨迹合法性。
  2. 分别控制路由、实例排队、准入占用和组批，才能解释 seed418 的差距。本次没有新增这些消融实验。
  3. C_B 只有一个官方输入种子。3 次路由重复不能当作 3 个独立负载；本轮没有显著性检验或置信区间。
  4. layer_compute 固定用于当前 synthetic-v1 / no_speedup=false。不能把它视为任意 SA 画像的通用适配器。
