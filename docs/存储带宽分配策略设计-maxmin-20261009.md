# 存储带宽分配策略设计：按需水土填充（max-min fair）

- 日期：2026-10-09
- 状态：**设计稿，未实现**。§4 的三个决策点按推荐默认值写入，等待用户确认后实施；任一决策被推翻只需修改对应章节。
- 关联：`dynamo_vllm_cpu_sim/sim/storage.py`（现行实现）、`docs/共享KV多ASU多Path下的组批错峰与带宽协同调度设计-20260917.md` §4（ASU 模型）、`docs/CPU真实代码仿真环境检视报告-20260924.md` §4.1（B 层差距条目）。

## 1. 需求原文与理解

用户 2026-10-09 提出的存储侧带宽分配策略需求（原文）：

> 1）可以认为一个 IO 请求就在一个 Path，每个 Path 可以分配的带宽范围是 0~整个 ASU 的上限带宽；
> 2）在 IO 请求的诉求之和小于总带宽时，先按需分，然后剩余带宽均分；
> 3）在 IO 请求的诉求之和大于总带宽时，均分，但是对于均分大于需求的，可以仅分需求的，然后把（均分−需求）的多余部分均分给其他需求超过均分的。

理解：这是一个**带需求上限的 max-min fair（水土填充）分配**。分配主体是每个活跃 Path 队首的 IO 请求，每个请求携带一个期望带宽（诉求）；供过于求时先满足全部诉求、剩余容量在所有活跃请求间均分叠加；供不应求时迭代执行"均分→超额者截断到诉求→多余再均分"直到不动点。现行策略不删除，通过配置项切换，默认保持现行。

## 2. 不变量（新策略不改变的部分）

以下机制与现行实现完全一致，本次设计只替换 `Storage.rates()` 中带宽分配规则的计算：

- **放置**：块经 sha256 哈希固定到唯一 (ASU, Path)，无迁移（`storage.py:41-50`）；
- **队列**：每 (ASU, Path) 一条 FIFO，只有队首且已过 `read_latency_s` 的读请求参与带宽分配（head-of-line 语义不变）；
- **事件循环**：`submit / next_time / advance` 的虚拟时间推进与"必须在下一个存储事件处停车"的约束不变；
- **指标**：`snapshot().path_rates_Bps` 继续报告每路径实际分配速率，`bytes_transferred` 口径不变。

## 3. 策略形式化定义

### 3.1 分配主体与需求

- 分配主体：某时刻每个 ASU 内所有活跃读请求（即各 Path 的队首且 `ready <= now`），一个 IO 请求 = 一次块读，位于唯一 Path 上（对应需求原文第 1 点）；
- 需求 d_i > 0：该读请求的期望带宽，单位 bytes/s（SI）。需求挂在 trace 的逻辑请求行上，随其全部块读下发；同一逻辑请求的块分散在多个 Path 时，每个 Path 的队首读各自携带该需求参与所在 ASU 的分配（即同一逻辑请求在 k 条 Path 上可各获至多其需求）；
- **新策略下 `path_Bps` 不再是分配上限**（需求原文第 1 点：分配范围为 0 ~ ASU 上限带宽），仅在未显式配置需求时作为需求缺省值复用（§5）。

### 3.2 供过于求（Σd ≤ C）

设某 ASU 容量 C = `disk_Bps`，活跃请求集合 A，|A| = N：

```
alloc_i = d_i + (C − Σd) / N    对所有 i ∈ A
```

即先按需分，剩余容量（C − Σd）在**所有** N 个活跃请求间均分叠加。注意叠加后 alloc_i 仍 ≤ C（因 Σd ≤ C 且 d_i ≤ Σd），分配范围约定成立。

### 3.3 供不应求（Σd > C）：迭代水土填充

```
cap ← C; active ← A; alloc ← 0
循环直到 active 为空：
    share ← cap / |active|
    satisfied ← { i ∈ active : d_i ≤ share }
    若 satisfied 为空：
        每个 i ∈ active 分得 share，结束
    否则：
        每个 i ∈ satisfied 分得 d_i
        cap ← cap − Σ_{satisfied} d_i
        active ← active − satisfied
```

性质（标准 max-min fair）：

- 不动点：任何请求不会分得超过自身需求，除非所有请求需求都被满足（那是 §3.2 情形）；
- 单请求独占：N=1 时分得整个 C；
- 均匀需求退化：所有 d_i 相等时结果为 C/N 均分（与 §3.2 在 Σd ≤ C 时给出的 d + (C−Nd)/N = C/N 一致）。

### 3.4 数值例子

**供过于求**：C = 40 GB/s，d = [2, 4, 8]（Σ=14 ≤ 40）：
alloc = [2+8.67, 4+8.67, 8+8.67] = **[10.67, 12.67, 16.67] GB/s**，Σ=40。

**供不应求（体现迭代）**：C = 100，d = [10, 28, 100, 100]（Σ=238 > 100）：

| 轮次 | 剩余容量 | 参与者 | 均分 | 截断 |
|---|---|---|---|---|
| 1 | 100 | {10,28,100,100} | 25 | 10 定格于 10 |
| 2 | 90 | {28,100,100} | 30 | 28 定格于 28 |
| 3 | 62 | {100,100} | 31 | 无超额者 |

结果 **[10, 28, 31, 31]**。（若只执行一轮再分配会得 [10, 30, 30, 30]，其中需求 28 的请求分得 30 超过自身诉求——见 §4 决策三。）

**与现行策略的量级对比**（默认 demo 配置，2 盘 × 40 GB/s、链路 10 GB/s、path_Bps=1 GB/s，某盘 2 条活跃路径、均匀需求 1 GB/s）：

- 现行 active_split：每路径 min(1, 40/2) = 1 GB/s，Σ=2 ≤ 10，链路不压缩 → **各 1 GB/s**；
- 新 max_min_fair：Σd=2 ≤ 40 → 各 1 + 19 = 20 GB/s，Σ=40 > 10 → 链路等比例压缩 0.25 → **各 5 GB/s**。

差异来自两点：新策略取消单路径 1 GB/s 上限，剩余带宽均分叠加。

### 3.5 与共享链路的组合（按 §4 决策二的默认）

各 ASU 内部按 §3.2/§3.3 分配后，全局仍按现行规则等比例压缩：

```
scale = min(1, shared_link_Bps / Σ_{所有盘} Σ_{盘内 alloc})
最终速率 = alloc × scale
```

**已知语义损失（如实记录）**：默认配置下链路（10 GB/s）远紧于单盘（40 GB/s），几乎总是全局瓶颈；链路压缩按比例缩小一切分配，**盘内water-filling 的需求满足保证在链路处不再成立**。例如盘 1 分得 [16, 24]、盘 2 分得 [40]，全局 Σ=80，scale=1/8，最终 [2, 3, 5]——盘 1 中需求 8 的请求实际只得到 2。若实验需要端到端需求语义，按 §4 决策二的选项 B/C 演进。

## 5. 配置接口

`storage` 配置块新增两个字段，trace 新增一个可选字段：

```json
{
  "storage": {
    "bandwidth_policy": "active_split",
    "request_demand_Bps": 1000000000,
    "disks": 2, "paths_per_disk": 256, "disk_Bps": 40000000000,
    "shared_link_Bps": 10000000000, "path_Bps": 1000000000,
    "read_latency_s": 0.0001, "kv_bytes_per_token": 131072
  }
}
```

trace 行（可选字段，缺省用全局值）：

```json
{"id":"r1","arrival_s":0.0,"prompt_token_ids":[...],"output_tokens":8,
 "remote_prefix_tokens":32,"demand_Bps":2000000000}
```

规则：

- `bandwidth_policy`：`"active_split"`（现行，**缺省默认**，老配置零改动）或 `"max_min_fair"`（本设计）；其他值报错；
- `request_demand_Bps`：仅 `max_min_fair` 生效；未配置时缺省取 `path_Bps`（保持"单路径期望带宽"的直觉连续，并让老配置可直接切换对比——注意均匀需求下新策略退化为无上限均分，§3.4 例）；
- `demand_Bps`（trace 行级）：> 0 有限值，`run.validate()` 校验；同一请求的全部块读继承该值；
- `active_split` 下出现需求字段不报错、不生效（便于同一份 trace 跑两种策略对照）。

## 6. 实现方案

改动集中在三个文件，引擎/路由层零改动：

1. **`sim/storage.py`**
   - `Read` dataclass 增加 `demand: float` 字段；`submit(now, key, blocks, demand)` 按块下发需求；
   - 构造时校验 `bandwidth_policy` 与 `request_demand_Bps`（仅新策略要求正值）；
   - `rates()` 按 `bandwidth_policy` 分派：
     - `active_split`：现有代码路径**原样保留**（逐字节不变）；
     - `max_min_fair`：按盘分组活跃队首 → 各盘对 (path, demand) 集合执行 §3.3 水土填充（Σd ≤ C 时直接用 §3.2 公式）→ 全局 `scale = min(1, link/Σ)`；
   - 水土填充实现为模块级纯函数 `waterfill(capacity, demands) -> list[float]`，排序实现，单盘 O(P log P)，256 Path 规模无性能问题；确定性成立（无平局随机）。
2. **`sim/connector.py` / `sim/engine.py`**：需求传递。`run.py` 从 trace 行构造 `{request_id: demand}` 表，经 `connector.demands`（与现有 `connector.store` 同法注入）到达 `SimConnector`；`submissions` 条目从 `(rid, blocks)` 扩为 `(rid, blocks, demand)`，`engine.schedule()` 调 `store.submit` 时透传。
3. **`sim/run.py`**：`validate()` 增加 `demand_Bps` 校验；构造需求表并注入各引擎 connector。

`snapshot().path_rates_Bps` 与 `report.json` 的 `config` 回显无需改动，天然区分两种策略的运行。

## 7. 边界情形

| 情形 | 处理 |
|---|---|
| 单请求独占一盘 | 分得整个 `disk_Bps`（§3.3 性质；现行策略此时受 path_Bps 封顶，是两策略最大差异之一） |
| d_i > 盘容量 | 允许；水土填充自然给出 ≤ C 的分配，不预截断 |
| Σd 恰等于 C | §3.2 边界，剩余为 0，alloc = d |
| 均匀需求 | 退化为无上限均分 C/N（§3.4 量级对比例） |
| 链路压缩破坏需求保证 | 默认接受并记录（§3.5）；决策二若改选项 B/C 则消除 |
| 未过 read_latency 的队首 | 不参与分配（与现行 `heads` 定义一致） |
| 需求字段出现在 active_split 运行 | 忽略不报错（§5） |

## 10. 与策略文档 09-17 B 层的关系

09-17 的 B 层设想是**分类组份额**规则（B0：SS/LS/SL/LL 四类 20/12/4/4 GB/s 组基础份额 + 空闲均分；B1：保底+借用+权重）。本设计的 max-min fair 是**按请求需求**的通用规则，不含分类组概念，二者不同；但 `bandwidth_policy` 配置项建立了 B 层第一个可切换挂载点，B0/B1 未来可作为该配置的额外取值接入，形成 `active_split | max_min_fair | B0 | B1` 的策略序列。E26 实验中"ASU 另测"的跨组借用、相同字节不同条目等观测项在本设计下可直接复用现有事件输出。
