# 存储带宽分配策略设计：按需水土填充（max-min fair）

- 日期：2026-10-09（同日二次修订：Path 语义改为两策略共用，新策略取消 Path 排队）
- 状态：**已实现（2026-10-10）**。按 §6 实施，验收见 `dynamo_vllm_cpu_sim/VALIDATION.md` 追记与 `results/{max_min_fair,max_min_fair_slow}/`；§9 同步清单已全部完成。
- 关联：`dynamo_vllm_cpu_sim/sim/storage.py`（现行实现）、`docs/共享KV多ASU多Path下的组批错峰与带宽协同调度设计-20260917.md` §4（ASU 模型）、`docs/CPU真实代码仿真环境检视报告-20260924.md` §4.1（B 层差距条目）。

## 1. 需求原文与理解

用户 2026-10-09 提出的存储侧带宽分配策略需求（原文）：

> 1）可以认为一个 IO 请求就在一个 Path，每个 Path 可以分配的带宽范围是 0~整个 ASU 的上限带宽；
> 2）在 IO 请求的诉求之和小于总带宽时，先按需分，然后剩余带宽均分；
> 3）在 IO 请求的诉求之和大于总带宽时，均分，但是对于均分大于需求的，可以仅分需求的，然后把（均分−需求）的多余部分均分给其他需求超过均分的。

同日第一次补充确认（原文要点）：

> 需求可以认为是每个请求自己携带的。对于一个请求，由于是按层传输和计算，所以需求可以认为是一层的传输数据量除以一层的计算时间。
> 块应该不是固定到某一个 path 的，每个块对所有 path 均可见，但是 IO 请求是发到 Path 的，并且每个 IO 请求都可以认为独占了一个 Path。
> 再强调一下，这个新的带宽分配策略并不要直接把原有策略替换了，而是作为一个可选的策略进行实现和配置。

同日第二次补充确认（原文）：

> 对于现行的策略，也要改成"块应该不是固定到某一个path的，每个块对所有path均可见，但是IO请求是发到Path的"。对于新策略，即使超过256个path，也可以认为有更多的path可以占用，也就是取消在同一个path队列中排队的概念。

理解：这是一个**带需求上限的 max-min fair（水土填充）分配**，作为**可选策略**接入。**Path 语义的修改（块只落 ASU、发 IO 时才指派 Path）为两策略共用**；两策略的差异收敛为带宽分配规则与排队语义：现行 `active_split` 保留"活跃路径均分 × path_Bps 上限 × 链路压缩"的速率规则与每 Path FIFO 排队；新 `max_min_fair` 按需求水土填充且**无排队**（每个 IO 请求独占一条 Path，数量不限）。

## 2. 不变量与新变化总览

两策略共用的新 Path 语义（用户二次确认，**现行策略亦改**）：

- 块经 sha256 哈希只固定到唯一 ASU（盘），对该盘所有 Path 可见；
- IO 请求发出时才指派 Path，`location()` 的"块哈希到 (盘, Path)"定位**废除**（两策略都废）。

不变的部分：

- **`active_split` 的速率规则**：活跃路径均分盘带宽（`disk_Bps / 该盘活跃队首数`）、`path_Bps` 上限、链路等比例压缩——公式不变；
- **ASU 放置哈希**（块 → 盘）、`read_latency_s` 门控、事件循环（`submit / next_time / advance`）、`bytes_transferred` 口径、`snapshot().path_rates_Bps` 输出。

**重要后果（如实记录）**：现行策略的放置/Path 语义变化会改变其时间线结果，**既有 `results/` 与 `VALIDATION.md` 数值对应旧哈希定位语义，实现后须全部重跑并更新基线**。"不替换"指的是速率规则与排队语义保留、配置共存，不再是逐字节复现。

## 3. 策略形式化定义

### 3.1 分配主体、Path 语义与需求

**Path 语义（两策略共用）**：块不固定到某条 Path——按哈希落在唯一 ASU 后，对该盘全部 Path 可见；Path 是 IO 请求发出时才选定的访问通道。指派规则为**确定性最少占用**：发出时选所在盘中占用最少的 Path，平局取最小下标。这是占位规则，不是选路策略——09-17 的 P0/P1 仍是独立的后续挂载点（§10）。

两策略在排队语义上的分野（用户二次确认）：

- **`active_split`**：保留每 Path FIFO 队列与 head-of-line 语义。最少占用指派下，同盘并发 IO ≤ 256 时每个 IO 请求自然各占一条 Path（无排队）；超过 256 才在最少占用 Path 上排队。分配主体 = 各非空 Path 的队首且 `ready <= now`。
- **`max_min_fair`**：**取消同一 Path 队列内排队的概念**。每个 IO 请求独占一条 Path，Path 数量不设上限（超过 256 视为还有更多 Path 可占），发出后过 `read_latency_s` 即成为分配主体。`paths_per_disk` 在该策略下仅为名义值，不构成并发上限；snapshot 中的 path 标签用发放序号。

**需求 d_i（`max_min_fair` 用）**：

```
d = 一层的 KV 传输数据量 ÷ 一层的计算时间
```

来源是逐层重叠的理想节奏：层 ℓ 计算期间传输层 ℓ+1，要使计算不因等待 KV 停顿，一层的 KV 必须在一层计算时间内到齐。当前仿真为聚合模型（无层概念，`kv_bytes_per_token` 为全层合计、`prefill_token_s` 为全层合计的单 token 计算时间），两处的层数相消，公式化为：

```
d = kv_bytes_per_token / prefill_token_s
```

采用 prefill 系数的理由：远端前缀 KV 在 prefill 阶段被消费，追赶的节奏是 prefill 计算速度（decode 阶段不加载远端前缀）。未来引入逐层模型（P2）后，公式逐字成立，无需修改定义。demo 配置下 `d = 131072 / 4e-6 = 32.768 GB/s`——单个请求的需求即达盘容量（40 GB/s）的 82%，天然形成高争抢工况。

每个请求在创建时自行携带该需求（同配置下数值相同，但它是请求属性而非全局常量）；trace 行可选 `demand_Bps` 字段覆盖推导值，用于 A/B 双类等实验制造异质需求。

**分配范围**：`max_min_fair` 下 `path_Bps` 不再是分配上限（需求原文第 1 点：0 ~ ASU 上限带宽）；单请求独占一盘时分得整个 `disk_Bps`。

### 3.2 供过于求（Σd ≤ C）

设某 ASU 容量 C = `disk_Bps`，活跃请求集合 A，|A| = N：

```
alloc_i = d_i + (C − Σd) / N    对所有 i ∈ A
```

先按需分，剩余容量（C − Σd）在**所有** N 个活跃请求间均分叠加。叠加后 alloc_i 仍 ≤ C（因 Σd ≤ C 且 d_i ≤ Σd），分配范围约定成立。

### 3.3 供不应求（Σd > C）：迭代水土填充（用户已确认：迭代到不动点）

```
cap ← C; active ← A; alloc ← 0
循环直到 active 为空：
    share ← cap / |active|
    satisfied ← { i ∈ active : d_i ≤ share }
    若 satisfied 为空：
        每个 i ∈ active 分得 share，结束
    否则：
        每个 i ∈ satisfied 分得 d_i
        cap ← cap − Σ_{satisfied} d_i
        active ← active − satisfied
```

性质（标准 max-min fair）：

- 不动点：任何请求不会分得超过自身需求，除非所有需求都被满足（§3.2 情形）；
- 单请求独占：N=1 时分得整个 C；
- 均匀需求退化：所有 d_i 相等时结果为 C/N 均分。

### 3.4 数值例子

**供过于求**：C = 40 GB/s，d = [2, 4, 8]（Σ=14 ≤ 40）：
alloc = [2+8.67, 4+8.67, 8+8.67] = **[10.67, 12.67, 16.67] GB/s**，Σ=40。

**供不应求（体现迭代到不动点）**：C = 100，d = [10, 28, 100, 100]（Σ=238 > 100）：

| 轮次 | 剩余容量 | 参与者 | 均分 | 截断 |
|---|---|---|---|---|
| 1 | 100 | {10,28,100,100} | 25 | 10 定格于 10 |
| 2 | 90 | {28,100,100} | 30 | 28 定格于 28 |
| 3 | 62 | {100,100} | 31 | 无超额者 |

结果 **[10, 28, 31, 31]**。（单轮再分配会得 [10, 30, 30, 30]，其中需求 28 的请求分得 30 超过自身诉求——已确认不采用。）

**推导需求的典型工况**（demo 配置，d = 32.768 GB/s，单盘 C = 40 GB/s）：两请求同盘时 Σd = 65.5 > 40，第一轮均分 20 < 32.77，无超额者 → **各 20 GB/s**；需求满足率 61%。新策略无排队语义下，多请求的全部块读同时参与分配，同盘 K 个请求各得 40/K GB/s。

**与现行策略的量级对比**（2 盘 × 40 GB/s、链路 10 GB/s、path_Bps=1 GB/s，某盘 2 个 IO 请求）：

- 现行 active_split（新 Path 语义下两请求各占一条 Path）：每路径 min(1, 40/2) = 1 GB/s，Σ=2 ≤ 10，链路不压缩 → **各 1 GB/s**；
- 新 max_min_fair（均匀推导需求 32.77）：Σd=65.5 > 40 → 各 20 GB/s，跨盘 Σ=40 > 10 → 链路等比例压缩 0.25 → **各 5 GB/s**。

差异来自两点：新策略取消单路径 1 GB/s 上限，剩余带宽均分叠加。

### 3.5 与共享链路的组合（用户已确认：仅盘内）

各 ASU 内部按 §3.2/§3.3 分配后，全局仍按现行规则等比例压缩：

```
scale = min(1, shared_link_Bps / Σ_{所有盘} Σ_{盘内 alloc})
最终速率 = alloc × scale
```

**已知语义损失（如实记录，用户已确认接受）**：默认配置下链路（10 GB/s）远紧于单盘（40 GB/s），几乎总是全局瓶颈；链路压缩按比例缩小一切分配，**盘内 water-filling 的需求满足保证在链路处不再成立**。例如盘 1 分得 [16, 24]、盘 2 分得 [40]，全局 Σ=80，scale=1/8，最终 [2, 3, 5]——盘 1 中需求 8 的请求实际只得到 2。若后续实验需要端到端需求语义，再演进为两级填充或全局单层 max-min（超出本设计范围）。

## 4. 已确认决策（2026-10-09 用户答复记录，含二次确认）

| # | 决策点 | 结论 |
|---|---|---|
| 一 | 需求来源 | **每个请求自携带，按"一层传输数据量 ÷ 一层计算时间"推导**；当前聚合模型下即 `kv_bytes_per_token / prefill_token_s`；trace 行 `demand_Bps` 可选覆盖（供异质需求实验），不设全局常量配置 |
| 二 | 作用层级 | **仅每个 ASU 盘内**做水土填充；共享链路维持现行等比例压缩，压缩破坏需求保证的语义损失接受并记录（§3.5） |
| 三 | 再分配轮数 | **迭代到不动点**（标准 max-min fair；单轮方案 [10,30,30,30] 型偏差不采用） |
| 四 | Path 语义（两策略共用，二次确认扩大到现行策略） | **块对所有 Path 可见（放置只定 ASU），IO 请求发出时按确定性最少占用指派 Path**；哈希 (盘, Path) 定位两策略一律废除；P0/P1 选路策略仍是独立后续挂载点 |
| 五 | 排队语义分野（二次确认新增） | `active_split` 保留每 Path FIFO（>256 并发才排队）；**`max_min_fair` 取消 Path 排队**——每个 IO 请求独占一条 Path、数量不限，`paths_per_disk` 仅为名义值 |
| 六 | 与现行策略关系 | **不替换的是速率规则与配置共存**：`active_split` 的均分×上限×链路压缩公式保留为默认；其放置/Path 语义随决策四修改，**历史结果基线须重跑**（§2 后果） |

## 5. 配置接口

`storage` 配置块新增一个字段，trace 新增一个可选字段：

```json
{
  "storage": {
    "bandwidth_policy": "active_split",
    "disks": 2, "paths_per_disk": 256, "disk_Bps": 40000000000,
    "shared_link_Bps": 10000000000, "path_Bps": 1000000000,
    "read_latency_s": 0.0001, "kv_bytes_per_token": 131072
  }
}
```

trace 行（可选字段，缺省用推导公式）：

```json
{"id":"r1","arrival_s":0.0,"prompt_token_ids":[...],"output_tokens":8,
 "remote_prefix_tokens":32,"demand_Bps":2000000000}
```

规则：

- `bandwidth_policy`：`"active_split"`（现行，**缺省默认**，老配置零改动）或 `"max_min_fair"`（本设计）；其他值报错；
- `demand_Bps`（trace 行级）：> 0 有限值，`run.validate()` 校验；覆盖该请求全部块读的推导需求；
- 需求推导使用仿真配置中的 `kv_bytes_per_token` 与 `prefill_token_s`，不引入新配置项；修改二者即改变推导需求（连带改变计算/字节口径，做需求敏感性实验时优先用 trace 覆盖而非改全局系数）；
- `paths_per_disk`：`active_split` 下为指派池大小（超过才排队）；`max_min_fair` 下仅为名义值（snapshot 标签用），不约束并发；
- `path_Bps` 在 `max_min_fair` 下不参与分配（既非上限也非需求）；在 `active_split` 下语义不变（单路径速率上限）；
- `active_split` 下出现需求字段不报错、不生效（便于同一份 trace 跑两种策略对照）。

## 6. 实现方案

改动集中在三个文件，引擎调度/路由层零改动：

1. **`sim/storage.py`**
   - `location()` 拆分：`disk_of(block)` 哈希定盘（两策略共用）；Path 指派移入 `submit`；
   - `Read` dataclass 增加 `demand: float` 字段；
   - `submit(now, key, blocks, demand)`：逐块按策略处理——
     - `active_split`：块 → 盘哈希，选该盘当前占用最少的 Path（平局最小下标）入队，FIFO 不变；
     - `max_min_fair`：块 → 盘哈希，分配新 Path 序号（每盘计数器递增，仅作标签），读请求挂入该盘的活跃集合，**无队列**；
   - `rates()` 按策略分派：
     - `active_split`：现有公式不变（活跃队首计数、`min(path_Bps, disk_Bps/计数)`、链路 scale）；
     - `max_min_fair`：按盘收集 `ready <= now` 的全部读请求，各盘执行水土填充（Σd ≤ C 用 §3.2 公式），全局 `scale = min(1, link/Σ)`；
   - 水土填充实现为模块级纯函数 `waterfill(capacity, demands) -> list[float]`，排序实现，单盘 O(P log P)；确定性成立（无平局随机）；
   - `next_time / advance / snapshot` 的结构沿用：`max_min_fair` 下"队首"即每个就绪读请求，`queued_reads` 语义变为未就绪读请求数（README 注明）。
2. **`sim/connector.py` / `sim/engine.py`**：需求传递。`run.py` 从 trace 行构造 `{request_id: demand}` 表（行覆盖值或推导值），经 `connector.demands`（与现有 `connector.store` 同法注入）到达 `SimConnector`；`submissions` 条目从 `(rid, blocks)` 扩为 `(rid, blocks, demand)`，`engine.schedule()` 调 `store.submit` 时透传。
3. **`sim/run.py`**：`validate()` 增加 `demand_Bps` 校验；构造需求表并注入各引擎 connector；`report.json` 的 `config` 回显天然区分两种策略。

## 7. 边界情形

| 情形 | 处理 |
|---|---|
| 单请求独占一盘（max_min_fair） | 分得整个 `disk_Bps`（active_split 此时受 path_Bps 封顶，是两策略最大差异之一） |
| d > 盘容量（demo 推导值 32.77 GB/s 接近此情形） | 允许；水土填充自然给出 ≤ C 的分配，不预截断 |
| 同盘并发 IO > 256 | `active_split`：最少占用指派下在 Path 上排队，队首独占服务；`max_min_fair`：**无此情形**，Path 数不限（决策五） |
| Σd 恰等于 C | §3.2 边界，剩余为 0，alloc = d |
| 均匀需求 | 退化为无上限均分 C/N（§3.4 量级对比例） |
| 链路压缩破坏需求保证 | 接受并记录（§3.5，决策二） |
| 未过 read_latency 的读请求 | 不参与分配（两策略一致的 `ready` 门控；`max_min_fair` 下即该请求尚不可传） |
| 需求字段出现在 active_split 运行 | 忽略不报错（§5） |
| 同一逻辑请求的多个块读（max_min_fair） | 各自独占 Path、各自携带该请求需求参与分配；请求完成语义仍是全部块收到 |

## 8. 验证计划（实现后执行，遵守"不伪造结果"）

1. **单测**（`tests/` 新增/修订）：
   - `waterfill` 向量断言：§3.4 两例（[10.67,12.67,16.67] 与 [10,28,31,31]）、均匀需求退化 = C/N、单请求 = C、Σd=C 边界、d > C；
   - 需求推导：demo 系数下 d = 32.768 GB/s；trace 覆盖生效；
   - Path 指派：`active_split` 最少占用铺开、>256 排队退化、确定性（同输入同落点）；`max_min_fair` 无排队（任意数量读请求全部直接活跃）；
   - `active_split` 速率规则回归：`min(path_Bps, disk/活跃数) × scale` 公式断言（与位置无关地构造活跃集合验证）；
   - `Storage` 级：max_min_fair 下两请求的完整 submit→advance 时间线（完成时间 = bytes/alloc 解析可对拍）；
   - 配置校验：非法 policy 值、非正 demand_Bps 报错；
   - **存量测试修订**：依赖旧哈希 (盘, Path) 定位的既有断言按新语义改写。
2. **集成与基线重跑**（决策四的必然后果）：五模式 + slow_storage 全部重跑，`scripts/check_results.py` 通过后作为**新基线**记入 `VALIDATION.md`，并注明旧数值对应哈希定位语义、已被本设计取代；
3. **对照实验**：同一 trace × 两策略，比较 makespan / TTFT / bytes_read / path_rates，验证量级对比（§3.4）；
4. 真实输出存 `results/<实验名>/`，数值记入 `VALIDATION.md`。

## 10. 与策略文档 09-17 B 层 / P 层的关系

09-17 的 B 层设想是**分类组份额**规则（B0：SS/LS/SL/LL 四类 20/12/4/4 GB/s 组基础份额 + 空闲均分；B1：保底+借用+权重）。本设计的 max-min fair 是**按请求需求**的通用规则，不含分类组概念，二者不同；但 `bandwidth_policy` 配置项建立了 B 层第一个可切换挂载点，B0/B1 未来可作为该配置的额外取值接入，形成 `active_split | max_min_fair | B0 | B1` 的策略序列。

Path 侧：本设计把 Path 修正为真正的访问通道（两策略一致：放置只定 ASU、发 IO 时指派，与 09-17 的放置模型对齐），但指派规则是最少占用占位，**不构成 P0/P1 策略**——选路策略（含观测滞后、客户端账本）仍是 P 层独立工作。E26 实验中"ASU 另测"的跨组借用、相同字节不同条目等观测项在本设计下可直接复用现有事件输出。
