# 真机实测准备：集群配置与部署信息清单（2026-11-04）

## 0. 目的与用法

本清单把仿真分支的冻结假设逐项映射为真机实测前必须弄清的问题。
当前所有数值（带宽、计时、速率）都是仿真量，不是Ascend910C实测。切真机后必须重新取证。

用法：

- 每项标注来源：集群文档 / 巡检命令输出 / 负责人口头答复。口头答复须复核。
- 每项标注状态：【事实】可复查的证据；【观察】一次或多次实测；【待验证】尚无证据。
- 未弄清的项不猜默认值。仿真配置里的数值只作对照参考，不搬进真机结论。

仿真冻结值速查（对照用，来源见各benchmark的`config.json`与`manifest.json`）：

| 维度 | 仿真冻结值 |
|---|---|
| 逻辑实例 | 12个，TP1/DP8/EP8计算公式（非96个真实NPU进程） |
| 共享池带宽 | 90 GB/s（Mooncake/人工ABC）、180 GB/s（AgentX） |
| 盘模型 | `disks=1`、`paths_per_disk=128`、`path_Bps=2 GB/s`、`read_latency_s=0` |
| 模型 | `glm5_d950pr`、78层、`kv_bytes_per_token=109824` B |
| 上下文 | `max_model_len` 120634（Mooncake）/ 300481（AgentX） |
| vLLM参数 | block16、`num_blocks=30159`、`max_num_seqs=4`、`max_num_batched_tokens=8192`、prefix caching关闭 |
| 到达 | Mooncake 4s、AgentX 12s、人工ABC 6s；每请求输出1 token、prefill-only、K=1 |
| SLO | TTFT≤4×T0，T0按模型公式估算；p95用nearest-rank |

## 1. 集群硬件与组网

### 1.1 节点与角色

| 需弄清 | 说明 |
|---|---|
| 节点总数与角色划分 | 计算、存储、混部还是分开。Mooncake存储单独成节点还是与计算共址 |
| 每节点NPU型号与卡数 | 是否Ascend910C，8卡/节点还是其他 |
| 每节点HBM容量 | 决定`num_blocks`类KV预算在真机的真实上限 |
| CPU/内存/本地NVMe | 影响权重加载、页缓存与日志落盘 |
| 可用节点数是否固定 | 测试期间能否独占，还是与其他业务共址 |

### 1.2 网络

仿真中`shared_link_Bps`是一个聚合数字。真机必须拆开取证：

| 需弄清 | 仿真对应 | 说明 |
|---|---|---|
| 参数面（计算节点间）组网 | 无（仿真不含NCCL/HCCL通信） | 协议RoCEv2/IB、单卡网卡带宽、拓扑spine-leaf、收敛比 |
| 存储面（计算↔存储）组网 | `shared_link_Bps` 90/180 GB/s | 独立组网还是与参数面共用；几张网卡、几条路径聚合出总额 |
| 单路径带宽与并发路径数 | `path_Bps=2 GB/s`、`paths_per_disk=128` | 真机单连接/单队列深度实测值；并发扩展是否线性 |
| MTU与交换机配置 | 无 | jumbo frame是否开启；PFC/ECN配置；是否有限速策略 |
| 网络实测方法 | 无 | 用什么工具压测（iperf3/RDMA perftest/自研）；何时测、测多久 |

风险：共享池"90 GB/s"在真机可能是多网卡×多路径的聚合。逐路径带宽与路径数不弄清，租约账本的每盘B/s粒度就无法落地。

## 2. 共享KV存储（Mooncake侧）

| 需弄清 | 仿真对应 | 说明 |
|---|---|---|
| 部署形态 | — | Mooncake master/allocator/存储节点各几个进程，部署在哪些机器 |
| 物理盘数量与单盘带宽 | `disks=1`、`disk_Bps` | 真机几块NVMe、单盘顺序读多少GB/s；仿真单盘，真机多盘时HRW落盘逻辑要对应 |
| 传输引擎 | — | RDMA还是TCP；内存注册区域大小；连接数上限 |
| 实测聚合带宽 | `disk_Bps=shared_link_Bps` | 真机上盘带宽与链路带宽谁先饱和；饱和点是否随并发变化 |
| 读延迟 | `read_latency_s=0` | 真机每path固定延迟多少；小读（1.5 GB级别单请求独占读）实测耗时 |
| 容量与淘汰 | `gc_policy=defer_during_run` | 共享池总容量配额；淘汰策略是什么；测试中途会不会触发淘汰 |
| KV块大小核对 | `kv_bytes_per_token=109824` B、block16 | 真机engine的KV布局（层数、GQA头数、dtype）折算每token字节数，与仿真值对拍 |
| 命中语义 | `cache_model=first_seen`、人工命中构造 | 真机Mooncake按块哈希命中；回放给定命中率需先按同一哈希预写KV，映射规则要弄清 |

风险：人工构造的命中量在真机不会自然出现。必须确定"先写入哪些块、何时写入、如何校验命中数"，否则h/u分布失真。

## 3. 模型与推理引擎

| 需弄清 | 仿真对应 | 说明 |
|---|---|---|
| 模型身份 | `glm5_d950pr` | 真机部署的模型名、参数量、层数（仿真78层）、精度 |
| KV布局 | `kv_hbm_reuse=true`、稀疏HBM命中 | GQA分组、head_dim、KV dtype；与`kv_bytes_per_token`核对 |
| 上下文长度 | 120634 / 300481 | 真机`max_model_len`支持到多少；300k级上下文对显存/块表的要求 |
| 版本三件套 | vLLM 0.20.2、vllm-ascend 0.20.2rc1、Dynamo 1.5.0（含commit） | 真机用哪组版本；与本分支固定commit的差异清单 |
| CANN/驱动/固件 | 无（CPU仿真） | 版本号与兼容矩阵；升级需重测 |
| 并行与实例映射 | 12逻辑实例、TP1/DP8/EP8公式 | 真机12个实例怎么摆：每实例几卡、共几张卡、跨几个节点；DP8/EP8是真实展开还是继承公式口径 |
| vLLM调度参数 | block16、`max_num_seqs=4`、`max_num_batched_tokens=8192`、prefix caching关闭 | 真机是否沿用同值；chunked prefill是否开启 |
| 口径 | prefill-only、每请求输出1 token | 真机是否保持同口径；若输出多于1 token，TTFT/完成时间语义都要重新定义 |
| KV传输模式 | `layer_pipeline`逐层预取、KV就绪屏障 | 真机是否有逐层加载能力；没有则调度语义与仿真不同 |

## 4. 调度与准入移植

| 需弄清 | 仿真对应 | 说明 |
|---|---|---|
| 四臂落点 | direct/tfs-a01/tfs-a1/tfs-lease | 真机Dynamo picker与加权Rust scorer如何部署（`build_weighted_dynamo`产物）；三臂是否同源同版本 |
| EDF与T0 | `request_ordering=edf`、slo_multiplier=4 | 真机T0用哪个估时公式；`glm5_actual_batch_work_v2`与`glm5_direct_sum_v1`的选择要有依据 |
| P75分类与配额 | quantile 0.75、条数cap=参考带宽÷P75阈值 | 真机分类统计在哪维护；预热后重置的机制 |
| 租约账本 | 每盘B/s、五步放行、轻重线=disk_Bps×10% | 真机"每盘"粒度是什么；账本的带宽值是静态配置还是实测更新 |
| 释放时机 | `release_on=first_token` vs `lease_events`（读开始/末层读毕） | 真机在哪埋点能拿到读开始与末层读毕事件 |
| 带宽感知 | 仿真无实时带宽传感器 | 真机要不要加带宽采样；不加则租约账本只能用静态容量值 |
| 反馈模式 | 四类在线执行反馈关闭 | 真机默认开哪些反馈；与仿真关闭口径不一致要记录 |

## 5. 负载回放与SLO

| 需弄清 | 仿真对应 | 说明 |
|---|---|---|
| 请求发生器 | 固定benchmark→按计划时刻发HTTP | 真机客户端部署位置（集群内/外）；并发模型；`K=1`的发送语义如何复现 |
| 到达控制 | 43个计划时刻、相隔约95.24ms、每波3–16条；总窗口4s/6s/12s | 真机网络与排队会引入迟到；计划到达≠实例开始执行，须记录实际接收时刻 |
| 输入冻结 | trace.jsonl的h/u、token、顺序、到达时刻不可修改 | 真机回放用同一JSONL；token化在客户端还是服务端 |
| 预热 | 每组72条small/median/large三阶段 | 真机预热怎么构造；预热后是否清空共享池、重置P75历史与GC窗口 |
| SLO口径 | 每请求TTFT≤4×新T0；TTFT=网关接收至首token，含排队 | 真机TTFT计时起止点定义；跨节点时钟误差是否影响判级 |
| 轮次 | 每臂360请求正式 | 真机重复轮次计划；全部有效轮次保留，不只留有利轮次 |

## 6. 观测、指标与验收

仿真输出的每类验收文件，真机要有对应数据源：

| 仿真产物 | 真机需弄清的数据源 |
|---|---|
| `report.json`（逐请求TTFT/事件时刻） | 网关与engine侧逐请求时间戳；采样精度与时钟源 |
| `benchmark.check.json`（均值/p95/SLO） | 汇总脚本输入数据从哪来；p95口径是否仍nearest-rank |
| `formula_check.json`、`layer_check.json` | 真机是否有batch形状、逐层时刻的日志或trace；没有则公式与层因果无法验收 |
| `hit_check.json` | Mooncake命中数与命中块的核对接口 |
| `lease_accounting.check.json` | 租约放行/释放事件流；带宽账本对账数据 |
| `driver.json`（资源保护/宿主内存） | NPU/内存/温度/功耗监控；降频或OOM的判定信号 |
| counters（存储带宽、队列） | NPU利用率、存储读带宽、网络流量的采集链路（已有Prometheus还是新搭） |

另需弄清：

- 集群时钟同步方式（NTP/PTP）与节点间误差上界。TTFT跨节点统计依赖此值。
- 日志与事件的保留位置、容量配额、保留时长。360条×多臂×多轮的原始事件不小。

## 7. 环境与运维

| 需弄清 | 说明 |
|---|---|
| OS与内核版本 | 与NPU驱动、容器运行时的兼容性 |
| 部署方式 | 裸机、k8s还是自研脚本；配置如何版本化；能否一键重建环境 |
| 容器镜像 | 镜像仓库地址、tag、内含的vLLM/vllm-ascend/CANN版本；与版本三件套核对 |
| 权限 | root还是普通用户；NPU设备、RDMA设备、大页内存的访问权限 |
| 网络与端口 | 防火墙规则；Dynamo、Mooncake、监控所用端口的占用与申请流程 |
| 独占性 | 测试窗口是否独占集群；共址业务的干扰记录方式 |
| 模型权重分发 | 权重从哪拉取、每节点磁盘是否放得下、校验和 |
| 故障与重跑 | 节点故障、进程崩溃后的恢复流程；一轮失败如何标记与保留 |
| 环境快照 | 开测前固定一次全量版本快照（驱动、CANN、镜像、代码commit），与结果一起归档 |

## 8. 优先级

- P0（不弄清无法开跑）：节点/卡数、网络组网、版本三件套与CANN、模型与上下文、部署方式与权限、请求发生器。
- P1（不弄清结论无效）：存储面实测带宽与路径粒度、KV每token字节数核对、命中构造映射、TTFT口径与时钟同步、独占性。
- P2（校准与移植）：逐层事件埋点、租约账本带宽来源、batch形状日志、真机数据反哺仿真公式。

## 9. 附：常用巡检命令草案

```bash
npu-smi info                    # NPU型号/卡数/固件
lscpu; free -h; lsblk           # CPU/内存/盘
cat /usr/local/Ascend/ascend-toolkit/latest/version.cfg 2>/dev/null || true   # CANN版本
npu-smi info -t usages -i <id>  # 测试中利用率/带宽
ethtool <nic>; ip link          # 网卡速率与状态
ibstat 2>/dev/null || rdma link show 2>/dev/null || true   # RDMA端口
nvme list; fio --name=t --filename=/dev/nvmeXn1 --rw=read --bs=1M --direct=1 --runtime=60 --time_based   # 单盘带宽
chrony tracking 2>/dev/null || ntpstat 2>/dev/null || true  # 时钟同步
```

命令输出须存档并与结果同放。不同批次巡检结果不一致时，以测试当日为准。
