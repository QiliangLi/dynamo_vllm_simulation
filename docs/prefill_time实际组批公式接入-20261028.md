# prefill_time 实际组批公式接入

2026-10-28。用户要求将已验证的候选组批公式接入正式 prefill_time 计时链。

## 问题与目标

当前 GLM5ComputeTimeModel 仍将异构请求变成最大长度乘请求数，并用
`DP=32//bs` 改变参考部署。工作区候选 glm5_actual_batch_work_v2 已实现实际
工作量聚合和 MoE 路由工作量守恒，但正式 DV 没有调用候选代码。

本次把候选公式收入 DV 自身，由正式计时、请求参考时间和逐层执行共同使用。
修改批次耗时估计，不改变原生 Scheduler 的 token 预算、请求选择、KV 分配和路由。
SA/ABC 与线性模型不切换公式。

## 实现

1. 新建 `sim/timing_models/prefill_time_batch.py`，提供 `estimate_batch()` 与
   `per_batch()`。输入为每条请求本轮结束长度和新增长度 `(h+u,u)`。
   保留原冻结 `glm5_d950pr_reference.py` 与 SHA，用于算子常数和历史追溯。
2. 线性层用 `sum(u)`；indexer 分别累加请求的打分量和扫描长度；稀疏注意力
   保留原 top-k 和请求内部 KV 复用假设。MoE、dispatch、combine 共用
   `DP*sum(u)*top_k`，专家放置余数准确分配，权重读取按活跃专家期望计量。
3. 正式 `compute.mode=glm5_d950pr` 默认调用新版。配置 `compute.tp/dp/ep`
   固定部署，默认 TP1/DP8/EP8，与此前四请求候选示例一致；要求 EP=DP*TP。
   这些是公式参考布局，不自动推定真实实例卡数。实际 batch 改变时不改变部署。
   标准配置和有效运行配置显式写出该布局与 batch_time_model 版本。
4. 返回原 timing 字段，新增实际工作量、MoE 明细、模型版本和逐层时间。
   `padded_prefill_tokens` 与实际新增量相同。层时间保持3个Dense层和75个MoE层，
   engine_overhead 仍只按既有协议计一次。前缀KV字节仍精确按 h 求和；
   逐层执行后续 chunk 不重新读取前缀。
5. GLM 请求画像升级 `glm5_reference_v3`，以同部署、同公式计算 singleton T0。
   旧 v1/v2 标签显式警告迁移；历史运行必须使用冻结源码。
   单请求计算时间、压力、期限和SLO可能变化，不能把新旧结果差异归因于TFS。
6. 工作区原候选入口改成兼容转发，不再维护第二份公式。v1源码快照保持不变。

## 验收

- 迁入候选不变量测试：拆批/合批路由量、FLOPs和激活字节守恒；零token；
  EP12余数；固定部署；请求顺序与并发不变性；不修改冻结来源。
- 正式入口独立算术审计，覆盖异构长度、前缀、TP、EP12、启动开销、单位和层总和。
  旧运行无版本字段时按历史算法审计，不使用新公式重释旧结果。
- 检查三种KV协议的参考T0、分块前缀只读一次、实际层时间与整批时间一致。
- 运行完整现有单元测试；再用本机固定依赖运行小规模真实链路，检查公式、层屏障、
  完成数、KV字节、路由/配额释放与服务清理。不重跑360收益矩阵。

## 边界

新版沿用GLM5/D950PR的硬件常数及均匀独立专家路由假设。没有GLM5实机定标，
没有模拟真实专家倾斜、专家kernel内部补齐、计算通信重叠或物理网卡传输量。
4090/Qwen实测拟合系数不进入GLM公式。默认稀疏HBM命中1，避免额外固定带宽
取数与独立共享存储服务重复计算。验收结果完成后另记VALIDATION。
