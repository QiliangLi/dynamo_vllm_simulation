# TFS与Mooncake360实验分支使用说明

本分支把请求级TFS、等待重读评分、实际组批计时和固定benchmark放入同一个DV仓库。
另新增[AgentX360固定输入](../benchmark/agentx_random_360_12s_12_180GBps/README.md)：360条、12秒到达、180GB/s、12实例。统一入口已支持显式长上下文外推和专用运行验收；命令见该负载README。下文运行入口接受目录中支持完整运行的负载；共享带宽读取所选benchmark的配置。
同事或AI只需本仓库及固定版本依赖，即可导出输入、启动实验、读取结果和执行验收。
同步版本和逐文件SHA见包内RUNTIME_SYNC.json；历史章节按日期理解。
本分支不需要原作者的外层工作区、SA仓库、聊天记录或历史results/temp目录。

## 3. 一条请求如何执行

```text
固定benchmark → 按计划到达时间发HTTP请求 → 准入网关 → 原生Dynamo选择实例
  → vLLM等待队列 → scheduler申请全局重读许可 → token预算与slot分配
  → SchedulerOutput确定实际batch → 仿真执行器逐层等待KV并计算
  → 首token反馈 → 释放许可、回收路由记账 → 请求完成
```

直接准入跳过TFS许可门控。两种TFS在实例内scheduler申请许可。
α影响路由对等待重读的评分：0.1降低等待负载的计分，1保持完整计分。
两种TFS都在首token释放许可，没有实现“实际开始IO才占配额、IO结束立即释放”。
本分支没有新增实时读取真实存储带宽的传感器。配置中的共享带宽是仿真容量与准入参考值。

## 4. 从零准备环境

以下命令从仓库根目录开始。建议Python3.12；固定依赖见包内requirements.lock。
本机验证复用了已安装依赖，没有重新执行Linux全新bootstrap。不要把本机通过扩大成全平台通过。

```bash
cd dynamo_vllm_cpu_sim
bash scripts/bootstrap.sh
bash scripts/bootstrap_stack.sh
```

Linux使用CPU PyTorch/torchvision。macOS Apple Silicon的torch、Dynamo原生构建与vLLM empty-device适配，
按[包内README](../dynamo_vllm_cpu_sim/README.md)的macOS小节执行；无模型权重、CUDA或CANN要求。
首次安装需联网；正式实验使用本地模型stub与tokenizer，可离线。

准备独立加权Dynamo构建。它只供实验frontend加载，不替换已安装wheel，不修改固定upstream源码。

```bash
.venv/bin/python scripts/build_weighted_dynamo.py \
  --source upstream/dynamo --output build/weighted-dynamo --release --jobs 4
```

输出`build/weighted-dynamo/python`及`build.json`。后续三臂共用同一构建。
Rust/protoc等原生工具须按Dynamo固定版本准备。macOS若本机SDK头损坏，参考旧README的适配记录。
构建目录必须不存在；失败尝试保留，换一个新输出目录重试。

## 5. 先校验输入，再跑冒烟

回到仓库根目录校验目录中的冻结输入：

```bash
python3 benchmark/manage.py verify
```

预期`status=passed`；请求总数由当前目录汇总。当前名单见[Benchmark目录](../benchmark/benchmark目录.md)，AgentX已纳入运行器`--case all`；人工ABC六秒负载也已纳入完整运行，见其README。
需要只导出输入时，使用manage.py的export；新统一运行器会自行导出，无需手动生成token数组。

在包目录启动小规模真实进程栈：

```bash
cd dynamo_vllm_cpu_sim
.venv/bin/python scripts/run_benchmark.py \
  --case mooncake_abc_360_4s_12_90GBps --arm tfs-a01 --smoke \
  --dynamo-python build/weighted-dynamo/python \
  --output results/benchmark_runs/smoke-abc-a01
```

冒烟为2实例、Mooncake每类选最短/最长，AgentX每类另取中位；全部计划时刻置零、不预热，仅检查运行正确性。
简单版本4条、ABC6条、ABCD8条；AgentX6条，含最长300480 token。输出目录必须不存在；不要把冒烟延迟与360条结果比较。
固定端口28765/28766及worker系统端口29111起，仅串行运行；端口占用会失败，不清理其他人的进程。

## 6. 正式对照命令与参数

单个benchmark三臂：

```bash
.venv/bin/python scripts/run_benchmark.py \
  --case mooncake_abc_360_4s_12_90GBps --arm all \
  --dynamo-python build/weighted-dynamo/python \
  --output results/benchmark_runs/abc-r1
```

运行当前目录中支持完整运行的benchmark与三个策略的组合（任务数由目录决定）：

```bash
.venv/bin/python scripts/run_benchmark.py \
  --case all --arm all \
  --dynamo-python build/weighted-dynamo/python \
  --output results/benchmark_runs/all-r1
```

|参数|含义|
|---|---|
|`--case`|Benchmark目录中的支持名称、旧别名或`all`；包括`agentx_random_360_12s_12_180GBps`|
|`--arm`|`direct`、`tfs-a01`、`tfs-a1`或`all`|
|`--dynamo-python`|本机加权Dynamo构建的python目录；三臂同源并校验build.json/二进制SHA|
|`--output`|新的独立实验目录；拒绝覆盖|
|`--seed`|仅决定组间运行顺序，默认20261029；不重排请求或改变类别|
|`--smoke`|小规模正确性检查；正式回放不要带此参数|

共同条件：按所选benchmark配置的单共享池容量、K=1、12逻辑实例、block16、每步最多4请求/8192新token，
78层流水、TP1/DP8/EP8、无本地prefix复用、EDF；Mooncake正式4秒到达，AgentX正式12秒到达。
每组72条预热分small/median/large三阶段，确认12实例覆盖且排空；
排除预热P75历史，重置正式存储GC边界，再运行360条；三臂均采用相同预热，当前均关闭四类在线执行反馈。
内存可用量低于768MiB持续10秒或单组超过900秒会中止；保护触发不是成功结果。

|case|计算额度|人工类别|
|---|---|---|

|mooncake_abc_360_4s_12_90GBpsd|相同全局204699|A220/B90/C30/D20|

总input均5117755 token；ABC与ABCD总读取均539571462144 B。
简单版本总读取539258683392 B，历史结果在120 GB/s运行；最初三个负载为90 GB/s；新增带宽版本以Benchmark目录及各自配置为准。
交付时已验收简单版本90 GB/s的直接准入完整流程，尚未重新进行它的三臂性能比较。
不能把120 GB/s旧结果直接当成本分支简单版本的90 GB/s基线。

原input与请求顺序保留。分类时按input长度选成员，回放时恢复原行号顺序。
没有人为排成ABC循环或按类别分段，也没有随机打乱。类别与时间关系来自原trace。
三份到达时间逐请求相同：43个计划时刻、相隔约95.24ms、每波3–16条。
同一波的HTTP投递仍可能有系统迟到；计划到达不等于实例开始执行。
原output_length不参与工作量分配，hash_ids不参与命中；命中量是人工构造。
人工标签不等于TFS在线P75重读分类，也不保证每个时间段的类别配比固定。

## 8. 输出、验收与结果解释

主目录有`plan.json`、`progress.json`、`summary.csv`和逐组日志。
每个case有冻结`package/`、输入/源码/native指纹及新画像。
逐组文件位于`<output>/<case>/package/results/<arm>/`：

|文件|用途|
|---|---|
|`driver.json`|总状态、资源保护、宿主内存/swap与所属残留进程|
|`run/measured/report.json`|正式360条HTTP请求，不含预热|
|`run/report.json`|含72预热的完整审计，不用于正式均值|
|`run/benchmark.check.json`|正式均值/p95/SLO/完成窗口及读取量|
|`run/check.json`、`formula_check.json`、`layer_check.json`、`hit_check.json`|原生链路、公式、层因果和命中合同验收|
|`run/read_admission.check.json`、`routing.score.check.json`|TFS准入及评分账本；直接准入无此要求|
|`run/warmup.check.json`、`warmup.history.check.json`|预热排空及分类历史隔离|

正式TTFT按网关实际接收时刻至首token统计，包含排队；p95使用nearest-rank。
SLO为各请求TTFT≤4×新T0，不是统一198.5ms。K=1的HTTP/IPC/轮询/宿主调度开销都保留。
代码和输入相同不保证时延数值逐次一致；需要重复实验并保留全部有效轮次。
历史观察含改善和反例：ABC的α0.1较好，ABCD的α1较好；ABCD的α0.1平均TTFT劣化。
这些单次结果不能当作性能保证，也不能证明旧负载的优化目标完成。
