**一句话**：用磁盘上的状态机执行全部硬规则（跑什么、怎么算分、谁能改什么）。LLM Agent 只在固定环节出场：诊断、提案、反驳、复核、复盘。流程分三层循环，最外层允许 Agent 改自己的提示词、工具和搜索分配，但评价代码与验收规则冻结。

## 一、设计依据

以下三个事实决定了流程的形态和验收门槛。本文按「代码事实」「性能观察」「待验证」区分各类陈述。

### 事实 1：余量在负载之间差别很大（性能观察，粗估）

用已有的默认策略（light）轮次估了一个「无争用参考」：每条请求按独占链路的参考服务时间执行，worker 归属和到达顺序沿用 light 轮，每个 worker 按 FCFS。它是乐观的粗略参考，不是紧界，待第 0 代精算。

| 负载 | 默认策略 平均 TTFT | 无争用参考 | 默认策略 完成时间 | 无争用参考 |
|---|---|---|---|---|
| 408 | 2.08 s | 0.79 s（−62%） | 11.9 s | 9.7 s（−19%） |
| 540 | 4.91 s | 1.86 s（−62%） | 18.8 s | 14.3 s（−24%） |
| mooncake | 1.97 s | 0.85 s（−57%） | 16.6 s | 13.6 s（−18%） |
| AgentX 窄 | 17.35 s | 14.31 s（−18%） | 48.0 s | 42.9 s（−11%） |
| AgentX 宽 | 19.17 s | 16.50 s（−14%） | 52.5 s | 47.1 s（−10%） |

默认策略列：408、540、mooncake、AgentX 宽为 5 轮均值，AgentX 窄为 1 轮。无争用参考各取 1 轮 light 计算。

AgentX 两版余量小，因为它们基本是计算受限：模型计算总量分别为 157 s 和 176 s，分到 4 个 worker。准入策略改变不了计算量。

### 事实 2：链路是保活的（代码事实）

`dynamo_vllm_cpu_sim/sim/storage.py` 的分配规则是带需求上限的最大最小公平（`waterfill`），有未读数据链路就不空转。所以准入策略减少不了总读取量，只能减少争用造成的停顿、改变谁先读。

链路时间（读取量 ÷ 25 GB/s）：408 为 8.2 s，540 为 9.3 s，mooncake 为 11.6 s，AgentX 两版为 28–29 s。

### 事实 3：现有 TFS 离目标很远，方向也不一致（性能观察，5 轮均值）

相对默认策略，普通 TFS 的结果：

| 负载 | 平均 TTFT | 完成时间 |
|---|---|---|
| 408 | −13.7% | +1.6% |
| 540 | −8.0% | −0.5% |
| mooncake | +4.7% | +4.2% |
| AgentX（各 1 轮） | 约 ±1% | 约 ±1.5% |

代码上的缺口：

- 判满只数许可条数，不看带宽：`dynamo_vllm_cpu_sim/sim/stack/read_admission.py` 的 `FrozenClassification.acquire`，条件是 `held >= cap`。轻读请求不申请许可，所以不记账。
- θ 同时当分类线和额度分母：`dynamo_vllm_cpu_sim/sim/admission.py` 的 `AdmissionController.on_arrivals`，`cap = max(1, floor(B / θ))`。
- 执行器不向账本上报加载开始和结束，加载事实只用于离线审计；许可到首 token 才释放。见[实验分支使用说明](实验分支使用说明.md)。

另外，同机重复运行的波动是：短请求负载的平均 TTFT 半宽约 ±2.5–6%。所以任何结论都必须多轮才能下。

## 二、总体结构

```
第 3 层  流程自改进（每代一次，元策略师）
         可改：假设库、提示词、工具、搜索分配、筛选轮数。下一代生效，可回滚。
   │
   ▼
第 2 层  机制搜索（每代一轮）
   诊断 → 两组提案 → 红队盲审与答辩 → 实现与静态门
       → 实测筛选 → 实测确认 → 独立复核 → 裁决 → 记账
   │  机制确定后
   ▼
第 1 层  参数搜索（程序执行，不用 LLM）
   │
   ▼
冻结区   评价代码、指标定义、验收门槛、允许修改的文件清单、基线定义、账本
```

设计原则：

- 硬规则交给程序。跑什么、怎么算分、谁通过，都由冻结的代码决定。
- Agent 只做需要判断的事：读数据、想机制、挑毛病、复盘。
- 所有结论以真实栈上的多轮运行为准。辩论只用来省运行预算，不用来定输赢。

## 三、角色

| 角色 | 执行者 | 模型 | 职责 | 产物 | 约束 |
|---|---|---|---|---|---|
| 编排器 | 程序 | 无 | 状态机、排队跑轮次、算分、裁决、记账 | 状态文件、账本 | 只执行冻结规则，不做判断 |
| 诊断分析师 | Agent | 5.3 | 读摘要，定位每个负载的时间去向 | 瓶颈卡 | 只读结果 |
| 提案组 A、B | Agent × 2 | 5.4 | 各出 1–2 个候选并实现 | 候选卡、覆盖层、单测 | 两组视角不同、每代轮换；只能动允许清单 |
| 红队 | Agent | 5.4 | 找针对性常数、标签依赖、饿死和死锁；设计攻击负载 | 攻击清单、攻击负载 | 先盲审代码，再看理由；攻击须在真实栈上运行证实才算数 |
| 复核审计 | Agent | 5.3 | 从原始运行目录独立重算两个指标 | 审计结论 | 只拿原始目录，不拿提案组的脚本 |
| 理论评审 | Agent | 5.4 | 盲评是否通用、因果链是否成立 | 解释质量分 | 看不到提案组身份 |
| 元策略师 | Agent | 5.4 | 复盘一代，出流程修改单 | 修改单 | 不能碰冻结区 |
| 工具匠（按需） | Agent | 5.4 | 造分析脚本、快速代理模型、并行运行 | 工具、验证报告 | 工具过保真门才能启用 |

模型列里的 5.4、5.3 指 GLM-5.4、GLM-5.3，是默认分配，待确认。本机只有 GLM 一族三个模型，所以对抗性来自角色和信息隔离，不靠跨厂商模型。

## 四、一代怎么走

1. **诊断。** 程序先从运行产物生成摘要：超载秒数、worker 空转秒数、逐类 TTFT、许可时间线。分析师据此给每个负载出一张瓶颈卡。
2. **提案。** 两组各出 1–2 张候选卡。必填：触发信号、动作、参数（不超过 6 个）、尺度不变声明、因果链、预测的数据特征、失效模式和保护。
3. **红队盲审与答辩。** 最多两轮。确认存在针对性或作弊路径的候选直接淘汰，其余带着风险标记进入运行验证。
4. **实现与静态门。** 允许清单、通用性检查、相关单测、一次冒烟。不过退回一次，再不过淘汰。
5. **运行筛选。** 5 个负载各 2 轮。两个指标方向都对才进入确认。
6. **运行确认。** 补到 5 轮。
7. **复核。** 审计独立重算；编排器运行红队给出的攻击负载；核对预测的数据特征。
8. **裁决。** 程序按冻结规则打分，理论评审给解释分，决定是否更替冠军。
9. **记账。** 所有候选（含淘汰的）追加进账本，更新状态页和一代小结。
10. **复盘。** 元策略师出流程修改单。

### 动作空间

当前分支的四实例入口只有 light、tfs、a_cap1 三个固定臂，没有参数入口，所以另建候选运行器。候选以「覆盖层」形式存在沙箱里：在入口生成的独立 harness 上替换允许的文件，并覆盖配置里的 `admission.*` 和 `routing_accounting.*`。

路径均相对仓库根目录。包内 stack 模块位于 `dynamo_vllm_cpu_sim/sim/stack/`，下表省略该前缀。

允许修改（初版清单，第 0 代定稿）：

- 准入账本与分类：`dynamo_vllm_cpu_sim/sim/admission.py`、stack 下的 `read_admission.py` 和 `admission_service.py`。
- 调度侧闸门：stack 下的 `scheduler_admission.py` 中的 `ReadGate`。对 vLLM 调度器的 AST 锚点部分不得改动。
- 反馈通路：stack 下的 `feedback.py`、`admission_outbox.py`、`load_observation.py`、`best_effort.py`。
- 请求提示：stack 下的 `storage_hint.py`。
- 路由评分的 Python 侧：stack 下的 `routing_accounting.py`、`async_score.py`。
- 新增文件：`dynamo_vllm_cpu_sim/sim/stack/policy/` 目录。

禁止修改：

- 存储模型：`dynamo_vllm_cpu_sim/sim/storage.py`，stack 下的 `storage_service.py`、`layer_storage.py`、`layerwise.py`。
- 计算模型：`dynamo_vllm_cpu_sim/minimax_prefill/`、`dynamo_vllm_cpu_sim/sim/compute_time.py`、`dynamo_vllm_cpu_sim/sim/timing_models/`。
- `dynamo_vllm_cpu_sim/patched/` 下的调度器与路由补丁。
- `dynamo_vllm_cpu_sim/scripts/run_tfs_stack.py`、仓库根的 `scripts/four_worker/` 和各校验脚本。
- `benchmark/`、`source_dev/` 及原生构建。

如果搜索得出「目标在动作空间内达不到」，流程停下来如实报告，不自行扩大范围。

## 五、「通用方案」怎么被强制

- **G1 一套参数跑全部负载。** 候选代码不得读取负载名、类标签、请求 ID、trace 内容、文件路径、环境变量。
- **G2 尺度不变。** 链路带宽和所有需求同乘一个系数，决策不变。用属性测试检查。
- **G3 复杂度上限。** 参数不超过 6 个，带物理单位或无量纲，写明含义。
- **G4 留出验证。** 压力负载由冻结 trace 派生，只放沙箱，不进 `benchmark/`：
  - 带宽 10 和 50 GB/s；
  - 到达密度减半和加倍；
  - 需求分布：双峰、连续、全重、全轻、多零读；
  - 实例数 2 和 8。

  冠军在压力套上不得有超出噪声的回退。另做留一法：去掉任一负载重新排序，冠军仍须进前三。
- **G5 解释。** 预测的数据特征没出现，就标为「未解释收益」，不能当冠军。

## 六、评价协议（冻结）

- **基线。** 默认策略 light，同一提交、同一入口步骤。普通 TFS 另测，作参考。
- **指标。** 平均 TTFT 和完成时间，沿用 `scripts/four_worker/summary.py` 的定义。其余只作诊断，不计分。
- **门槛（建议规则）。** 第 0 阶段余量的 40%，下限 TTFT 10%、完成时间 3%，五个负载都过。按第一节的粗估，408、540、mooncake 约为 TTFT 23–25%、完成时间 7–10%；AgentX 约为 10% 和 4%。
- **统计。** 单侧 95% 置信，方差取自基线历史。最终报告只用冠军与基线各 10 轮、交替进行的新数据。
- **排序分。** 每个负载算「闭合了余量的多少」，均值与最差负载各占一半，防止靠单个负载拉分。
- **冠军更替。** 候选通过全部门禁，且排序分以 95% 置信高于现任冠军，才更替。
- **漂移控制。** 每 10 轮插 1 轮 light 对照。对照偏离历史带 3 个标准差，就重测基线，窗口内结果作废重跑。

## 七、防作弊

- 评价代码、门槛、允许清单做 SHA256 固定，状态机每次开工先校验。
- 允许清单外的文件一律拒绝运行，运行后对 harness 做全量 diff。
- 每轮必须通过入口原有断言，且请求数、读取字节、模型计算总量与基线逐值相等。
- 审计的重算结果与评价器相差超过 0.5% 就查。
- 账本只追加，失败轮和被否决的候选都留档。
- 中间结果不进仓库，只在冠军更替时提交一次。

## 八、RSI 层

- **可改**：假设库及优先级、提案与红队提示词、工具、探索与利用的预算分配、筛选轮数与早停规则。
- **不可改**：冻结区。
- **生效方式**：每项修改记录原因和预期收益，下一代生效，比较「每百轮的确认收益」，连续两代下降自动回滚。每代修改不超过 3 项。
- **代理模型门。** 快速代理模型只用于筛选。它须在至少 12 个已知配置上与真实栈方向一致率不低于 80%、秩相关不低于 0.6。验收只认真实栈。
- **边界。** 模型权重不会变。递归效果体现在账本、经验、工具和搜索策略逐代累积。

## 九、无人值守怎么保证

- **状态在磁盘。** 状态文件原子写入，每步幂等。LLM 任务都是短命子代理，输入是摘要文件，输出是结构化文件。
- **心跳驱动。** 定时自动化每 20 分钟触发「推进到时间片用完」。WSL 重启、会话退出、额度报错都从断点继续。
- **角色不提问。** 提示里写明：无法判断时按保守默认处理，写入阻塞清单。
- **自动停止。** 以下情形写 `NEEDS_HUMAN.md` 后停：冻结区校验失败、漂移重测后仍在、连续 10 轮运行失败、磁盘不足。
- **控制点。** 放一个 `PAUSE` 文件即暂停；`STATUS.md` 看进度；预算写在章程文件里；停用自动化即总闸。
- **安全。** 候选代码以专用非 root 用户在沙箱内运行；用命令钩子拦截越界操作（改 `benchmark/`、推送其他分支、删除结果目录）。

## 十、预算与产出

- **机器时间。** 单轮 1–2.5 分钟。一个候选筛完约 15–20 分钟，确认再加约 25 分钟。一代约 2–3 小时。
- **默认上限。** 72 小时或 800 轮，先到为准，约 20 代、80 个候选。
- **LLM 用量。** 每代约 8–10 个任务。成本没有可靠数据：一次只读调研（约 9 分钟、104 次工具调用）累计约 660 万 token。按此量级，全程可能达数亿 token。对策：摘要由程序生成、每个任务限工具调用次数、机械角色用 GLM-5.3-Flash。
- **产出。**
  - 冠军策略，合入为 `scripts/run_4w25.sh` 的新臂；
  - 设计与证据文档；
  - 最终 10 轮确认数据和压力套结果；
  - 全部候选账本和经验清单。

## 十一、lql_dev 上可参考的内容

以下来自对 `lql_dev` 的只读调研。

- **在读带宽合计已有实现，但只在 lease 臂。** 位置是 `dynamo_vllm_cpu_sim/sim/stack/lease_ledger.py`：`sum_after = heavy_sum + 候选 share_Bps + light_rate_Bps`，轻读速率由存储侧流量推算。三个 lease 文件（`lease_admission.py`、`lease_ledger.py`、`lease_events.py`）只在 `lql_dev`，可以移植到四实例的调度前准入。
- **overdraft 和 cap_policy 不在当前分支。** 它们在 `lql_dev` 的 `dynamo_vllm_cpu_sim/sim/admission.py` 和 `dynamo_vllm_cpu_sim/sim/stack/read_admission.py`，入口是 `BENCH_TFS_JSON` 和 `--tfs-json`。定量结论多为单轮。
- **可当红队先验攻击库的反例。**
  - measured 策略在 cap=1 时自锁：串行下按实际占用算出的中位数，得到的 cap 仍是 1。
  - 放宽 cap 在巨需求负载上有害。
  - 固定 cap=1 让 408 的完成时间从约 12.2 s 变到 20.5 s。
  - lease 释放改回首 token 后更差。

相关文档（均在 `lql_dev`）：`docs/evidence/tfs-cap-relief-20261117/`、`docs/TFS空闲实例强制准入-20261028.md`、`docs/TFS前置分诊与反馈开销对照-20261029.md`、`docs/存储带宽租约调度实现方案-20261031.md`、`docs/租约吞吐目标调优-20261103.md`。

## 十二、待确认事项

1. **门槛规则。** 默认余量的 40%，下限 TTFT 10%、完成时间 3%。
2. **AgentX 的期望。** 按余量，它的上限只有 TTFT 14–18%、完成时间 10–11%。要求更高就超出准入策略能动的范围。
3. **预算。** 默认 72 小时、800 轮。建议再加一个 token 上限。
4. **分支。** 默认从 `lql_1125_opt` 新建 `lql_1125_tuning`，`lql_dev` 只作参考来源。
5. **模型分配。** 默认提案、红队、理论评审、元策略师用 GLM-5.4，其余用 5.3 或 Flash。
6. **基线与范围。** 以 light 为基线，五个负载（AgentX 两版各算一个）。
7. **动作空间。** 第四节的允许与禁止清单是初版。

## 十三、未验证的事项

- 工作区级子代理定义（`.zcode/agents/*.md`）是否被本客户端读取。
- 定时自动化运行时是否会弹权限确认。
- 无人长跑下的真实 token 消耗。
- 无争用参考是粗估。
- 目标能否达成。540 上定向的 a_cap1 闭合了约 52% 的 TTFT 差距和 36% 的完成时间差距（单轮）；通用策略能闭合多少，没有数据。

## 十四、审核通过后的落地步骤

1. 实现骨架：编排器、候选运行器、冻结评价器、门禁、角色定义、章程，配单测。
2. 第 0 代：基线复测、余量精算，把门槛数值给用户确认。
3. 干跑：用一个已知答案的候选走完一代，并演练中断恢复、漂移、额度报错。
4. 用户确认后开启心跳，进入无人值守。
