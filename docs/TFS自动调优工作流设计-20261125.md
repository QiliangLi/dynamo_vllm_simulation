## 实现状态（2026-11-25）

代码在 `scripts/tuning/`，分支 `lql_1125_tuning`。工作区在仓库之外：`D:\Coding\tfs-tuning`。看板是其中的 `dashboard\index.html`，三个双击脚本是 `暂停.cmd`、`继续.cmd`、`停止并收尾.cmd`。守护进程通过自己的工作树 `D:\Coding\tfs-tuning\repo` 提交，不动用户的主检出。

已实现并验证：

- **WSL 候选运行器。** 逐步复刻 `run_4w25.sh`。默认策略与普通 TFS 的结果落在入口已有结果的波动范围内。每轮核对仿真环境与冻结基线的差异恰好等于候选的覆盖层。
- **诊断与压力负载。** 逐轮诊断摘要（三种口径的超载时间、饱和时间、读取拉伸、实例空转、等读时间、分类 TTFT、时间线），由冻结输入派生的 12 个压力负载。
- **守护进程。** 状态在磁盘，崩溃后由守护脚本重启，登录自启。发现并解决了一个长跑特有的问题：WSL 在没有会话挂着一会儿后会自动停掉整个发行版，把正在跑的回放一起杀掉；守护进程现在持有一个常驻 WSL 会话，并在运行器消失时立即记失败、补跑。
- **角色与权限。** 每个任务临时生成 agent 定义，写权限限于任务的输出路径，命令先全部拒绝再放行任务所需；任务结束后还原越界改动。自检确认运行 git、调用 WSL、往受保护目录写文件都被拒绝。
- **搜索流程。** 一代的全部步骤、静态门禁、冻结评价器、冠军更替、留一法、停滞升级、机制地图、元策略师修改单与回滚、工具匠。
- **测试。** 27 个单元测试，不需要 WSL 和模型。其中三个用假模型和假回放走完整代流程（好候选被立为冠军、坏候选被否决；全部提案失败；工具跑通与跑不通）。

与设计的出入，或尚未验证的：

- **第二梯队第 3 档（路由评分的 Rust 侧）没有打通。** 运行器不会重新编译 Dynamo。改到 `.rs` 的候选在静态门处被明确拒绝。范围清单里它是放开的，但要等运行器支持重编译才能真正搜索到。
- **快速代理模型及其保真门没有实现。** 工具匠目前只造只读的分析脚本。
- **敏感性分析没有实现**（第九节「参数登记」里说冠军附敏感性分析）。
- **流程自改进的范围比第十二节窄。** 能改的是经验教训、假设库、重点提示、预算分配和分析工具；角色提示词的正文、筛选轮数与早停规则没有做成可修改的。
- **候选代码在 WSL 里以 root 运行**，与入口本身一致，没有另建非 root 用户。约束来自静态门禁禁用的 API、agent 的权限和工作区还原。只读角色可以运行经过编排器验证的分析脚本，脚本本身能执行任意代码，这是一个已知的残余风险。
- **真实的 LLM 环节在启动时只经过假模型测试。** 第 1 代及以后的实际表现要看看板和账本。

## 一、设计依据

以下三个事实决定了流程的形态。本文按「代码事实」「性能观察」「待验证」区分各类陈述。

### 事实 1：余量在负载之间差别很大（性能观察，粗估）

用已有的默认策略（light）轮次估了一个「无争用参考」：每条请求按独占链路的参考服务时间执行，worker 归属和到达顺序沿用 light 轮，每个 worker 按 FCFS。它是乐观的粗略参考，不是紧界。

| 负载 | 默认策略 平均 TTFT | 无争用参考 | 默认策略 完成时间 | 无争用参考 |
|---|---|---|---|---|
| 408 | 2.08 s | 0.79 s（−62%） | 11.9 s | 9.7 s（−19%） |
| 540 | 4.91 s | 1.86 s（−62%） | 18.8 s | 14.3 s（−24%） |
| mooncake | 1.97 s | 0.85 s（−57%） | 16.6 s | 13.6 s（−18%） |
| AgentX 窄 | 17.35 s | 14.31 s（−18%） | 48.0 s | 42.9 s（−11%） |
| AgentX 宽 | 19.17 s | 16.50 s（−14%） | 52.5 s | 47.1 s（−10%） |

默认策略列：408、540、mooncake、AgentX 宽为 5 轮均值，AgentX 窄为 1 轮。无争用参考各取 1 轮 light 计算。

AgentX 两版余量小，因为它们基本是计算受限：模型计算总量分别为 157 s 和 176 s，分到 4 个 worker。准入策略改变不了计算量。

这个参考假设不重排队、不换实例。范围包含排序和路由之后，它不再是上限，只是「争用全部消失」的效果。

### 事实 2：链路是保活的（代码事实）

`dynamo_vllm_cpu_sim/sim/storage.py` 的分配规则是带需求上限的最大最小公平（`waterfill`），有未读数据链路就不空转。所以策略减少不了总读取量，只能减少争用造成的停顿、改变谁先读、把负载摆到更合适的位置。

链路时间（读取量 ÷ 25 GB/s）：408 为 8.2 s，540 为 9.3 s，mooncake 为 11.6 s，AgentX 两版为 28–29 s。

### 事实 3：现有 TFS 离目标很远，方向也不一致（性能观察，5 轮均值）

相对默认策略，普通 TFS 的结果：

| 负载 | 平均 TTFT | 完成时间 |
|---|---|---|
| 408 | −13.7% | +1.6% |
| 540 | −8.0% | −0.5% |
| mooncake | +4.7% | +4.2% |
| AgentX（各 1 轮） | 约 ±1% | 约 ±1.5% |

代码上的缺口：

- 判满只数许可条数，不看带宽：`dynamo_vllm_cpu_sim/sim/stack/read_admission.py` 的 `FrozenClassification.acquire`，条件是 `held >= cap`。轻读请求不申请许可，所以不记账。
- θ 同时当分类线和额度分母：`dynamo_vllm_cpu_sim/sim/admission.py` 的 `AdmissionController.on_arrivals`，`cap = max(1, floor(B / θ))`。
- 执行器不向账本上报加载开始和结束，加载事实只用于离线审计；许可到首 token 才释放。见[实验分支使用说明](实验分支使用说明.md)。

同机重复运行的波动是：短请求负载的平均 TTFT 半宽约 ±2.5–6%。所以任何结论都必须多轮才能下。

## 二、目标、范围与停止条件

### 目标

在 TFS 范畴内找一个通用策略。相对默认策略（light），五个负载的平均 TTFT 和完成时间都要改善，任何一项都不回退。幅度越大越好，不预设上限。

「通用」的含义见第九节：一套参数跑全部负载，不依赖负载身份，能推广到没见过的负载。

### 范围

把「TFS 范畴」理解为：决定一条请求何时读 KV、在哪个实例读、以什么顺序读的全部控制逻辑。用户已确认这个划分。

核心范围，一开始就开放：

- 请求画像与分类：需求怎么估，重读和轻读怎么分，提示怎么下发给执行端。
- 额度与账本：许可的数量和计量单位（条数、字节、带宽），判满条件，过期与回收。
- 调度前闸门：放行、扣住、跳过，以及在等待队列里选哪一条。
- 释放与反馈：何时释放额度，账本在决策时刻能看到哪些执行事实。
- 路由与实例选择：等待重读的计分方式、α、请求分到哪个实例。
- 入口侧分诊、空闲放行、老化、租约式控制。
- 以上部分用到的配置项。

第二梯队范围，搜索停滞时按顺序逐步放开，放开后保持可用：

1. 逐层预取深度（现为提前一层）。
2. 等待队列的基础排序（现为 FCFS）。
3. 路由评分的 Rust 侧。改它要重新编译，增量约 3 分钟。每个改到 Rust 的候选使用独立的构建目录。

冠军报告必须写明用到了第二梯队的哪一处。

不纳入（它们是被仿真的对象，或实验的裁判）：

- 存储带宽模型与分配规则。
- 计算耗时模型。
- benchmark 输入与到达时刻。
- 客户端、校验脚本、汇总脚本。
- vLLM 与 Dynamo 的内核实现，只通过现有钩子接入。

第二梯队全部放开后仍然达不到的差距，流程在看板上如实标注，并继续运行。

### 停止条件

- **唯一的正常停止方式是用户叫停。** 时长和运行轮数都不设上限。
- **系统永远不会自己停。** 「没想法了」「够好了」「达到某个水平」都不是停止条件。
- **安全停止**是例外，出现时挂起并写 `NEEDS_HUMAN.md`，处理后从断点继续：冻结区校验失败；漂移重测后仍在；连续 10 轮运行失败；磁盘不足；网关长时间不可用。

### 关于上限

不需要事先设定。第 0 代给出两组参考，显示在看板上：

- 理论下界。完成时间不低于「总计算量 ÷ 4」「总读取量 ÷ 25 GB/s」「到达窗口」三者的最大值。相对默认策略，这个乐观下界约为：408 −24%，540 −29%，mooncake −27%，AgentX 两版 −16% 到 −18%。
- 经验上限。用离线的「事后诸葛」搜索（允许预知未来）找最好的排法，作为现实可达范围的估计。

平均 TTFT 取决于排序，没有简单的下界。

## 三、总体结构

```
第 3 层  流程自改进（每代一次，元策略师）
         可改：假设库、提示词、工具、搜索分配、筛选轮数。下一代生效，可回滚。
   │
   ▼
第 2 层  机制搜索（每代一轮）
   诊断 → 两组提案 → 红队盲审与答辩 → 实现与静态门
       → 运行筛选 → 运行确认 → 独立复核 → 裁决 → 记账 → 复盘
   │  机制确定后
   ▼
第 1 层  参数搜索（程序执行，不用 LLM）
   │
   ▼
冻结区   评价代码、指标定义、规则、范围清单、基线定义、账本
```

设计原则：

- 硬规则交给程序。跑什么、怎么算分、谁通过，都由冻结的代码决定。
- Agent 只做需要判断的事：读数据、想机制、挑毛病、复盘。
- 所有结论以真实栈上的多轮运行为准。辩论只用来省运行预算，不用来定输赢。

## 四、运行载体

```
Windows                                WSL Ubuntu-24.04
┌────────────────────────────────┐     ┌──────────────────────────────┐
│ 编排器（独立守护进程）            │     │ 候选 harness（每轮新建）       │
│   状态机 · 运行队列 · 评价 · 账本  │ ──> │ 仿真栈（脱离会话运行）         │
│                                │ <── │ summary.json 和诊断摘要       │
│ LLM 角色（opencode 无界面调用）   │     └──────────────────────────────┘
│   提案 · 红队 · 评审 · 复盘       │
│ 看板（静态 HTML）                │
└────────────────────────────────┘
仓库：只在冠军更替和每代结束时提交
```

- **编排器**是独立进程，不依赖任何聊天会话。状态在磁盘、每步幂等。由计划任务在登录时启动，崩溃后自动重启，从断点继续。
- **LLM 角色经 `opencode run` 调用**，不用聊天会话派发。角色定义在工作区的 `.opencode/agents/<角色>.md`，写明模型、权限和提示。
- **仿真在 WSL 运行**，由编排器逐轮拉起。Agent 不直接启动仿真，只能通过编排器的辅助命令申请单测和冒烟。
- 已验证的事实（2026-11-25）：本机 opencode v2.4.1 支持无界面调用；`kimi/zhipu/glm-5.4` 和 `kimi/glm-5.3-flash` 都能调用；在 `--auto` 下能写文件、执行命令；JSON 输出带会话号和每步的 token 用量。本机的睡眠和休眠超时都是「从不」。
- 备用方案：如果 opencode 的长任务不稳定，角色可以退回由 ZCode 子代理承担。

## 五、角色与模型

| 角色 | 模型 | 职责 | 产物 | 约束 |
|---|---|---|---|---|
| 编排器 | 程序 | 状态机、运行队列、算分、裁决、记账 | 状态文件、账本、看板 | 只执行冻结规则 |
| 诊断分析师 | GLM-5.3 | 读摘要，定位每个负载的时间去向 | 瓶颈卡 | 只读结果 |
| 提案组 A、B | GLM-5.4 | 各出候选并实现 | 候选卡、覆盖层、单测 | 两个独立会话，视角不同，互不知晓；只能动范围内文件 |
| 红队 | GLM-5.4 | 找针对性常数、标签依赖、饿死和死锁；设计攻击负载 | 攻击清单、攻击负载 | 独立会话；先盲审代码再看理由；每代更换视角；攻击须在真实栈上证实 |
| 举证者 | GLM-5.4 | 专职找出没试过的方向 | 未试方向清单 | 独立会话 |
| 理论评审 | GLM-5.4 | 盲评是否通用、因果链是否成立 | 解释质量分 | 独立会话；看不到提案组身份 |
| 元策略师 | GLM-5.4 | 复盘一代，出流程修改单 | 修改单 | 独立会话，跨代延续；不能碰冻结区 |
| 工具匠（按需） | GLM-5.4 | 造分析脚本、快速代理模型、并行运行 | 工具、验证报告 | 工具过保真门才能启用 |
| 复核审计 | GLM-5.3 | 从原始运行目录独立重算两个指标 | 审计结论 | 只拿原始目录 |
| 摘要与报表 | GLM-5.3-Flash | 整理摘要和一代小结 | 文档 | 不参与判断 |
| 交叉验证员 | kimi-k3.1-pro | 在关键环节给独立意见 | 复核意见 | 只在这些环节出场；每代不超过 5 次；意见不直接裁决 |

主力全部是 GLM 系列，token 不设上限。

交叉验证员只在四个环节出场：

1. 红队给出「零发现」时，复核一次有没有漏。
2. 冠军更替前，对「是否通用、因果链是否成立」给独立意见。
3. GLM 的两个角色僵持不下，或提案与已有经验相矛盾时，做第三方评议。
4. 系统认为搜索枯竭时，复核未试方向清单。

交叉验证意见不直接决定结果，只决定是否追加运行验证。其他非 GLM 家族默认不用。kimi-k3.1-pro 不可用时，交叉验证环节跳过，并在看板上标注。

主力是同一个模型，所以对抗性靠隔离：盲审、独立会话、匿名候选卡、视角轮换、攻击须在真实栈上证实。关键环节再加交叉验证。

## 六、一代怎么走

1. **诊断。** 程序先从运行产物生成摘要：超载秒数、worker 空转秒数、逐类 TTFT、许可时间线。分析师据此给每个负载出一张瓶颈卡。
2. **提案。** 两组各出 1–2 张候选卡。必填：触发信号、动作、参数清单、尺度不变声明、因果链、预测的数据特征、失效模式和保护。
3. **红队盲审与答辩。** 最多两轮。确认存在针对性或作弊路径的候选直接淘汰，其余带着风险标记进入运行验证。
4. **实现与静态门。** 范围清单、通用性检查、相关单测、一次冒烟。不过退回一次，再不过淘汰。
5. **运行筛选。** 5 个负载各 2 轮。两个指标方向都对才进入确认。
6. **运行确认。** 补到 5 轮。与冠军差距小于噪声时自动加轮，最多 15 轮。
7. **复核。** 审计独立重算；编排器运行红队给出的攻击负载；核对预测的数据特征。
8. **裁决。** 程序按冻结规则打分，理论评审给解释分。冠军更替前，交叉验证员给独立意见。
9. **记账。** 所有候选（含淘汰的）追加进账本，标明淘汰原因；更新看板和一代小结。
10. **复盘。** 元策略师出流程修改单；举证者交出未试方向清单。

当前分支的四实例入口只有 light、tfs、a_cap1 三个固定臂，没有参数入口，所以另建候选运行器。候选以「覆盖层」的形式存在：在入口生成的独立 harness 上替换范围内的文件，并覆盖相关配置项。

## 七、候选的版本、回滚与并行验证

### 回滚

策略不是原地改代码，而是版本化的覆盖层。回滚因此是零成本的：

- 每个候选是一个目录（文件、参数、候选卡），带内容哈希，写后不再修改。
- 每轮运行都从同一份冻结基线新建一份 harness，再叠加指定候选的覆盖层。运行目录是一次性的。
- 切换策略就是换一个候选编号，没有任何东西需要撤销。
- 任一历史结果都能按「基线提交 + 候选编号 + 哈希」原样重跑。
- 冠军更替时仓库提交一次并打标签。撤销冠军就是回到上一个标签。
- 流程自身的修改（提示词、假设库、工具、预算分配）按代做快照。回滚就是恢复某一代的快照。
- 被淘汰的候选保留在账本里。失败原因可修的，可以被复活。

### 并行验证

分两层：

- **设计层本来就是并行的。** 多个候选的提案、实现、红队审查同时进行。
- **运行层默认串行。** 仿真栈的端口是写死的（28765、28766、29111–29114），同一时间只能跑一个栈。第 0 代做一个实验：把端口做成可偏移，在同一台机器上以并行度 1、2、3 各跑几轮默认策略，比较均值和方差。
  - 并行度 N 下噪声不变，则筛选阶段用 N 路并行。
  - 确认阶段和最终报告始终串行、零端口偏移，与已发布数字同口径。
  - 改变并行度时，基线在同一机制下重测。
  - 同时核对内存余量和 inotify 余量。WSL 有 28 核、23 GB 内存；inotify 实例基线已被系统进程占用 53/128。

候选与基线、候选与冠军的对比按交替方式安排（A、B、A、B），抵消慢漂移。

## 八、搜索不停：停滞处置与发散保证

「优化一点就停」有两个来源：运行本身中断，和搜索过早收敛。分别处理。

### 运行不断

见第四节。编排器独立于聊天会话，崩溃后由计划任务拉起。LLM 调用和仿真运行都有超时、重试和退避。每代结束自动提交一次账本摘要，进度不丢。

### 停止与停滞分开

- 唯一的正常停止方式是用户叫停（第二节）。
- 找到改进、达到某个水平、若干代没有进展，都不触发停止。

### 改进叠加

新候选默认在现任冠军之上继续改，而不是每次从零开始。每个候选记录父候选，形成一条只进不退的谱系。

### 探索保底

至少 40% 的运行预算永远留给新机制。当前冠军还能靠调参取得改进时，也不挤占这部分。

### 停滞升级

连续若干代冠军没有更替时，按阶梯扩大搜索，而不是退出：

1. 放开当前机制的全部参数。
2. 组合已验证有效的机制。
3. 在核心范围内换环节：分类、路由、释放、排队、反馈。
4. 放开第二梯队范围，按第二节的顺序：逐层预取深度、等待队列的基础排序、路由评分的 Rust 侧。
5. 引入外部思路：检索文献，借鉴其他领域的流控和调度。
6. 复活曾被淘汰、失败原因可修的候选。
7. 提高测量精度，让更小的收益能被看见。

阶梯走完之后也不停：按机制地图系统扫格，对冠军做高精度扫参，定期重访文献。

### 机制地图

把机制空间摆成格子：信号（条数、字节、需求合计、实测吞吐、观测到的拉伸、等待时间）× 动作（放行、扣住、释放、排序、路由）× 时机（到达、调度、逐层、结束）× 反馈（开环、闭环）。每试过一格就标记。看板直接显示还有多少格没碰过。未试的格子多于阈值时，「优化不动了」这个说法不成立。

### 举证者与枯竭档案

举证者每代交出未试方向清单。当它连续若干轮提不出新的可信方向、机制地图上也没有未试的格子时，系统生成枯竭档案，请交叉验证员复核，并显示在看板上。档案包括：每个机制家族的状态（已试并附结果、被数据和论证否定、在范围内不可行），以及每个参数已扫的范围。

枯竭档案只是信息，不触发停止。

### 发散的来源

- 提案视角每代轮换：排队论、控制论、调度理论、网络流控、运筹、定价与拍卖、在线学习。
- 两个提案组互不知晓，盲评。
- 定期从文献引入思路，次数有上限。
- 失败必须带原因记账，指明下一步该改哪里。
- 上限探针：给策略一个现实中拿不到的理想信号，看能提升多少。提升大，就去找这个信号的可估计代理。探针只用于指引方向，不作候选。
- 两条独立谱系，加交叉组合。

### 单次任务不浅尝辄止

- 每个角色任务有完成标准，产出不达标就退回重做。
- 红队给出「零发现」的审查，由交叉验证员复核一次才被接受。

## 九、「通用方案」怎么被强制

- **G1 一套参数跑全部负载。** 候选代码不得读取负载名、类标签、请求 ID、trace 内容、文件路径、环境变量。
- **G2 尺度不变。** 链路带宽和所有需求同乘一个系数，决策不变。用属性测试检查。
- **参数登记。** 不限制参数个数。每个参数要有名称、单位或标明无量纲、取值范围、含义。冠军附敏感性分析，说明哪些参数起作用。过拟合与否由下面的留出数据检验，不靠数参数。
- **G4 留出验证。** 压力负载由冻结 trace 派生，只放沙箱，不进 `benchmark/`：
  - 带宽 10 和 50 GB/s；
  - 到达密度减半和加倍；
  - 需求分布：双峰、连续、全重、全轻、多零读；
  - 实例数 2 和 8。

  冠军在压力套上不得有超出噪声的回退。另做留一法：去掉任一负载重新排序，冠军仍须进前三。
- **G5 解释。** 预测的数据特征没出现，就标为「未解释收益」，不能当冠军。

## 十、评价协议（冻结）

- **基线。** 默认策略 light，同一提交、同一入口步骤、同一并行机制。普通 TFS 另测，作参考。
- **指标。** 平均 TTFT 和完成时间，沿用 `scripts/four_worker/summary.py` 的定义。其余只作诊断，不计分。
- **排序分。** 每个负载的改进分 = 两个指标相对基线的改进百分比各占一半。总分 = 各负载改进分的均值与最小值各占一半，防止靠单个负载拉分。
- **轮数。** 筛选 5 个负载各 2 轮；确认补到 5 轮；冠军更替看 5 轮对 5 轮以上；最终报告用冠军与基线各 10 轮、交替进行的新数据。
- **统计。** 单侧 95% 置信，方差取自基线历史。
- **并行机制。** 筛选可用 N 路并行（N 由第 0 代确定，默认 1）；确认和最终报告串行。
- **漂移控制。** 每 10 轮插 1 轮 light 对照。对照偏离历史带 3 个标准差，就重测基线，窗口内结果作废重跑。

## 十一、防作弊

- 评价代码、规则、范围清单做 SHA256 固定，编排器每次开工先校验。
- 范围清单外的文件一律拒绝运行，运行后对 harness 做全量 diff。
- 每轮必须通过入口原有断言，且请求数、读取字节、模型计算总量与基线逐值相等。
- 审计的重算结果与评价器相差超过 0.5% 就查。
- 账本只追加，失败轮和被否决的候选都留档。
- 中间结果不进仓库，只在冠军更替和每代结束时提交。
- Agent 的权限写死在角色定义里：评审类角色禁止编辑文件；所有角色禁止 `git` 写操作；提案角色只能写自己的候选目录。

## 十二、RSI 层

- **可改**：假设库及优先级、提案与红队提示词、工具、探索与利用的预算分配、筛选轮数与早停规则。
- **不可改**：冻结区，即评价代码、指标定义、规则、范围清单、基线定义。
- **生效方式**：每项修改记录原因和预期收益，下一代生效，比较「每百轮的确认收益」，连续两代下降自动回滚。每代修改不超过 3 项。
- **代理模型门。** 快速代理模型只用于筛选。它须在至少 12 个已知配置上与真实栈方向一致率不低于 80%、秩相关不低于 0.6。验收只认真实栈。
- **边界。** 模型权重不会变。递归效果体现在账本、经验、工具和搜索策略逐代累积。

## 十四、资源与产出

- **运行时长。** 不设上限，直到用户叫停。电脑需要保持开机。本机的睡眠和休眠超时均为「从不」（2026-11-25 核对）。
- **机器占用。** 单轮 1–2.5 分钟。一个候选筛完约 15–20 分钟，确认再加约 25 分钟；并行 N 路时筛选约为原来的 N 分之一。每轮占用 WSL 的若干进程，具体占用在第 0 代实测并显示在看板上。
- **token。** GLM 系列不设上限，仍记录用量，并观察网关的限速。非 GLM 模型只有交叉验证员，每代不超过 5 次。网关不上报费用，只能按 token 计。
- **产出。**
  - 冠军策略，合入为 `scripts/run_4w25.sh` 的新臂，带标签；
  - 设计与证据文档，写明用到了第二梯队的哪一处；
  - 最终 10 轮确认数据和压力套结果；
  - 全部候选账本、枯竭档案和经验清单；
  - 每代的看板快照。

## 十五、lql_dev 上可参考的内容

以下来自对 `lql_dev` 的只读调研。

- **在读带宽合计已有实现，但只在 lease 臂。** 位置是 `dynamo_vllm_cpu_sim/sim/stack/lease_ledger.py`：`sum_after = heavy_sum + 候选 share_Bps + light_rate_Bps`，轻读速率由存储侧流量推算。三个 lease 文件（`lease_admission.py`、`lease_ledger.py`、`lease_events.py`）只在 `lql_dev`，可以移植到四实例的调度前准入。
- **overdraft 和 cap_policy 不在当前分支。** 它们在 `lql_dev` 的 `dynamo_vllm_cpu_sim/sim/admission.py` 和 `dynamo_vllm_cpu_sim/sim/stack/read_admission.py`，入口是 `BENCH_TFS_JSON` 和 `--tfs-json`。定量结论多为单轮。
- **可当红队先验攻击库的反例。**
  - measured 策略在 cap=1 时自锁：串行下按实际占用算出的中位数，得到的 cap 仍是 1。
  - 放宽 cap 在巨需求负载上有害。
  - 固定 cap=1 让 408 的完成时间从约 12.2 s 变到 20.5 s。
  - lease 释放改回首 token 后更差。

## 十六、已确认的事项

2026-11-25 用户确认：

| 事项 | 决定 |
|---|---|
| 目标 | 整个 TFS 范畴内优化，两个指标越多越好，不设门槛 |
| 范围 | 核心范围如第二节；三个灰色地带都算，停滞时按顺序逐步放开 |

| 工作分支 | 从 `lql_1125_opt` 新建 `lql_1125_tuning`（默认，未提异议） |

## 十七、未验证的事项

- opencode 长任务（上百次工具调用）在无界面模式下的稳定性，以及多个 `opencode run` 并发时的表现。
- 网关的限速，以及 GLM-5.4 经网关调用时推理强度档位怎么指定。
- kimi-k3.1-pro 另两条路由的可用性和速度。
- Agent 在 Windows 上经 `wsl.exe` 跑单测和冒烟是否顺畅。
- 并行运行对噪声的影响，以及内存和 inotify 余量。
- 改到 Rust 的候选使用独立构建目录的做法和耗时。
- 无争用参考是粗估；经验上限尚未计算。
- 备用方案里，工作区级子代理定义是否被 ZCode 读取。
