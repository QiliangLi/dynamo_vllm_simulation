# 额度 RPC：最终答复与后台收尾（2026-10-29）

## 行为变化

普通额度申请仍是同步决策。中央完成本次内存账本操作及相关路由评分更新后，返回带 `rpc_final=true` 的最终答复。客户端校验协议、调用标识、实例、账本 epoch 和结果后，立即交回 Scheduler。客户端不再为了等待响应流结束而继续阻塞 Scheduler。

传输仍使用固定版本 Dynamo Runtime 的 `direct()`、TCP 和 MessagePack。没有改 Dynamo/vLLM 上游源码、推理请求 RPC、计分公式、KV 读取或首 token 释放规则。这里只修改仿真适配层的额度控制协议。

```text
Scheduler / outbox 同步路径：
  发出申请 → 中央完成操作 → 收到最终答复 → 校验 → 返回结果、处理下一条

同一客户端事件循环中的后台任务：
  最终答复之后 → 继续读取流 → 确认没有额外响应 → 结束并释放流引用
```

每个 EngineCore 仍只有常驻的通信线程和事件循环。每次响应流收尾使用异步任务，不新增线程。outbox 仍按最终答复确认的顺序提交操作。下一次申请、强制通知或回滚可以在上一条流尚未结束时执行。

## 完成语义

协议升级为 `dynamo-admission-v2`。每次调用携带唯一 `call_id`，中央答复回显 `rpc_call_id`，并带 `rpc_final`、`rpc_protocol`、实例和 epoch。`rpc_final` 表示本次应用操作已经完成，不表示响应流已经关闭，也不提供持久化或故障切换保证。

客户端启动握手仍严格检查完整的单响应流。业务调用采用“最终答复先返回，响应流后台检查”。旧协议不会静默回退；历史实验继续使用原冻结包。

## 后台任务的边界

- 每个客户端最多保留 64 个待结束响应流。达到上限时，在发送下一条操作前失败，不无限积压，也不把流结束等待悄悄移入 outbox。
- 每个后台收尾有独立的壁钟超时。超时长度沿用 `admission.rpc_timeout_wall_s`，从最终答复之后开始计算。
- 流结束之外的额外响应、传输错误和收尾超时都会记录为故障。下一轮 Scheduler、下一次控制调用和最终验收都检查故障。
- 最终答复已确认的操作不会因为后续流故障而自动重放或撤销。普通额度仍按既有首 token 事件释放。回滚仍需明确调用。
- 最终答复之前超时仍属于不确定结果。客户端失败关闭，不改投账本，不自动重试。

## 验收与观测

`run_tfs_stack.py` 为本轮设置独立的 `SIM_STACK_ADMISSION_STATUS_DIR`。每个客户端只在初始化时登记 PID。回放排空后，runner 向这些 EngineCore 发送 `SIGUSR2`，要求等待后台收尾并写出状态。该信号是本机验收接口，不是分布式调度协议；环境未设置该目录时不安装信号处理器。

`admission_rpc.check.json` 检查应有的每个 worker 均交回结果，最终响应数等于已排空流数，待结束流与错误数均为零。缺少客户端、状态未返回或后台失败都不能通过验收。热路径不逐次写状态文件。已有 fine_trace 开启时，缓冲记录 `admission_rpc` 的最终答复、流结束及故障事件。

测试使用真实 Dynamo 独立服务进程，故意扣留流尾。测试确认同一 outbox 的四个额度操作可以在四条流仍打开时依次完成。随后测试额外响应、缺失 EOF、错误身份、额度重放与显式回滚。精确运行结果及限制见包内 [VALIDATION.md](../dynamo_vllm_cpu_sim/VALIDATION.md)。
