## 0. 一句话结论

MPC 假设的架构把"控制量、观测、预测模型、反馈节拍"四要素全部放在调度器手里；实际架构把这四要素拆散进了两个自治组件（直通路由立即单发、引擎自治组批、路由侧只有记账投影）。**本方案的设计硬约束是：MPC 算法最终要在线运行**——因此预测模型必须是控制周期内可计算的轻量模型（09-13 §10.5 的事件重放器，正是研究文档原设计），观测只能走可新建的事件流通道（StepBatch，20261010 §4.2），控制只能经 admission 接口生效（upstream `SchedulerQueue` 升级为主动扣留/指令放行），决策必须在墙钟预算内完成并计入生效延迟（09-17 §11.8 的原始条款）。**本仓库的真实代码仿真不是 MPC 的运行形态，而是它的开发与校准环境**：在仿真里人为施加在线约束（受限观测面/决策预算/动作延迟），用真实代码轨迹做 ground truth 校准轻量模型的预测误差，并用"深拷贝影子世界"作离线 Oracle 上界（`scripts/verify_rollout_copy.py` 已验证其可行性，18.45ms/拷贝）——它量化"轻量近似损失了多少增益"，但**不是在线方案**。部署时的迁移只换观测与控制的通道实现，算法内核不变。

## 1. MPC 需要什么：四要素框架

本文用四个要素组织对照，先把 MPC 在本研究中的含义固定下来。09-13 §11.1 与 09-17 §11.8 的在线算法是同一形态，且**研究文档对它的设计本来就是在线形态的**：墙钟预算（起点 1ms，扫描 0.1–5ms）、"成本计入真实时间，控制器不能暂停其他已经运行的计算与 I/O"、观测滞后/版本冲突的回退链（§11.9）——这些都是在线条款。轻量预测模型也早已指定：09-13 §10.5 的算法 A（共享事件重放器）就是为在线 rollout 写的抽象模型。

```text
触发（请求到达/批完成/读取完成/定时器到期）
  → 构造观测快照（含己方提交回执补账）
  → 生成候选联合动作（批成员 × 空闲实例 × 立即/延迟启动，含"暂缓"空动作）
  → 对每个候选：在估计状态中重放（rollout）到视窗终点，统一终端代价，算四目标增量
  → 只落实第一个动作；未来计划留待下一轮重算
```

| 要素 | 内容 | 在线意味着什么 |
|---|---|---|
| **E1 控制量** | 批成员 β、目标实例 w、领取/启动时刻 u；σ=(P,w,u)；"暂缓"是显式空动作（09-13 §10.6） | 必须有真实的 admission 接口：能把请求扣在队列里、按指令放行 |
| **E2 状态观测** | 队列、活动批进度、存储队列/服务率（09-17 §11.2 接口表） | 只能用可新建的通道：事件流+记账投影+存储投影，不能进程内直读 |
| **E3 预测模型** | 给定状态与动作推出未来轨迹（09-13 §10.5 重放器） | 必须毫秒级可计算：轻量抽象模型，误差靠校准与纠偏管理 |
| **E4 反馈节拍** | 滚动重算触发与纠偏锚点（09-17 §11.1/§11.9） | 事件流驱动；控制延迟与决策墙钟计入；超时回退基线 |

**判据**：一个 MPC 设计若依赖"冻结被控对象、进程内全量状态、无界计算时间"中的任何一条，它就只存在于离线仿真，不是在线算法。这是 §5 方案设计的硬约束，也是对上一版方案（深拷贝影子世界作主预测模型）的否定理由——该方案三条全占（§5.4）。

## 2. 假设架构：MPC 的设计前提

两份研究文档的系统模型（09-13 §1.1/§5、09-17 §1.1/§5）概括为一句话：**调度侧维护唯一全局等待队列，分批下发给推理实例，实例对收到的一批一起执行**。五条约定：

1. **中央唯一等待队列**：请求到达即入 Q(t)；实例无本地等待队列，完成当前批后原子领取新批（09-13 §5.1）。
2. **调度器占有全部投放决策** σ=(P,w,u)：批成员、目标实例、领取时刻（含有限延迟/暂缓）；多实例联合决策（09-17 §11.7）。
3. **完整 prefill 批**：每实例同一时刻仅一个活动批（含 STALL 期），批成员绑定到最后一层，末层完成后整批一起产出首 token。
4. **存储侧有明确服务纪律**，带宽分配是决策层之一（09-13 FCFS 按需；09-17 B0/B1）。
5. **执行前不读、执行中仅下一层 lookahead**：批的数据依赖由领取时刻唯一决定。

该架构给 MPC 的核心便利是 **E3：实例是哑执行器，系统动力学完全由调度动作决定**——重放器没有隐藏自由度。对照实际架构的差距由此展开。

## 3. 实际架构：当前实验台与真实部署

### 3.1 调度侧：Dynamo 的三种形态

| 形态 | 排队 | 下发原则 | 与本仓库的关系 |
|---|---|---|---|
| (a) 网关 ext-proc | 无（流式转发不缓冲） | 调用选择核心，逐请求 | 20261009 文档描述的真实部署路径 |
| (b) `SelectionService` 直通 | 无 | `select_and_reserve` 逐请求：成本分 = prefill 负载折算 + decode 负载 + 权重×active_requests，取最低（cache-blind 下无缓存重叠项，等分随机平局） | **本仓库仿真使用**（`sim/router.py`，Python in-process） |
| (c) 完整 kv_router 组件的 `SchedulerQueue` | **有（被动）** | `should_queue` = class 开启排队 且（该 class 已有积压 或 所有 eligible worker 的 prefill 记账满）；不排队则立即放行；排队后按 `RouterQueuePolicy`（fcfs/lcfs/wspt）排序，记账释放触发放行 | **本仓库未启用**；Python 配置面已暴露（`router_queue_policy` 等） |

**(c) 是本次分析新核实的结构性发现**（`lib/kv-router/src/scheduling/queue.rs`，`handle_enqueue`/`should_queue` 约 1058–1136 行；`config.rs:454-469`；Python 侧 `kv_router_args.py:212-218`）。三点精确表述：它是**被动排队**（超载才留请求，不能为等批/错峰主动扣留）；放行规则固定（记账空位即放），**不是开放给策略的决策点**；Python in-process `SelectionService` 的接口面（`_core.pyi:736-816`）**没有 enqueue 路径**，当前直通桥接方式接不到它。它与 20261009 文档"路由器看不见引擎内部"的结论不矛盾：排队改变"何时放行"，不改变观测边界。

### 3.2 引擎侧：vLLM V1 逐步重组批

每个推理实例内是真实 vLLM v0.20.2 `Scheduler`（细节见 20261010 文档 §2）：每引擎步两阶段重组合批（RUNNING 分 token → WAITING 准入，批逐步重组）；`max_num_seqs` 是并发上限、`max_num_batched_tokens` 是逐步共享预算；KV 不足触发抢占（清零回队首）；PD 远端 KV 门控（`WAITING_FOR_REMOTE_KV` 等传输放行）；完成语义是逐 token 流。本仓库 `sim/run.py` 把两层真实代码装进虚拟时间事件循环，胶水层看得见引擎内部状态（`events.jsonl`），但这只进产物文件不进路由决策。

## 4. 挑战：四要素逐项对照实际架构

这些挑战按"在线运行"这一最终目标定义，因此**任何"在仿真里绕过它们"的做法（利用仿真特权：冻结时间、进程内全量直读、无界墙钟）都不构成解决，只是推迟暴露**。逐条如下；§5 的方案以在线必需件应对，§5.6 给出总对照。

### C1（E1）控制量缺失：直通路由没有"扣住请求"与"联合决策"的合法动作

1. **无暂缓动作**：MPC 的错峰/等批 = 推迟领取时刻。直通路径上请求到达即单发，调度侧没有地方放一个未来才放行的请求。形态 (c) 的队列能放，但触发是超载被动排队。
2. **无联合决策接口**：Dynamo 的接口模型是 per-request（Filter → Scorer → Picker"Selects one row"，`selector/policy.rs:111-143`），一次调用回答"这个请求去哪"，无法表达"这 3 个请求同刻发往实例 2、实例 1 再等 5ms"。
3. **自定义策略挂载点够不着控制量**：Rust policy 挂载点（Filter/Scorer/Picker）决策粒度是逐请求选 worker，组批/错峰/启动延迟动作在这个接口形状里没有参数位。

### C2（E1/E3）控制语义错位：MPC 的"批"与 vLLM 的"批"是两个概念

投放决策只是引擎状态机的输入，批是两阶段算法的涌现结果：同刻投放的请求可能分步准入（预算不够）、chunk 切开、被 decode 抢预算、被抢占清零。完成语义也不同（整批首 token vs 逐 token 流；decode 阶段本身是假设架构没有的维度）。后果：预测模型必须把 vLLM 调度状态机作为被控动力学来近似——**在线上这是"带纠偏的近似推演"，不是"跑一份真实代码"**。

### C3（E2）状态观测缺失

路由侧只有每 worker 两个聚合记账数（20261009 §3），与真实执行隔着两层不可见差集；20261010 §3.2 的八项缺失观测清单是完整枚举。存储侧 09-17 §11.2 要求的带版本/延迟观测在真实栈不存在。

### C4（E4）反馈节拍缺失：误差开环累积

没有每步事件流，"实际发生了什么"锚点只有输出流边沿；一次偏差通过引擎状态机传播放大而无纠偏通道。E2/E4 缺失时同一份 MPC 代码退化为开环启发式——这是"当前架构对 MPC 不利"判断的技术内核：不利不在搜索算法，而在闭环的两个端点（控制端 C1、反馈端 C3/C4）。

### C5 节拍与控制延迟

引擎毫秒级步进、`async_scheduling` 下步间重叠；MPC 计算期间被控对象前进，预测的"当前状态"到手即过期；控制通道还有传输延迟。**在线预测模型的单轮 rollout 必须显著短于被控对象的特征时间尺度**，且控制延迟要么计入预测、要么作为保守余量。

### C6 多控制器互相稀释

实际架构已有两个活跃控制器：Dynamo 选择核心（逐请求贪心）与 vLLM 调度器（自治组批）。MPC 作为第三个加入，不让权则意图被改写：MPC 想让实例 1 空着等批，直通路由照样把新请求发给记账最轻的实例 1。必须显式设计让权边界（§5.5）。

### C7 存储侧控制量缺失

09-17 的 B 层在真实栈无挂载点；PD 传输发起由引擎 connector 决定。第一版在线 MPC 把存储固化为规则环境。

### C8 研究对象本身的合法性：语义模型必须拍板

检视报告 §5.3：09-13/09-17 的形式化结论（四目标、复杂度、候选批目录、E26–E31）定义在假设架构的动作空间上；换到实际架构，动作空间/状态空间/完成语义全变。在线方案的应对是双口径并存（§5.7）。

## 5. 在线 MPC 的架构与仿真的角色

### 5.0 设计硬约束（对上一版方案的修正声明）

最终交付物是**在线运行**的调度算法。由此得到四条硬约束，任何不满足的设计只在离线仿真里成立：

1. **预测模型在线可计算**：单候选 rollout 必须远低于控制周期（毫秒级）。深拷贝整个世界（实测 18.45ms/拷贝，还需 ×候选数）不满足；且它依赖"冻结世界"与"进程内全量状态"，在线都不成立。**深拷贝影子世界的正确用途是离线 Oracle 上界与校准工具（§5.4），不是在线方案。**
2. **观测走可新建通道**：控制器不能假设进程内直读引擎对象；只能消费事件流（StepBatch）+记账投影+存储投影——这些是真实部署能建出来的通道。
3. **控制经 admission 接口生效**：扣住请求/指令放行必须有真实接口（§5.2）；仿真里的投放点只是该接口的模拟器，算法必须对着抽象接口编程。
4. **决策预算与生效延迟计入**：墙钟预算（超时回退基线）、动作生效延迟 δ、观测交付延迟都要进实验模型（E30 式扫描）。

推论：**MPC 的算法内核（候选生成、轻量 rollout、目标函数、回退链）在仿真与在线是同一份代码**；迁移时只替换观测与控制的通道实现。这也正是 09-17 §11.8 原始设计的形态——上一版"在仿真里用深拷贝特权"反而是偏离。

### 5.1 在线 MPC 参考架构

```text
                 请求到达
                    │
        ┌───────────▼───────────┐
        │  队列 / admission 组件 │◄─── 控制指令：放行集合 β、
        │ （SchedulerQueue 升级）│     目标实例 w、放行时刻 s
        └───────────┬───────────┘
                    │ 受控放行（唯一进入引擎的路径）
                    ▼
        ┌───────────────────────┐      StepBatch 事件流（每步批组成/准入/
        │  推理实例 ×m            │ ──► 抢占/完成 + PD finished_recving）
        │  （vLLM V1，自治组批）  │ ──► 记账事件（首 token/完成→记账回调）
        └───────────┬───────────┘ ──► 存储/带宽投影
                    │
        ┌───────────▼──────────────────────────────────┐
        │  在线 MPC 控制器（调度侧，独立于数据面转发路径） │
        │  ① 观测聚合：事件流→状态估计（waiting/running/  │
        │     KV 估计、存储队列估计），边沿锚点纠偏        │
        │  ② 候选生成：(β,w,s) 联合动作 + 空动作          │
        │  ③ 轻量预测模型 rollout（毫秒预算）              │
        │  ④ 滚动优化：四目标之一 + 终端排空代价           │
        │  ⑤ 预算超时/观测过期 → 回退基线策略              │
        └──────────────────────────────────────────────┘
```

四个在线必需件（缺一即回到 §4 的某条挑战）：**admission 接口**（应 C1）、**事件流观测**（应 C3/C4）、**轻量预测模型**（应 C2/C5）、**预算化滚动优化与回退**（应 C4/C5）。

#### 5.1.1 组件关系：控制器到底是什么、和调度器/实例是什么关系

**控制器是一个新写的软件组件**（部署时是调度侧的一个进程或模块；仿真时是 `sim/mpc.py` 里的一个对象，被事件循环调用）。它不替换 Dynamo 也不替换 vLLM，而是坐在两者中间。三个关系各一句话：

| 关系 | 表述 |
|---|---|
| 控制器 ↔ Dynamo 调度器 | 控制器就是新的调度算法本身；Dynamo 退为它脚下的记账员与 worker 目录（记账仍是真实代码、路径不变） |
| 控制器 ↔ 推理实例 | 实例**完全不知道控制器存在**——它看到的只是"请求在某些时刻到达"；控制器影响系统的唯一手段是控制请求到达各实例的时刻、顺序与目标 |
| 控制器 ↔ vLLM 调度器 | vLLM 调度器一行不改、全权保留；它组它的批，控制器预测它、经投放时机影响它 |

一次请求在闭环里的完整生命周期（每行都是具体的组件动作）：

| 时刻 | 组件 | 动作 |
|---|---|---|
| t₀ | 控制器队列 | 请求到达，**扣入队列**（不再直通转发）——C1 的扣留动作在此发生 |
| t₀ | 控制器·观测 | 收"到达"事件；此前一直在收各实例的每步 StepBatch 事件，据此维护每实例状态估计（waiting/running/KV/传输） |
| t₀ | 控制器·决策 | 生成候选投放方案 (β,w,s)（含"再等"）；每个方案在**轻量模拟器**里跑一遍视窗（模拟器模仿 vLLM 组批规则与存储带宽，输出预测完成时间）；按目标选优，**只执行第一个动作** |
| t₀ | Dynamo 记账 | 对放行的请求记账（`create_reservation` 指定 w，或 `select_and_reserve` 由选择核心定 w） |
| t₀+δ | 推理实例 | 收到请求进 waiting，按 vLLM 自己的规则组批执行——投放≠执行，差异由模拟器预测、由事件纠正 |
| 每步 | 推理实例 | 执行一个引擎步，发 StepBatch 事件（本步批组成/准入/抢占/完成；PD 加 finished_recving） |
| 每步 | 控制器 | 用事件**重置**对应实例的状态估计（误差不开环）；若是决策点则滚动重算 |

一个最小示例：队列中有大请求 A（远端 KV 4GB）与小请求 B（0.1GB），实例 0 空闲，B 到达触发决策。控制器试：①A、B 立即同发实例 0；②先发 B、0.5ms 后发 A；③先发 A；④再等。模拟器对每个方案推演——"A、B 同步进实例 0 的 waiting，token 预算不够同时 prefill，B 先准入 A 分步；A、B 的远端 KV 读同刻挤同一批盘按带宽规则分速率；实例 1 的长任务 2ms 后腾出预算"——输出各请求预测首 token 时刻，按平均 TTFT 选②。执行第一步（发 B、设 0.5ms 唤醒）；届时用实例实际上报的每步事件校正模拟器状态，重新决策。之前验证过的深拷贝影子世界在此例中的位置：相当于把"模拟器"换成"复制整个真实系统跑一遍"——更准但在线不可行（§5.0），只作离线上界参照。

### 5.2 在线必需件一：admission 控制接口（应 C1）

真实侧的落点就是 §3.1(c) 发现的 `SchedulerQueue`，需要两处升级：

- 入队条件：`should_queue` 从"class 开启排队 且（有积压 或 prefill 记账满）"改为"**控制器指令**"——控制器认为该扣就扣（为凑批形状、为避开预测的热点窗口、为联合多实例决策）；
- 放行规则：从"记账空位即放"改为"**执行控制器输出的 (β,w,s)**"——同刻把 β 成员放行到同一实例 w，在时刻 s 生效。

改动面在 kv-router 的 admission 决策注入通道（`LocalScheduler`/`SchedulerQueue` 层加控制器回调），upstream 已有 class 队列、RouterQueuePolicy、优先级跳变、逐 worker 记账容量的全部结构。**仿真对应物**：`run.py` 的投放点（`run.py:102-109` 的"到达即投"改造为"到达入 MPC 队列、决策点投放"）就是该接口的同语义模拟器——算法对着抽象接口（`admit(β,w,s)` / `hold()`）编程，部署时把接口实现从胶水层换成 Rust 侧升级件，算法内核不动。C1 的"无联合决策接口"由此消解：联合决策发生在控制器内部，对引擎呈现的只是常规的逐请求到达流（只是到达时刻与顺序受控）。

### 5.3 在线必需件二：StepBatch 事件流观测（应 C3/C4）

20261010 §4.2 的完整设计在此原样采用：引擎每步发布 `{step_seq, scheduled:[{rid,n}], admitted/preempted/finished, waiting/running counts}`，PD 侧并入 `finished_recving`；按 `(engine_id, step_seq)` 全序；通道类比 kv_events 的 ZMQ publisher 先例。过渡方案（档 3）：先解析输出流上的 `RequestStateStats` 时间戳（SCHEDULED/首 token），把状态估计从纯开环升级为边沿纠偏。

**仿真侧的关键纪律**：控制器**不许直读** `scheduler` 对象——仿真胶水层把引擎每步输出转成同一 StepBatch schema 喂给控制器（数据现成：`run.py:81-93` 的 step_complete 事件已含 scheduled/waiting_remote 字段）。这条纪律保证：状态估计代码（从事件流重建 waiting/running/KV 估计）在仿真里开发的就是在线要跑的那份，其误差（事件丢失/延迟/乱序）可以在仿真里注入后量化。

### 5.4 在线必需件三：轻量预测模型（应 C2/C5）——核心组件

**在线预测模型 = 09-13 §10.5 的事件重放器 + vLLM 两阶段调度语义的确定性近似 + 存储速率规则模型。** 它是纯数据结构上的抽象模拟（无真实代码调用），单步推进是 O(队列长度) 的内存操作，毫秒预算内可跑数百步：

| 被控对象 | 轻量近似 | 误差源 | 纠偏锚点（事件流） |
|---|---|---|---|
| vLLM 两阶段调度 | 逐实例维护 waiting/running 估计与 token 预算计数；准入按"预算够则准入、不够分步、KV 满则停"近似；chunk 按 prompt 长度与预算边界近似；抢占不精确预测 | 抢占发生点、精确 chunk 边界、前缀命中 | 每步 `scheduled/admitted/preempted` 事件直接重置估计——推错一步，下一步即被纠正 |
| 请求完成（EOS） | 未知；按声明 `max_tokens` 或已知输出长度（PD/预填场景）预测 | 输出长度偏差 | `finished` 事件；首 token 锚点修正 TTFT |
| PD 远端 KV | 等传输完成：由存储模型预测 | 传输完成时刻 | `finished_recving` 事件 |
| 存储/带宽 | 复用 `sim/storage.py` 已实现的速率规则（active_split/max_min_fair 的速率公式部分，纯函数） | 队列组成估计误差 | 存储投影（snapshot schema）周期对账 |
| 引擎侧到达 | = admission 放行序列（自己已知）+ δ 生效延迟 | δ 抖动 | 下一步 `admitted` 事件 |

这正是 20261010 §3.2 的结论转化为设计：**在线推演缺的不是规则（§2 已完备）而是观测**；有了事件流，"带边沿纠偏的近似推演"从不可行变为可行，且误差不再开环累积（每步事件重置状态估计）。

**深拷贝影子世界的角色（离线 Oracle，非在线方案）**：`scripts/verify_rollout_copy.py` 已验证可行性（拷贝世界相同驱动下与原世界轨迹逐位一致、18.45ms/拷贝）。它的三个正确用途：

1. **Oracle 上界**：同 trace 跑"轻量 MPC vs Oracle MPC（深拷贝 rollout）"，差值 = 轻量近似的代价——若差值小，轻量模型够用；若大，先改进模型再谈部署；
2. **校准器**：用真实代码轨迹（ground truth）逐事件对拍轻量模型，产出预测误差分布（完成时间误差、准入时刻误差），进控制器的保守余量；
3. **回归断言**："零干预 rollout 复现真实轨迹"作为仿真内的常开测试，保证真实代码升级后立即发现语义漂移。

### 5.5 在线必需件四：预算化滚动优化、让权分工与回退（应 C4/C5/C6）

- **决策预算**：沿用 09-17 §11.8（beam=8、深度=3、墙钟起点 1ms，扫描 0.1–5ms）；超时/观测过期/版本冲突回退链：MPC→固定 admission 规则→直通（现状 S0），回退次数入指标。
- **让权分工**：vLLM 调度器不让权——它是被控动力学，MPC 经投放时机影响它、经事件流观测它；Dynamo 选择核心退为记账（MPC 指定 w 后 `create_reservation` 记账，或 w 仍由 `select_and_reserve` 选，两模式做对照实验）；admission 队列为 MPC 独占决策点。三层各司其职，C6 消解。
- **控制延迟**：动作生效延迟 δ 与观测交付延迟进仿真实验模型（E30 档位：0/1/5/20/100ms），线上取实测值。

| C2 批语义错位 | 轻量模型近似 vLLM 语义 + 每步事件纠偏（§5.4） | 用真实代码 ground truth 校准近似误差 |

### 5.7 仿真的三重角色与实验设计（应对 C8 同时定口径）

仿真实验台在这个路线里不是"在线 MPC 的替身"，而是它的**开发场、校准场、验收场**，三重角色对应三类实验：

1. **开发场（施加在线约束）**：控制器在仿真里就按 §5.0 的四条硬约束跑——只吃事件流、只用轻量 rollout、有墙钟预算、有生效延迟。仿真特权（全量直读、深拷贝、冻结时间）只属于 Oracle 对照与校准工具，不进被评测的控制器。
2. **校准场（ground truth 对拍）**：真实代码轨迹 vs 轻量模型预测，产出误差分布报告（§5.4 表的最后一列）；误差超阈值的场景（抢占频繁、命中多变）进保守余量或回退条件。
3. **验收场（三对照）**：同 trace 同到达序——`S0` 直通基线（现状）vs `MPC-online`（在线形态：轻量模型+事件流+预算+延迟）vs `MPC-oracle`（深拷贝 rollout，上界）。两个差值都有含义：`MPC-online − S0` = 可部署的净收益；`MPC-oracle − MPC-online` = 近似+在线约束的代价（若大，说明模型或预算需要加强）。
4. **口径**：A2（真实引擎语义、MPC 只控投放）为主口径——它就是在线形态在仿真里的投影；A1（驯化配置逼近假设架构）按需作对照，E26–E28 矩阵在 A1 口径有效；检视报告 §5.3 的"先二选一"由此放宽为"先 A2、A1 按需"。

### 5.8 已知风险与工程量

1. **轻量模型误差可能吃掉 MPC 增益**：这是本路线最大的科学风险，三对照实验（§5.7-3）就是为量化它设计的；缓解手段是校准余量、事件纠偏、必要时局部使用"受限深拷贝"（只拷单引擎调度器子图，验证过可拷贝）。
2. **事件流丢失/乱序**：需 step 序号水位 + 快照对账重同步（20261010 §4.4 档 2）。
3. **驱动一致性**：轻量模型的推进逻辑与真实调度器语义的对齐靠校准流程维护，真实代码升级后重跑校准。
4. 工程量：轻量重放器（09-13 §10.5 为蓝本）+ 事件流 schema/转出 + admission 接口抽象 + 三对照实验框架 ≈ 2–3 人周；真实部署侧的 Rust admission 升级与事件流导出另计（§6）。

## 6. 真实部署迁移（接口件即 §5 的在线必需件）

迁移不是"另写一套"，而是把 §5 的四个必需件的仿真实现换成生产实现，算法内核（候选生成/轻量 rollout/目标/回退）不变：

| 必需件 | 仿真实现（开发期） | 生产实现（部署期） |
|---|---|---|
| admission | 胶水层投放点（`run.py` 改造） | kv-router `SchedulerQueue` 升级（主动扣留+指令放行）或前置队列组件 |
| 观测 | 胶水层转出 StepBatch schema | vLLM 侧每步事件发布（挂点 `schedule()` 组装 `SchedulerOutput` 后，20261010 §4.2）+ NATS/ZMQ 通道 |
| 记账 | `SelectionService` 直通 + 生命周期回调（现状保留） | `create_reservation`（MPC 指定 w）或 `select_and_reserve`（w 由选择核心定） |
| 预算/延迟 | 虚拟时间下的墙钟预算与 δ 注入 | 实测控制周期定档 |

部署顺序建议：观测流先行（B1，无论哪档控制都需要）→ admission 升级（B2）→ 引擎准入让权（B3，`scheduler_cls` 继承，仅当 A2 口径实验显示投放级增益被引擎自治显著稀释时投入）→ 组批让权（B4，仅当整批语义必须真实成立）。零改造折中（MPC 退化为参数调节器）保留为对照基线。

## 7. 与研究路线的关系

- 检视报告 §5.3 的语义决策（本文 C8）：§5.7-4 的双口径把它从先决项放宽为"先 A2 后按需 A1"。
- 检视报告 §8.3 的 P1 路线（动态 admission → Storage 投影 → Rust scorer）与本文 §5.2/§5.3/§6 对应；本文新增 `SchedulerQueue` 升级这条结构路径（§3.1(c)、§5.2）。
- 20261010 §4 的 StepBatch 事件流在本文中是 MPC 的 E2/E4 必需件；其仿真对应物（§5.3 纪律）先行定型 schema 与定序语义。
- E26–E31 的有效域：E26/E27/E28 定义在假设架构动作空间上，A1 口径有效；A2 口径需要自己的实验矩阵，建议作为 E28 并列子组；E30 的信息误差/鲁棒性扫描与 §5.0-4 的延迟注入合并设计。
- **表述边界**：A1 口径驯化了 vLLM 调度语义；在线形态的评测只允许事件流观测面——所有偏离默认形态的实验在 report.json 的 scope/limitations 显式声明。
