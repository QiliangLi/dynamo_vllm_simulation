## 0. 一句话结论

**MPC 假设的架构把"控制量、状态观测、预测模型、反馈节拍"四要素全部放在调度器手里；真实架构把这四要素拆散并藏进了两个自治组件**——控制量被 Dynamo 直通路由的"逐请求立即单发"吃掉（没有等批/错峰/联合决策的合法动作），观测被 vLLM 引擎的进程边界挡住（只有两个聚合记账数），预测模型面对的是引擎自治组批（两阶段调度、chunk、抢占）而非"收到一批整批执行"，节拍上引擎以毫秒级步进而路由器无事件流。**但差距不是二值的**：本仓库仿真胶水层天然占有四要素（离线推演已验证），upstream kv-router 里还发现了未被本仓库启用的被动排队能力（`SchedulerQueue`，class 队列 + fcfs/lcfs/wspt 策略 + 记账触发放行），它是把 MPC 挂回真实 Dynamo 的最短结构路径。落地建议：仿真内先重建中央队列验证 MPC 收益（两套实验口径），真实部署按"观测流 → admission 让权 → 组批让权"三步递进。

## 1. MPC 需要什么：四要素框架

本文用控制理论的四要素组织对照，先把 MPC 在本研究中的含义固定下来。09-13 §11.1 与 09-17 §11.8 的在线算法是同一形态：

```text
触发（请求到达/批完成/读取完成/定时器到期）
  → 构造观测快照（含己方提交回执补账）
  → 生成候选联合动作（批成员 × 空闲实例 × 立即/延迟启动，含"暂缓"空动作）
  → 对每个候选：在估计状态中重放（rollout）到视窗终点，统一终端代价，算四目标增量
  → 只落实第一个动作；未来计划留待下一轮重算
```

它成立的四要素：

| 要素 | 内容 | 在 09-13/09-17 中的位置 |
|---|---|---|
| **E1 控制量** | 合法动作空间：批成员 β、目标实例 w、领取/启动时刻 u；σ=(P,w,u) | 09-13 §5.1/G2、09-17 §5.1 式(9)；"暂缓领取"是显式的空动作（09-13 §10.6"必须包含所有空闲实例再等一格的空动作"） |
| **E2 状态观测** | 中央队列 Q(t)、各活动批层进度、存储队列/服务率、暂存池 | 09-17 §11.2 接口表（RequestManifest/DiskGroupObservation/ComputeProgress…） |
| **E3 预测模型** | 给定状态与动作，推出未来轨迹与完成时间：共享事件重放器 | 09-13 §10.5 算法 A、09-17 §10.1；预测=重放是 MPC 的内环 |
| **E4 反馈节拍** | 滚动重算的触发事件与纠偏锚点（实际发生了什么） | 09-17 §11.1 时间尺度分层；§11.9 观测过期/版本冲突回退 |

**MPC 与一次式启发式的区别全在 E4：预测错了下一轮会被实际状态纠正。若 E2/E4 缺失，同一个搜索代码就退化为开环启发式，误差无界累积**——这是后文 §4-C3/C4 的判据。

## 2. 假设架构：MPC 的设计前提

两份研究文档的系统模型（09-13 §1.1/§5、09-17 §1.1/§5）可以概括为一句话：**调度侧维护唯一全局等待队列，分批下发给推理实例，实例对收到的一批一起执行**。展开为五条约定：

1. **中央唯一等待队列**：请求到达即入 Q(t)={已到达、尚未被领取}；实例无本地等待队列，完成当前批后原子领取新批（09-13 §5.1）。
2. **调度器占有全部投放决策** σ=(P,w,u)：哪些请求组成批 β、由哪个实例 w 领取、何时领取（含有限延迟/暂缓）。多实例的批选择是**联合决策**（09-17 §11.7"对同时空闲实例做互不重叠的联合选择"）。
3. **完整 prefill 批**：每实例同一时刻仅一个活动批（含等待 KV 的 STALL 期），批成员绑定到最后一层，末层完成后**整批一起产出首 token**（09-13 §1.3、09-17 §1.4）。
4. **存储侧有明确的服务纪律**且带宽分配是决策层之一（09-13 的 FCFS 按需分配；09-17 的 B0 基础份额/B1 组保底+权重+上限）。
5. **执行前不读、执行中仅下一层 lookahead**：批的数据依赖由领取时刻唯一决定，读取时序是投放决策的确定性函数。

这个架构给 MPC 的结构性便利，正是四要素的直读：

| 要素 | 假设架构如何满足 | 关键点 |
|---|---|---|
| E1 控制量 | σ 的三个分量都是调度器变量；"等批/错峰"= u 的延迟动作，天然合法 | **请求在中央队列里，调度器想扣多久扣多久** |
| E2 观测 | Q(t)、层进度、队列状态都在模型内定义了导出观测（09-17 §11.2 白名单） | 状态与观测同构 |
| E3 预测 | 被控对象（实例+存储）无自治决策：给定 σ，式(10)–(11)/G3–G4 唯一确定轨迹 | **重放器=被控对象本身**，预测零模型误差（输入误差除外） |
| E4 节拍 | 领取/完成/读取完成都是调度器可感知的事件 | 闭环 |

**核心便利是 E3：实例是"哑执行器"，系统动力学完全由调度动作决定。** 09-13 §7.2/09-17 §7.1 的全局代价 `Q*_J(X_t,α)` 之所以可近似计算，是因为重放没有隐藏自由度。

## 3. 实际架构：当前实验台与真实部署

### 3.1 调度侧：Dynamo 的三种形态

对"请求是否在调度器上排队、按什么原则下发"这个问题，upstream Dynamo（本仓库 `versions.json` 固定的版本）实际存在三个层次，需分别表述：

| 形态 | 排队 | 下发原则 | 与本仓库的关系 |
|---|---|---|---|
| (a) 网关 ext-proc | 无（流式转发不缓冲） | 调用选择核心，逐请求 | 20261009 文档描述的真实部署路径 |
| (b) `SelectionService` 直通 | 无 | `select_and_reserve` 逐请求：成本分 = prefill 负载折算 + decode 负载 + 权重×active_requests，取最低（cache-blind 下无缓存重叠项，等分随机平局） | **本仓库仿真使用**（`sim/router.py`，Python in-process） |
| (c) 完整 kv_router 组件的 `SchedulerQueue` | **有（被动）** | 请求入队时判定 `should_queue` = class 开启排队 且（该 class 已有积压 或 所有 eligible worker 的 prefill 记账满）；不排队则立即 `admit_one`；排队后按 `RouterQueuePolicy`（fcfs/lcfs/wspt）排序，记账释放事件触发放行 | **本仓库未启用**；Python 配置面已暴露（`router_queue_policy`、`router_queue_threshold` 等） |

**(c) 是本次分析新核实的结构性发现**，代码位置：`lib/kv-router/src/scheduling/queue.rs`（3908 行，`handle_enqueue`/`should_queue` 于约 1058–1136 行）、`local.rs`（`LocalScheduler` 包装）、`config.rs:454`（`RouterQueuePolicy`）、Python 侧 `components/src/dynamo/common/configuration/groups/kv_router_args.py`。三点精确表述：

1. 它是**被动排队**：只有 worker 记账超限/已有积压时才留请求，不能为"等批凑形状"或"错峰"主动扣留一个记账未满的 worker 的请求；
2. 放行规则是固定的记账空位逻辑，**不是开放给策略的决策点**（策略只可选队列排序 fcfs/lcfs/wspt 与 class 配置）；
3. Python in-process `SelectionService` 的接口面（`_core.pyi:736-816`：select/select_and_reserve/create_reservation/prefill_complete/add_output_block/free_reservation）**没有 enqueue 路径**——即本仓库当前的直通桥接方式无法触达该排队能力。

这与 20261009 文档"路由器与推理引擎之间没有查询路径、路由器只有记账投影"的结论不矛盾：排队改变的是"何时放行"，不改变"路由器看不见引擎内部"。

### 3.2 引擎侧：vLLM V1 逐步重组批

每个推理实例内是真实 vLLM v0.20.2 `Scheduler`（细节见 20261010 文档 §2，此处只列对 MPC 要紧的）：

- **每引擎步两阶段重组合批**：先给 RUNNING 逐请求分 token（decode 每请求 1 个、chunked prefill 继续切），再用剩余预算从 WAITING 准入；批是逐步重组的，**不存在"组好贯穿始终的批"**；
- **两个上限是约束不是目标**：`max_num_seqs` 是 RUNNING 并发上限，`max_num_batched_tokens` 是逐步共享预算——同一时刻投放的请求只有在预算够、KV 够、无更早 waiting、无抢占时才会在同一步准入为同批；
- **自治行为**：KV 不足触发抢占（清零重算回队首）、本步抢占则停止准入、PD 远端 KV 门控（`WAITING_FOR_REMOTE_KV` 等传输完成放行）；
- **完成语义**：逐 token 流式产出，请求各自 EOS 离批，**没有"整批一起出首 token"**。

本仓库仿真（`sim/run.py`）把这两层真实代码装进虚拟时间事件循环：请求到达 → `router.route()` 直通选实例 → `scheduler.add_request()` 进该实例引擎 waiting 队列 → 引擎按上述规则自治推进。胶水层能看见引擎内部状态（`events.jsonl` 的 waiting/running/scheduled 字段），但这只进产物文件，不进任何路由决策。

## 4. 挑战：四要素逐项对照实际架构

### C1（E1）控制量缺失：直通路由没有"扣住请求"与"联合决策"的合法动作

这是最根本的挑战，分三层：

1. **无暂缓动作**。MPC 的错峰/等批动作 = "把请求 u 的领取时刻推迟 δ"。直通路径（形态 a/b）上请求到达即单发，`select_and_reserve` 的返回就是终点——调度侧没有地方"放"一个未来才放行的请求。形态 (c) 的队列能放，但触发条件是超载被动排队（§3.1），不是策略主动扣留。
2. **无联合决策接口**。MPC 每轮要对多个空闲实例做互不重叠的联合批选择（09-17 §11.7）。Dynamo 的接口模型是 per-request：Filter（过滤 eligible worker）→ Scorer（逐 worker 打分）→ Picker（"Selects one row"，`selector/policy.rs:111-143`）。**一次调用回答"这个请求去哪"，无法表达"这 3 个请求同刻发往实例 2、实例 1 再等 5ms"**。
3. **自定义策略挂载点够不着控制量**。检视报告 §4.1 指出 S 层挂载点是编译自定义 Rust policy（Filter/Scorer/Picker）——但如上，该接口的决策粒度是逐请求选 worker，S 层策略要求的组批/错峰/启动延迟动作在这个接口形状里**没有对应参数位**。让权必须发生在比 policy 更上层的 admission 处（§5.3-B2）。

### C2（E1/E3）控制语义错位：MPC 的"批"与 vLLM 的"批"是两个概念

假设架构里 σ 直接就是执行语义（一批一起执行、一起完成）。实际架构里投放决策只是引擎状态机的**输入**，批是引擎内部两阶段算法的**涌现结果**：

- 同刻把 N 个请求发给一个实例，若 Σprompt 超过 token 预算 → 分步准入；prompt 更长 → chunk 切开跨步；实例上已有 decode 在跑 → 预算被共享；KV 紧张 → 抢占清零重算。**"投放一个批"与"执行一个批"之间隔着整个调度器状态机**；
- 反向也不同：MPC 预测的完成语义是"末层完成=整批首 token"（F_i=Z_βL），实际是逐 token 流、各请求独立离批——TTFT/四目标的口径要重新对齐（decode 阶段的存在本身也是假设架构没有的维度，两份研究文档都只研究 prefill）。

后果：即使把控制量补上（C1 解决），MPC 的预测模型若仍假设"投放即整批执行"，预测将在首个 chunk/抢占/decode 干扰处失真。**预测模型必须升级为"vLLM 调度状态机 + 存储模型"的联合重放**——可行（20261010 §3.1 论证了离线推演所需的六类输入），但复杂度和误差源都远高于假设架构的重放器。

### C3（E2）状态观测缺失：MPC 的初始状态与反馈输入只有两个聚合数

MPC 每轮需要构建估计状态：各实例 waiting/running 组成、chunk 进度、KV 占用、远端传输进度、存储队列。实际路由侧可见的只有每 worker `active_requests` + `potential_prefill_tokens` 两个记账数（20261009 §3），且与真实执行隔着两层不可见差集（在途集合 ⊇ running ⊇ 本步执行批）。20261010 §3.2 的八项缺失观测清单（引擎侧到达时刻、步时钟、chunk 进度、KV/抢占、前缀命中、PD 传输完成、生成长度、spec 接受率）就是 MPC 状态估计缺口的完整枚举。存储侧同样：09-17 §11.2 要求的 DiskGroupObservation/PathObservation（带版本/延迟/置信度）在真实栈不存在，仿真里的 `Storage.snapshot()` 原型也尚无人消费（检视报告 §4.1 末段）。

### C4（E4）反馈节拍缺失：误差开环累积，MPC 退化为开环启发式

没有每步事件流，MPC 的"实际发生了什么"锚点只有输出流边沿（首 token/结束）。一次抢占、一次缓存命中、一步时序偏差都会通过引擎状态机传播放大而无纠偏通道（20261010 §3.2"误差是开环的"）。**严格说：E2/E4 缺失时，同一份 MPC 代码失去定义中的滚动纠偏性质**——这正是"当前架构对 MPC 不利"判断的技术内核：不利不在搜索算法，而在闭环的两个端点（控制端 C1、反馈端 C3/C4）都被架构堵死。

### C5 节拍与控制延迟：引擎毫秒级步进 vs MPC 决策周期

09-17 §11.1 设想的中央决策节拍是"实例空闲、关键完成、有限周期"，§11.8 预算墙钟 1ms 量级并明确"控制器不能暂停其他已经运行的计算与 I/O"。实际架构里引擎步是毫秒级、且 `async_scheduling` 下步 k+1 组批与步 k 执行重叠——MPC 计算期间被控对象在前进，预测的"当前状态"到手即过期。真实部署还有事件通道（StepBatch 流）的传输延迟。仿真里虚拟时间可以冻结（`settle()` fence 的先例），真实系统不行：**控制延迟必须计入 rollout 或作为保守余量**，这会压缩有效视窗。

### C6 多控制器互相稀释：三层决策都想控制同一资源

实际架构里已有两个活跃控制器：Dynamo 选择核心（每请求贪心选负载最轻）与 vLLM 调度器（自治两阶段组批）。MPC 作为第三个控制器加入，若不让权，其意图会在两个关口被改写：MPC 想让实例 1 空着等批 → 直通路由照样把新请求发给实例 1（它记账最轻）；MPC 想让 A、B 同批 → 引擎按预算把 B 排到下一步。**必须显式设计让权边界**（哪个控制器在哪个决策点上退位），否则 MPC 的控制量被稀释成建议。

### C7 存储侧控制量缺失：B 层与传输发起时刻

09-17 的 B 层（ASU 带宽分配）在真实栈没有挂载点（存储对计算侧是黑盒共享池）；PD/远端 KV 的传输发起时刻由引擎 connector 自身逻辑决定。仿真侧已建 `bandwidth_policy` 双策略挂载点（检视报告 §4.1 追记），但真实栈的 B 层与"动态 admission（waiting 请求是否启动远端读取）"都还是 P1 待建项。对 MPC 而言，这意味着第一版预测模型只能把存储当固定规则环境（B0），协同优化（E-SPB）后置。

### C8 研究对象本身的合法性：语义模型必须先拍板

检视报告 §5.3 早已指出："策略文档的系统模型是中央唯一等待队列+完整批；真实 vLLM 是连续批处理+chunked prefill+每 worker 独立调度+抢占。用真实代码做实验台，实验语义必然遵循 vLLM 而非策略文档的理想模型。"对 MPC 的含义是：**09-13/09-17 的形式化结论（四目标、复杂度、候选批目录、实验矩阵 E26–E31）都定义在假设架构的动作空间上**；换到真实架构，动作空间、状态空间、完成语义全变，这些结论不能直接迁移，需要重新形式化或显式声明两套口径（§5.2）。这不是工程障碍而是研究设计决策，且是所有后续工作的先决项（检视报告 §8.1）。

## 5. 解决办法

### 5.0 总览：三档路线

| 档 | 内容 | 得到什么 | 代价/边界 |
|---|---|---|---|
| A | **仿真内重建中央队列**：MPC 进驻本仓库胶水层 | MPC 全四要素（离线），验证算法收益（E27/E28） | 需区分两套实验口径；真实代码的"调度语义保真"让位于"接口/记账/KV 语义保真" |
| B | **真实部署接口改造**：观测流 + admission 让权 + （可选）组批让权 | 真实系统上的闭环 MPC，分弱/中/强三档 | 每档都要动 upstream 或新增组件；档位越高改动越大 |
| C | **零改造折中**：MPC 退化为参数调节器 | 参数级滚动优化（调 scorer 权重/每实例上限） | 控制量只剩标量旋钮，错峰/组批不可表达；作对照基线 |

### 5.1 档 A：仿真内重建中央队列（本仓库可立即做）

**位置**：`sim/run.py` 事件循环。今天它把到达即路由（`run.py:102-109`），改成：请求到达先入 MPC 全局队列；MPC 在决策点（到达/实例空闲/存储事件/定时唤醒）按滚动优化输出 (β, w, s)，在虚拟时刻 s 把 β 的成员**同刻投放**给实例 w（`add_request` + 记账）。

四要素在此全部成立，且都有现成基础：

- **E1**：投放时刻/目标/集合三个分量都在胶水层手里；"暂缓"就是让请求留在 MPC 队列（虚拟时间照走）。
- **E2**：胶水层天然看见全状态（`events.jsonl` 已记录 waiting/running/scheduled/waiting_remote；存储侧有 `Storage.snapshot()` 原型可升级）。
- **E3**：预测模型=离线推演，20261010 §3.1 已给出完备输入清单并论证本仓库具备——**rollout 就是仿真内核自身的受控重放**（对引擎状态机做浅拷贝/分支模拟，或用同一状态机做快速前向）。
- **E4**：虚拟时间可冻结，重算无竞态；实际轨迹每步可对照。

**让 vLLM 近似"收到一批一起执行"的充分条件**（档 A 的关键桥接结论，由 20261010 §2.2 的规则直接推出）——同刻投放的集合 β 要成为同一步准入的同批，需同时满足：

1. 所有成员在**同一个引擎调度步之前**完成 `add_request`（仿真里同刻投放即满足；真实系统见 B2）；
2. Σprompt ≤ `max_num_batched_tokens`，或接受 chunk 切开（那就要在预测模型里显式建 chunk）；
3. 该实例 waiting 队列中没有更早到达的其他请求（否则它们会排进同一/更早的批，改变批形状）；
4. `max_num_seqs` 有余量、`allocate_slots` 成功（否则触发抢占/停止准入）；
5. 无 decode 在途抢占预算（prefill-only trace 可回避；混合负载必须在预测模型里建 decode）。

**两套实验口径必须分开报告**（对应检视报告 §5.3 的路径 (a)/(b)）：

- **A1 假设架构口径**：用配置与投放纪律让引擎退化为"批执行器"——单活动批（控制投放节奏：上一批完成前不投新请求）、prefill-only、预算放大到不 chunk。此时 MPC 的预测模型可用 09-17 的事件重放器（批语义成立），E26–E28 实验矩阵在此口径下有效。**表述边界**：vLLM 的真实调度语义被有意驯化，真实代码的价值收缩为 KV 管理、记账接口与调度器数据结构的保真，须在论文中如实声明；
- **A2 真实引擎口径**：接受引擎自治（连续批处理、chunk、抢占全开），MPC 只控投放（时刻/目标/集合），预测模型用"vLLM 状态机+存储"联合重放。此口径研究的是"投放级 MPC 在真实引擎语义下还剩多少增益"——它与 A1 的差值本身就是重要实验结论（引擎自治吃掉了多少 MPC 收益）。

### 5.2 档 B：真实部署接口改造（弱 → 中 → 强三档让权）

**B1（前置，所有档位共用）：观测流。** 建 StepBatch 事件流（20261010 §4.2 的完整设计：每步发布批组成/准入/抢占/完成，PD 侧并入 `finished_recving`；通道类比 kv_events 的 ZMQ publisher 先例）。这是 MPC 的 E2/E4——没有它，任何档位的控制都是开环。过渡方案（输出流上的 RequestStateStats 时间戳解析）可先行为 MPC 提供边沿纠偏锚点（每请求至少 SCHEDULED/首 token 两个）。

**B2（弱控制）：MPC 挂 admission——借用并升级 `SchedulerQueue`。** 这是 §3.1(c) 发现的直接推论：upstream 已有"路由侧 class 队列 + RouterQueuePolicy + 记账触发放行"的全部结构，缺的只是把两个固定规则换成 MPC 指令：

- `should_queue` 从"class 超载才排"升级为"MPC 认为该扣就扣"（主动扣留：为凑批形状、为避开预测的热点窗口）；
- 放行从"记账空位即放"升级为"MPC 输出 (β, w, s)"——同刻把 β 成员放行到同一 worker，配合 B1 的观测即构成真实闭环。

改动面：kv-router Rust 侧的 admission 决策注入通道（策略接口从"选 worker"上移到"何时放行何者"，可在 `LocalScheduler`/`SchedulerQueue` 层面加控制器回调），或绕开 Rust 在 Python kv_router 组件层实现同语义队列（工程量小但失去 Rust 核心的记账一致性，需自行对账）。**仿真对应物**：把 `sim/router.py` 的直通 `SelectionService` 换成/并上一个带队列的投放层——恰好就是档 A 的 MPC 队列，两者是同一抽象在两侧的实现。

**B3（中控制）：引擎准入让权。** vLLM 侧经 `scheduler_cls` 继承（检视报告 §8.3a 已认定是"存储状态→真实调度"的最短路径）：waiting→running 的准入接受外部 gate——实例级并发上限动态调整、准入集合白名单、（PD 场景）远端读取发起时刻。组批算法本身不动（两阶段调度照跑，但准入受控）。MPC 的控制量仍是投放级+准入级，chunk/预算分配/执行顺序留给引擎。**这是"真实架构上 MPC"的实用甜点**：控制量覆盖错峰与并发整形，改动收敛在一个 Python 类。

**B4（强控制）：组批让权——引擎调度器退位为执行器。** fork/继承 scheduler，把两阶段算法的准入决策外置：每步的准入集合由 MPC 直接给出（StepBatch 事件流的反向通道）。此时真实系统在语义上回到假设架构（批由外部决定），MPC 预测模型可以复用 09-17 重放器。代价：深度修改引擎、失去 vLLM 调度器自身的鲁棒性兜底（抢占、防饿死）、上游版本升级成本高。**仅当研究问题需要"整批语义在真实硬件上成立"时投入**。

**B5（存储侧）：传输发起与带宽挂载。** 对应检视报告 P1 的 vLLM 动态 admission（waiting 请求是否启动远端读取）与 Rust `StorageAwareScorer`；B 层带宽策略在真实栈的挂载是更长线的工作（存储对计算侧的观测投影 + 控制通道都要新建）。第一版 MPC 可将存储固化为 B0 规则环境。

### 5.3 档 C：零改造折中——参数级 MPC

不改任何接口：MPC 滚动调节 Dynamo 选择核心的现有旋钮——scorer 权重（`decode_active_request_weight`/`prefill_load_scale`）、每实例限流阈值、（若启用排队）`router_queue_threshold`/queue policy。控制量从"批×实例×时刻"退化为"少量标量的时间序列"，错峰与组批不可表达。价值在于作为**对照基线**：量化"接口改造换来的控制自由度值多少"，支撑 B 档投入的 go/no-go。

### 5.4 建议组合与顺序

1. **先 A 后 B**：档 A1/A2 在本仓库先跑通 MPC 闭环（算法、候选生成、rollout、回退链全部可迭代），得到收益上界（A1）与真实引擎口径增益（A2）；A1−A2 差值 + 档 C 基线共同构成 B 档投入的依据——正对 09-17 §12.8 的预注册价值门槛（净改善≥5% 等）。
2. **B1 与档 A 并行推进**：StepBatch 事件流是观测基建，无论最终落在哪档都需要；其仿真对应物（胶水层全量观测）档 A 天然具备，可先在仿真内定义事件 schema 与定序语义（`(engine_id, step_seq)` 全序），为真实部署的通道设计定型。
3. **B2 起步，B3 视 A2 结果决定**：若 A2 显示投放级 MPC 在真实引擎语义下增益已足，则 B2+B1 即为部署形态；若增益被引擎自治显著稀释（A1−A2 大），则 B3 的准入让权是必要投入；B4 仅在整批语义被证明不可或缺时启动。
4. **语义决策先行**：C8 的两套口径选择（检视报告 §5.3）在档 A 开工前必须拍板，它决定 A1 是否存在。

## 6. 与研究路线的关系

- **检视报告 §5.3 的语义决策** = 本文 C1/C2/C8 的决策化表述；§8.1 将其列为 P1 先决项，本文从 MPC 视角给出了同一决策的技术依据与（§5.2）两套口径并行的方案。
- **检视报告 §8.3 的 P1 路线**（vLLM 动态 admission → Storage.snapshot 投影 → Rust scorer）与本文 B1/B3/B5 一一对应；本文新增的是 B2（SchedulerQueue 升级为 MPC admission 挂载点）这条此前未识别的结构路径。
- **20261010 §4 的 StepBatch 事件流**在本文中的角色从"观测接口"升级为"MPC 的反馈通道（E4）"；其 PD 补充字段（finished_recving）同时是错峰研究的关键观测量。
- **E26–E31 实验矩阵**的有效域：E26/E27/E28 定义在假设架构动作空间上，仅档 A1 口径有效；A2 口径需要自己的实验矩阵（投放级动作空间 + 真实引擎语义），建议作为 E28 的并列子组设计而非事后补做。
- **表述边界**：档 A1 中 vLLM 调度语义被驯化、B2 中 Dynamo 直通路径被替换——所有偏离"真实 Dynamo 路由 + 真实 vLLM 调度"默认形态的实验，都须在 report.json 的 scope/limitations 中显式声明（沿用现有 `scope` 字段惯例）。
