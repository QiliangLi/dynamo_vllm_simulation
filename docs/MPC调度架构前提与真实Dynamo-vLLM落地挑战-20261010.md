## 0. 一句话结论

MPC 假设的架构把"控制量、观测、预测模型、反馈节拍"四要素全部放在调度器手里；真实架构把这四要素拆散进了两个自治组件——控制量被直通路由的"逐请求立即单发"吃掉、观测被引擎进程边界挡住、预测面对的是引擎自治组批而非整批执行。**但在本仓库的真实代码仿真上，这四要素可以完整重建，且不需要修改任何真实代码**：控制量本来就握在 `run.py` 胶水层手里（"到达即投"只是当前主循环写法，不是架构约束，§5.2）；观测胶水层天然全量；**预测模型=把整个仿真世界（真实 vLLM 调度器对象+存储模型）深拷贝成影子世界再推进**——已用 `scripts/verify_rollout_copy.py` 真实运行验证：拷贝世界在相同驱动下与原世界轨迹逐位一致（§5.3），预测模型与被控对象同源、零模型误差；反馈靠虚拟时间冻结+每轮从真实状态重新拷贝。vLLM 的自治组批（chunk/抢占/分步准入）不是要消除的障碍，而是 rollout 如实预测的动力学。真实部署的迁移（StepBatch 观测流、Dynamo 排队能力升级）见 §6。

## 1. MPC 需要什么：四要素框架

本文用四个要素组织对照，先把 MPC 在本研究中的含义固定下来。09-13 §11.1 与 09-17 §11.8 的在线算法是同一形态：

```text
触发（请求到达/批完成/读取完成/定时器到期）
  → 构造观测快照（含己方提交回执补账）
  → 生成候选联合动作（批成员 × 空闲实例 × 立即/延迟启动，含"暂缓"空动作）
  → 对每个候选：在估计状态中重放（rollout）到视窗终点，统一终端代价，算四目标增量
  → 只落实第一个动作；未来计划留待下一轮重算
```

| 要素 | 内容 | 在 09-13/09-17 中的位置 |
|---|---|---|
| **E1 控制量** | 合法动作空间：批成员 β、目标实例 w、领取/启动时刻 u；σ=(P,w,u) | 09-13 §5.1/G2、09-17 §5.1 式(9)；"暂缓领取"是显式的空动作（09-13 §10.6"必须包含所有空闲实例再等一格的空动作"） |
| **E2 状态观测** | 中央队列、各活动批层进度、存储队列/服务率、暂存池 | 09-17 §11.2 接口表（RequestManifest/DiskGroupObservation/ComputeProgress…） |
| **E3 预测模型** | 给定状态与动作，推出未来轨迹与完成时间：共享事件重放器 | 09-13 §10.5 算法 A、09-17 §10.1；预测=重放是 MPC 的内环 |
| **E4 反馈节拍** | 滚动重算的触发事件与纠偏锚点（实际发生了什么） | 09-17 §11.1 时间尺度分层；§11.9 观测过期/版本冲突回退 |

**MPC 与一次式启发式的区别全在 E4：预测错了下一轮会被实际状态纠正。若 E2/E4 缺失，同一个搜索代码就退化为开环启发式，误差无界累积**——这是 §4-C3/C4 的判据。

## 2. 假设架构：MPC 的设计前提

两份研究文档的系统模型（09-13 §1.1/§5、09-17 §1.1/§5）概括为一句话：**调度侧维护唯一全局等待队列，分批下发给推理实例，实例对收到的一批一起执行**。五条约定：

1. **中央唯一等待队列**：请求到达即入 Q(t)；实例无本地等待队列，完成当前批后原子领取新批（09-13 §5.1）。
2. **调度器占有全部投放决策** σ=(P,w,u)：批成员、目标实例、领取时刻（含有限延迟/暂缓）；多实例联合决策（09-17 §11.7）。
3. **完整 prefill 批**：每实例同一时刻仅一个活动批（含 STALL 期），批成员绑定到最后一层，末层完成后整批一起产出首 token。
4. **存储侧有明确服务纪律**，带宽分配是决策层之一（09-13 FCFS 按需；09-17 B0/B1）。
5. **执行前不读、执行中仅下一层 lookahead**：批的数据依赖由领取时刻唯一决定。

该架构给 MPC 的核心便利是 **E3：实例是哑执行器，系统动力学完全由调度动作决定**——重放器没有隐藏自由度，09-13 §7.2/09-17 §7.1 的全局代价因此可计算。

## 3. 实际架构：当前实验台与真实部署

### 3.1 调度侧：Dynamo 的三种形态

| 形态 | 排队 | 下发原则 | 与本仓库的关系 |
|---|---|---|---|
| (a) 网关 ext-proc | 无（流式转发不缓冲） | 调用选择核心，逐请求 | 20261009 文档描述的真实部署路径 |
| (b) `SelectionService` 直通 | 无 | `select_and_reserve` 逐请求：成本分 = prefill 负载折算 + decode 负载 + 权重×active_requests，取最低（cache-blind 下无缓存重叠项，等分随机平局） | **本仓库仿真使用**（`sim/router.py`，Python in-process） |
| (c) 完整 kv_router 组件的 `SchedulerQueue` | **有（被动）** | `should_queue` = class 开启排队 且（该 class 已有积压 或 所有 eligible worker 的 prefill 记账满）；不排队则立即放行；排队后按 `RouterQueuePolicy`（fcfs/lcfs/wspt）排序，记账释放触发放行 | **本仓库未启用**；Python 配置面已暴露（`router_queue_policy` 等） |

**(c) 是本次分析新核实的结构性发现**（`lib/kv-router/src/scheduling/queue.rs`，`handle_enqueue`/`should_queue` 约 1058–1136 行；`config.rs:454-469`；Python 侧 `kv_router_args.py:212-218`）。三点精确表述：它是**被动排队**（超载才留请求，不能为等批/错峰主动扣留）；放行规则固定（记账空位即放），**不是开放给策略的决策点**；Python in-process `SelectionService` 的接口面（`_core.pyi:736-816`）**没有 enqueue 路径**，当前直通桥接方式接不到它。这与 20261009 文档"路由器看不见引擎内部"的结论不矛盾：排队改变"何时放行"，不改变观测边界。

### 3.2 引擎侧：vLLM V1 逐步重组批

每个推理实例内是真实 vLLM v0.20.2 `Scheduler`（细节见 20261010 文档 §2）：每引擎步两阶段重组合批（RUNNING 分 token → WAITING 准入，批逐步重组）；`max_num_seqs` 是并发上限、`max_num_batched_tokens` 是逐步共享预算；KV 不足触发抢占（清零回队首）；PD 远端 KV 门控（`WAITING_FOR_REMOTE_KV` 等传输放行）；完成语义是逐 token 流。本仓库 `sim/run.py` 把两层真实代码装进虚拟时间事件循环，胶水层看得见引擎内部状态（`events.jsonl`），但这只进产物文件不进路由决策。

## 4. 挑战：四要素逐项对照实际架构

**适用范围先分层**（避免误判）：C1 的仿真侧部分、C3、C5 在本仓库仿真内**不存在或已消解**（胶水层占有投放点与全量观测、虚拟时间冻结）——它们是**真实部署**的挑战；C2、C6、C8 在仿真与真实**共有**，但应对方式不同（仿真侧的应对见 §5，真实侧见 §6）。C4 在仿真内因 §5.3 的闭环设计而消解。

### C1（E1）控制量缺失：直通路由没有"扣住请求"与"联合决策"的合法动作

1. **无暂缓动作**：MPC 的错峰/等批 = 推迟领取时刻。直通路径上请求到达即单发，调度侧没有地方放一个未来才放行的请求。形态 (c) 的队列能放，但触发是超载被动排队。
2. **无联合决策接口**：Dynamo 的接口模型是 per-request（Filter → Scorer → Picker"Selects one row"，`selector/policy.rs:111-143`），一次调用回答"这个请求去哪"，无法表达"这 3 个请求同刻发往实例 2、实例 1 再等 5ms"。
3. **自定义策略挂载点够不着控制量**：检视报告 §4.1 指出的 Rust policy 挂载点（Filter/Scorer/Picker）决策粒度是逐请求选 worker，S 层要求的组批/错峰/启动延迟动作在这个接口形状里没有参数位。

### C2（E1/E3）控制语义错位：MPC 的"批"与 vLLM 的"批"是两个概念

投放决策只是引擎状态机的输入，批是两阶段算法的涌现结果：同刻投放的请求可能分步准入（预算不够）、chunk 切开、被 decode 抢预算、被抢占清零。完成语义也不同（整批首 token vs 逐 token 流；decode 阶段本身是假设架构没有的维度）。后果：预测模型若假设"投放即整批执行"，会在第一个 chunk/抢占/decode 干扰处失真——**预测模型必须把 vLLM 调度状态机作为被控动力学**。

### C3（E2）状态观测缺失（真实部署）

路由侧只有每 worker 两个聚合记账数（20261009 §3），与真实执行隔着两层不可见差集；20261010 §3.2 的八项缺失观测清单是完整枚举。存储侧 09-17 §11.2 要求的带版本/延迟观测在真实栈不存在。

### C4（E4）反馈节拍缺失（真实部署）：误差开环累积

没有每步事件流，"实际发生了什么"锚点只有输出流边沿；一次偏差通过引擎状态机传播放大而无纠偏通道。E2/E4 缺失时同一份 MPC 代码退化为开环启发式——这是"当前架构对 MPC 不利"判断的技术内核：不利不在搜索算法，而在闭环的两个端点（控制端 C1、反馈端 C3/C4）。

### C5 节拍与控制延迟（真实部署）

引擎毫秒级步进、`async_scheduling` 下步间重叠；MPC 计算期间被控对象前进，预测的"当前状态"到手即过期；控制通道还有传输延迟。

### C6 多控制器互相稀释（仿真与真实共有，需设计让权边界）

实际架构已有两个活跃控制器：Dynamo 选择核心（逐请求贪心）与 vLLM 调度器（自治组批）。MPC 作为第三个加入，不让权则意图被改写：MPC 想让实例 1 空着等批，直通路由照样把新请求发给记账最轻的实例 1。必须显式设计让权边界（仿真侧见 §5.5，真实侧见 §6）。

### C7 存储侧控制量缺失（仿真部分具备）

09-17 的 B 层在真实栈无挂载点；PD 传输发起由引擎 connector 决定。仿真里存储模型在进程内、`bandwidth_policy` 已是切换挂载点，但尚无在线策略接口；第一版 MPC 把存储固化为规则环境。

### C8 研究对象本身的合法性：语义模型必须先拍板

检视报告 §5.3：09-13/09-17 的形式化结论（四目标、复杂度、候选批目录、E26–E31）定义在假设架构的动作空间上；换到真实架构，动作空间/状态空间/完成语义全变。仿真侧的应对是**双口径并存**（§5.7），不必二选一。

## 5. 本仓库仿真上的 MPC 实施设计

本节是方案主体：四个部件逐一落到当前代码，全部**不修改任何真实（Dynamo/vLLM）代码**，只改胶水层与新增模块。

### 5.1 方案一句话

**MPC 控制器是 `run.py` 事件循环里的一个决策模块：请求到达不再立即投放，先入 MPC 全局队列；每个决策点，把当前世界（各引擎的真实 vLLM Scheduler 对象 + Storage）深拷贝成影子世界，在影子上试放各候选投放动作并推进到视窗终点算目标值，选最优的第一个动作在真实世界执行。** 预测模型与被控对象同源（都是真实代码），chunk/抢占/分步准入/PD 门控全部如实进入预测——不是近似。

### 5.2 控制量（E1）：投放点本来就握在胶水层手里

当前 `sim/run.py:102-109` 的写法是"到达即投"：`arrival_s <= now` 就 `router.route(r)` + `scheduler.add_request()`。**这不是架构约束，是主循环的三行写法**。MPC 化的改动：

```python
# 现状（run.py 事件循环内）
while cursor < len(rows) and rows[cursor]["arrival_s"] <= now + 1e-12:
    r = rows[cursor]; cursor += 1
    wid = await router.route(r)
    engines[wid].scheduler.add_request(reqs[r["id"]])

# MPC 化：到达只入队，投放变成决策
while cursor < len(rows) and rows[cursor]["arrival_s"] <= now + 1e-12:
    mpc_queue.push(rows[cursor]); cursor += 1          # 全局队列在此重建
...
# 决策点（到达/实例空闲/存储事件/唤醒定时器）：
action = mpc.decide(world, mpc_queue, now)              # §5.3
for r in action.batch:                                   # 执行第一个动作
    wid = await router.route(r)                          # 或 create_reservation 指定 w（§5.5）
    engines[wid].scheduler.add_request(reqs[r["id"]])
if action.is_wait: set_wakeup(action.delay)              # 空动作 = 请求留在队列
```

MPC 的三个控制分量与真实代码的对应：**β**（投放哪些请求）= `add_request` 的集合；**w**（发往哪个实例）= route 的目标；**s**（投放时刻）= 决策点选择空动作+定时唤醒。挑战 C1 的"无暂缓动作/无联合决策"在仿真里就此消解——中央队列在胶水层重建，等批/错峰/联合投放都是合法动作。合法批条件沿用 09-17 §3.1（人数/token/内存），空动作必含（09-13 §10.6）。

### 5.3 预测模型（E3）：深拷贝影子世界 rollout——已验证

MPC 内环要回答："若现在把 β 在 s 投给 w，之后会发生什么？"本实验台的独特答案是**让真实代码自己回答**：

```python
def rollout(world, queue, action, horizon, baseline_policy):
    shadow_store, shadow_engines, _ = copy.deepcopy(world)   # 世界=真实 vLLM Scheduler+Storage
    inject(shadow_engines, action)                            # 影子世界执行候选动作
    while shadow.now < horizon and not done:
        baseline_step(shadow_engines, shadow_store)           # 影子内按基线策略继续投放/推进
    return objective(shadow_engines)                          # 四目标之一 + 终端代价
```

**可行性已真实运行验证**（`scripts/verify_rollout_copy.py`，2026-10-10，demo 配置 2 实例 + 12 请求）：

1. 世界跑到中途（8 个请求在途、存储在传）时对 `(Storage, Engines, requests)` 整体 `copy.deepcopy` 成功——真实 `Scheduler`（含 `kv_cache_manager`/block_pool/请求对象）全部可拷贝；
2. 拷贝世界与原世界用**同一驱动函数**继续推进，每轮对比全状态指纹（时钟、每引擎 waiting/running/远端等待组成、逐请求 chunk 进度、空闲块数、inflight 批组成、存储队列余量、传输字节、步数），**逐位一致直至全部完成**；
3. 拷贝开销实测 18.45 ms/次（demo 规模，墙钟；虚拟时间为零——rollout 不占虚拟时间，MPC 的"决策计算期间系统冻结"在仿真里严格成立，C5 消解）。

这个验证同时定义了 rollout 的验收方法：**"零干预 rollout 必须复现真实轨迹"是 MPC 预测模型的一等断言**，可做成常开测试。预测模型=被控对象本身 ⇒ C2（批语义错位）不再是要消除的误差源，而是被如实预测的动力学；C4（开环误差）因每轮从真实世界重新拷贝而闭环。

工程量与优化空间：每次决策 K 个候选 × (1 次拷贝 + 视窗内推进) ≈ K×(18ms+推进)，K~10–30 时单决策点墙钟亚秒级，离线研究可接受；后续可用增量检查点（只拷贝调度器差量）或影世界懒同步优化。候选生成、视窗、终端排空策略直接沿用 09-17 §11.7–11.8 的设计（最老/最小 slack/四类代表候选，beam=8、深度=3、统一终端代价），本文不重复。

### 5.4 观测（E2）与反馈（E4）：现成

观测：胶水层直接读真实对象——`e.scheduler.waiting/running/requests`、逐请求 `num_computed_tokens`、`block_pool.num_free_blocks`、`store.queues/pending/rates()`。`events.jsonl` 已在逐事件记录同一访问面（`run.py:81-93`），MPC 用相同字段，无需新建观测层。反馈：每轮决策从**真实世界**状态重新拷贝与评估（预测状态不作跨轮传递）；决策点即事件循环的自然事件（到达/实例空闲/存储完成/唤醒）。挑战 C3/C4 在仿真内不存在——这正是 20261010 §3.1"离线推演可行"论断的直接体现，§5.3 的验证把它从论断变成了可执行的组件。

### 5.5 让权分工（应对 C6）：Dynamo 记账、vLLM 动力学、MPC 投放

三个控制器在闭环里的边界必须显式设计，本方案取：

| 控制器 | 仿真中的角色 | 让出的权 |
|---|---|---|
| MPC（新增，`sim/mpc.py`） | 投放决策：β/w/s 全部 | — |
| Dynamo 选择核心（真实代码保留） | **记账与路由一致性**：两种模式——(i) MPC 指定 w 后调 `create_reservation(selection_id, worker_id)`（`_core.pyi:793-802`，显式记账到指定 worker，真实记账路径）；(ii) MPC 只定 (β,s)，w 仍由 `select_and_reserve` 真实选择（保留"真实路由"成分，MPC 控制量收缩为投放时机+集合） | 选 worker（模式 i） |
| vLLM 调度器（真实代码保留） | 被控动力学：waiting→running 准入、chunk、预算、抢占、PD 门控全部自治 | 不让权——MPC 通过 rollout 预测它，通过投放时机影响它 |
| Storage（仿真模型） | rollout 内一并推进；`bandwidth_policy` 固定为环境规则 | 带宽决策暂不纳入控制量（C7 后置） |

模式 (i)/(ii) 是一组对照实验：差值即"Dynamo 贪心路由 vs MPC 指派"的贡献。首 token/完成时的 `prefill_complete`/`free_reservation` 记账回调不变（`run.py:70-80`），记账闭环与现在完全一致。

### 5.7 在线口径、对照与双口径（应对 C8）

- **在线口径（主实验）**：MPC 的 rollout 影子世界**不含未来到达**（trace 已知但策略不得使用）——这就是真实的在线 MPC；"离线全知"（rollout 注入未来到达）仅作 Oracle 上界对照。这继承了 09-13 §11.4/09-17 §11.2 的信息边界要求。
- **基线**：`S0` = 现状直通（到达即投 + Dynamo 贪心），即把 `mpc.decide` 换成恒等投放——它与 MPC 共享同一事件循环与 rollout 验收，差异只剩决策器，归因干净。
- **双口径**：(A1) 假设架构口径——配置驯化（投放纪律保证单活动批、prefill-only trace、预算放大不 chunk），使引擎行为趋近"整批执行"，09-17 的 E26–E28 实验矩阵与重放器在此口径有效；(A2) 真实引擎口径——引擎全自治，MPC 只控投放。两口径差值 = "引擎自治吃掉多少 MPC 收益"，本身是核心实验结论。A1 的表述边界：vLLM 调度语义被有意驯化，真实代码价值收缩为 KV 管理/记账/数据结构保真，须在 report.json 的 scope/limitations 声明（沿用现有惯例）。
- 检视报告 §5.3 的语义决策因此从"先二选一"放宽为"先跑 A2（改动最小、语义最真），A1 按需补充"。

### 5.8 已知风险与工程量

1. **deepcopy 对象图增长**：请求/块数大时拷贝成本线性增长（当前 18ms@12 请求）。缓解：增量检查点、影子世界懒同步、或按引擎分组拷贝（候选只动一个引擎时其余不拷）。需在正式实验前做规模曲线。
2. **rollout 与主循环的驱动一致性**：§5.3 的验证用独立驱动函数，正式实现应把 `run.py` 的推进逻辑抽成单一 `advance(world, action)` 供主循环与 rollout 共用——否则两处驱动漂移会让"零干预 rollout 复现真实轨迹"断言失效。这是实现时的第一等约束。
3. **虚拟时间与墙钟脱钩**：rollout 墙钟消耗不占虚拟时间，与真实部署的"控制延迟>0"不同；E30 类鲁棒性实验需显式注入决策延迟模型。
4. **Dynamo 平局随机**：`select_and_reserve` 等分平局随机（report limitations 已注明）会破坏 rollout 确定性——模式 (i)（MPC 指定 w）不受影响；模式 (ii) 需先落确定性 Picker（检视报告 §8.3c）。
5. 工程量估计：`sim/mpc.py`（队列+决策器+rollout 驱动复用）+ `run.py` 改造 + 验收脚本，1 人周量级；候选生成/目标函数参数化另计。

## 6. 向真实部署迁移（简述）

仿真验证 MPC 收益后，真实部署按"观测 → 让权"两步递进，详细论证见检视报告 §8 与 20261010 §4：

1. **B1 观测流（前置）**：StepBatch 事件流（每步批组成/准入/抢占/完成 + PD `finished_recving`）——MPC 的 E2/E4 在真实侧的对应物；过渡方案用输出流上的 RequestStateStats 时间戳解析做边沿纠偏。
2. **B2 弱控制**：把 §3.1(c) 的 `SchedulerQueue` 升级为 MPC admission 挂载点——"超载才排"改"MPC 主动扣留"、"记账空即放"改"MPC 指令放行 (β,w,s)"。upstream 已有 class 队列、fcfs/lcfs/wspt、记账容量的全部结构，改的是 admission 决策注入通道；仿真侧 §5.2 的 MPC 队列就是它的同语义对应物。
3. **B3 中控制**：vLLM `scheduler_cls` 继承做准入让权（实例并发上限/准入集合/远端读取发起时刻外置），组批算法不动——若仿真 A2 口径显示投放级增益被引擎自治显著稀释则投入。
4. **B4 强控制**（仅当整批语义必须真实成立）：组批决策外置，引擎调度器退位为执行器。
5. 零改造折中：MPC 退化为参数调节器（滚动调 scorer 权重/限流阈值），作对照基线量化接口改造的价值。

## 7. 与研究路线的关系

- 检视报告 §5.3 的语义决策（本文 C8）：§5.7 的双口径把它从先决项放宽为"先 A2 后按需 A1"；§8.1 的 P1 排序相应可调。
- 检视报告 §8.3 的 P1 路线（动态 admission → Storage 投影 → Rust scorer）与本文 §6-B3/B1/B5 对应；本文新增 B2（SchedulerQueue 升级为 admission 挂载点）这条结构路径。
- 20261010 §4 的 StepBatch 事件流在本文中的角色从"观测接口"升级为"MPC 的反馈通道"；其仿真对应物（§5.4 胶水层观测）可先行定型事件 schema（`(engine_id, step_seq)` 全序）。
- E26–E31 的有效域：E26/E27/E28 定义在假设架构动作空间上，A1 口径有效；A2 口径需要自己的实验矩阵（投放级动作空间 + 真实引擎语义），建议作为 E28 并列子组设计。
- **表述边界**：A1 口径驯化了 vLLM 调度语义、模式 (i) 替换了 Dynamo 的 worker 选择——所有偏离默认形态的实验在 report.json 的 scope/limitations 显式声明。
