## 1. 结论摘要

原交付仅验证 Linux x86_64。本次实测证明：在 macOS Apple Silicon 上，经三处受控适配后，**真实 Dynamo Rust `SelectionService` + 真实 vLLM 0.20.2 Scheduler + 按文件加载的 Ascend BalanceScheduler 构成的调度核心实验台可以原生运行**，且决策行为与 Linux 环境逐位一致（五模式汇总指标完全相同，见 §6）。macOS 因此可作为本工程的第二验证平台；但 `bootstrap.sh` 全自动路径仍仅限 Linux，mac 需按 §5 的手动步骤执行。

## 3. 三处平台适配（根因与解法）

### 3.1 torch：CPU 索引无 macOS wheel

`bootstrap.sh` 的 `torch==2.11.0+cpu` 来自 `download.pytorch.org/whl/cpu`，该索引只为 Linux/Windows 发布 `+cpu` 后缀 wheel（报错列出的可用平台为 manylinux/s390x/win_amd64）。macOS 官方 wheel 本身即 CPU 构建。

**适配**：改装 `torch==2.11.0`（无后缀同名版本）。
**副作用**：`scripts/doctor.py:23` 要求精确串 `2.11.0+cpu`，在 mac 上按预期失败（`Expected pinned CPU torch, got 2.11.0`）。该检查是 Linux 基准的溯源门槛，不作为 mac 通过条件；仿真与集成断言不受影响。

### 3.2 ai-dynamo-runtime：PyPI 只有 Linux wheel，且默认 feature 缺 SelectionService

`ai-dynamo-runtime==1.5.0` 在 PyPI 上仅有两个 manylinux wheel（x86_64/aarch64），无 sdist；最新 dev 每日构建同样仅 Linux。因此必须从本工程已按固定 SHA 下载的 dynamo 源码自行编译。

编译中发现的第二个坑：`SelectionService` pyclass 在绑定 crate 中被 `#[cfg(feature = "select-service")]` 门控（`rust/llm/kv.rs`），**默认 feature 集（`custom-policy`）不包含它**——不加 feature 编译出的 wheel 可安装但 `from dynamo.llm import SelectionService` 失败（`_core` 中只有 `SelectionServiceError`）。

**适配**：
```bash
uv pip install --python .venv/bin/python maturin        # 另需 brew 的 rust 与 protoc
cd upstream/dynamo/lib/bindings/python
SDK=$(xcrun --show-sdk-path)
CXXFLAGS="-isystem $SDK/usr/include/c++/v1" .venv/bin/maturin build --release \
    --features select-service --out /tmp/dynamo-wheels
uv pip install --python .venv/bin/python --no-deps /tmp/dynamo-wheels/*.whl
```
产物 `ai_dynamo_runtime-1.5.0-cp310-abi3-macosx_11_0_arm64.whl`，从固定 SHA 源码编译，版本与 Linux wheel 一致（1.5.0）。`CXXFLAGS` 的作用见 §4。编译约 8 分钟（依赖树含 parquet、google-cloud-storage、cudarc 等传递依赖，体量较大）。

### 3.3 vLLM：setup.py 在 darwin 强制覆盖设备为 cpu

vLLM 0.20.2 `setup.py:42-44`：`if sys.platform.startswith("darwin") and VLLM_TARGET_DEVICE != "cpu": ... = "cpu"`——环境变量在 macOS 上被无视，强制走 CPU 后端 C++ 扩展编译路径（本机触发后因 §4 的工具链问题失败；即便修好也非本工程所需，empty 模式从不导入 `vllm._C`）。

**适配**：将该条件改为 `not in ("cpu", "empty")`——仅当显式指定 `empty` 时不覆盖，macOS 未指定时的默认行为（自动 cpu）保持不变。这是一处对上游源码的有意修改；`setup.py` 不在 `source-fingerprints.json` 指纹清单内，doctor 溯源不受影响；已同步记录于包内 README 的 macOS 小节。Linux 环境不受该修改影响（原逻辑即允许 empty）。

## 4. 本机工具链问题：CommandLineTools 的 libc++ 残缺（与工程无关，但影响一切 C++ 编译）

症状：任何 C++ 编译报 `'cmath' / 'new' / 'cassert' file not found`。诊断：`/Library/Developer/CommandLineTools/usr/include/c++/v1` 目录存在但内容残缺，而 Apple clang 只从该路径查找 libc++ 头（SDK `MacOSX26.5.sdk/usr/include/c++/v1` 中那份是完好的，但不在默认搜索路径）。

**验证时的绕法**：所有 C++ 编译注入 `CXXFLAGS="-isystem $(xcrun --show-sdk-path)/usr/include/c++/v1"`（§3.2 命令中已含），vendored ZeroMQ 等编译即通过。

**根治**（需手动执行，验证时未做）：`sudo rm -rf /Library/Developer/CommandLineTools && xcode-select --install`。这是典型的 macOS 大版本升级后 CLT 损坏，与工程本身无关。

## 5. 完整复现步骤（macOS Apple Silicon）

在 `dynamo_vllm_cpu_sim/` 目录内执行（1–4 替代 bootstrap.sh 的对应步骤，其余与 Linux 相同）：

```bash
uv venv --python 3.12 .venv
.venv/bin/python scripts/fetch_sources.py                       # 三仓库固定 SHA 下载

# (1) torch：无 +cpu 后缀
uv pip install --python .venv/bin/python --no-deps 'torch==2.11.0'

# (2) lock 依赖（去掉 dynamo 行，它无 mac wheel）
grep -v 'ai-dynamo-runtime' requirements.lock > /tmp/lock-mac.txt
uv pip install --python .venv/bin/python --no-deps -r /tmp/lock-mac.txt

# (3) vLLM editable（setup.py 已按 §3.3 修改）
VLLM_TARGET_DEVICE=empty SETUPTOOLS_SCM_PRETEND_VERSION=0.20.2 \
  uv pip install --python .venv/bin/python --no-deps --no-build-isolation -e upstream/vllm

# (4) dynamo 自编译安装（见 §3.2，含 CLT 绕法与 select-service feature）

export PYTHONHASHSEED=0 VLLM_PLUGINS='' HF_HUB_OFFLINE=1 VLLM_LOGGING_LEVEL=ERROR
.venv/bin/python -m sim.run --output results/mac_default          # 默认模式
.venv/bin/python -m sim.run --scheduler upstream --output results/mac_upstream
.venv/bin/python -m sim.run --policy priority --output results/mac_priority
.venv/bin/python -m sim.run --config configs/slow_storage.json --output results/mac_slow
.venv/bin/python scripts/apply_ascend_patch.py                    # 生成显式补丁副本
.venv/bin/python -m sim.run --scheduler ascend_balance --output results/mac_ascend_balance
.venv/bin/python -m unittest discover -s tests -v                 # 3/3 通过
.venv/bin/python scripts/check_results.py results/mac_*           # 全部 PASS
```

`scripts/doctor.py` 在 mac 上因 torch 版本串差异失败（§3.1，预期）；其余检查（vllm 版本、editable 导入路径、指纹）通过。

## 6. 验证结果

### 6.1 汇总指标与 Linux 交付记录对照

| 模式 | 完成数 | 平均 TTFT (ms) | makespan (ms) | 读取量 (MiB) | vs Linux 记录 |
|---|---:|---:|---:|---:|---|
| 默认（Ascend 委托路径） | 12 | 5.364061 | 15.164912 | 48 | **逐位一致** |
| vLLM 原始调度器 | 12 | 5.364061 | 15.164912 | 48 | **逐位一致** |
| vLLM 原生 priority | 12 | 5.234561 | 15.164912 | 48 | **逐位一致** |
| 慢共享链路（10→0.1 GB/s） | 12 | 252.649073 | 673.670640 | 64 | **逐位一致** |
| Ascend balance + 显式补丁 | 12 | 5.364061 | 15.164912 | 48 | **逐位一致** |

一致性说明：虚拟时间由事件循环与确定性 tie 顺序（arrival_s、ID）驱动，与宿主平台无关，逐位一致是预期行为；Dynamo 原生 picker 对同代价候选存在平局随机，worker 标签可能对调，但汇总不变（Linux 复跑记录中已声明同一现象）。报告内 `scheduler_sha256`（`13e44070…`）与 `source-fingerprints.json` 中 Ascend 调度文件指纹一致，证明 mac 跑的确实是同一份固定源码。

### 6.2 存储延迟反馈到真实调度的因果证据

- 默认配置：SLO 达成率 100%（12/12，TTFT 阈值 20 ms）；慢链路（shared_link 10 GB/s→0.1 GB/s）：达成率降至 **33.3%**，worker 0 的 stall 从 5.3 ms 升至 **663.8 ms**、worker 1 为 496.5 ms——存储等待真实转化为调度停顿，而非只改数字。
- 请求级因果链（默认配置，r001，远端命中 64 token）：到达 t=0 → `kv_received` t=2.197 ms → 首 token t=2.826 ms，顺序满足 `check_results.py` 的"首 token 不早于依赖 KV 接收"断言；`WAITING_FOR_REMOTE_KVS → kv_received → token` 链路完整。
- 结束态：两 worker 未完成请求 0、可回收块 127/128（1 个 null sentinel，与上游行为一致）；Dynamo `active_requests / potential_prefill_tokens / potential_decode_blocks / pending_count` 全部归零。

### 6.3 单元测试与断言

存储模型 3/3 通过（动态竞争改写完成时间、同路径 FIFO、启动延迟+共享链路上限）；`check_results.py` 对五个结果目录全部输出 PASS（生命周期 / KV 等待 / 块回收 / 原生预留四组不变量）。

## 7. 已知限制与边界

1. 本报告所有时间为**合成模型的虚拟时间**，验证的是真实调度代码的决策因果闭环，不代表任何 NPU 的性能（与交付边界一致）。
2. mac 适配引入两处受控偏差（torch 版本串、vLLM `setup.py` 一行修改），均不触及被指纹保护的调度源码；`doctor.py` 的 torch 精确检查在 mac 按预期失败。
3. 自编译 dynamo wheel 与官方 Linux wheel 来自同一 SHA 源码，但构建产物未经 Dynamo 官方 CI 验证；`select-service` feature 是从源码门控推导出的必要 feature，官方并未发布 mac 构建配置。
4. 宿主 wall-clock（Python 导入、Rust 记账 fence 轮询、编译）与虚拟时间无关；makespan 15 ms 的案例实际宿主耗时以秒计，两者不可混读。
5. 本机 CLT libc++ 损坏问题（§4）未根治，重装 CLT 前所有 C++ 编译都需要 §3.2 的 CXXFLAGS 绕法。
