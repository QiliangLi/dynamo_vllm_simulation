## 一、目标与停止方式

### 目标

1. **主目标，与上一轮相同。** 找一套通用配置。五个负载的平均 TTFT 和完成时间相对默认策略（`light`）都改善，任何一项都不超出噪声地回退。幅度越大越好，不设上限。
2. **新增下限：不弱于出厂配置。** 本轮的起点不是空白。出厂配置已经在部分负载上明显好于 `light`（见 2.4）。候选相对出厂参考，两个指标都不得超出噪声地回退。
3. **可解释。** 候选声明的因果链和预测的数据特征必须出现。没出现的收益记为「未解释」，不能当冠军。

「通用」的含义与上一轮相同：一套参数跑全部负载，不依赖负载身份，能推广到没见过的负载。见第五节。

### 停止方式

- 唯一的正常停止方式是用户叫停。时长和轮数不设上限，系统不自己停。
- 安全停止照旧：冻结区校验失败、漂移重测后仍在、连续 10 轮运行失败、磁盘不足、网关长时间不可用。出现时挂起并写 `NEEDS_HUMAN.md`。

### 2.2 当前实现写死的规则（代码事实，读补丁得到）

| 环节 | 当前规则 | 位置 |
|---|---|---|
| 判重 | 均分份额 S = 参考带宽 ÷ worker 数，即 25 ÷ 4 = 6.25 GB/s。严格大于 S，并且达到 P75，才是重读 | `sim/stack/read_admission.py`（`bandwidth_central.patch`） |
| 许可账本 | 预算等于参考带宽 25 GB/s。账本里已有重读时，要求在持需求加本条需求不超过预算。账本为空时，任何需求都获批，超大请求独占。按条数的额度关闭 | 同上 |
| 被拒之后 | worker 记下返回的剩余额度。轻读上限取剩余额度和 S 中较小的。放得下的轻读里选需求最大的，相同取先到的。都放不下时选需求最小的。重试间隔 2 ms | `sim/stack/scheduler_admission.py`（`bandwidth_scheduler.patch`） |
| 开工上报 | 每条请求第一次分配成功后上报一次。有外部读的登记它的理论需求，没有的登记 0。首 token 或请求结束时销账 | `sim/stack/admission_service.py`、`scheduler_admission.py`（两个 `snapshot_*` 补丁） |
| 快照选队 | 余量 = 25 GB/s − 其他三个 worker 已登记的需求，可以是负数。候选按先 `skipped_waiting` 后 `waiting` 的原顺序扫描。取第一条重读，或第一条放得下的轻读。全部超限时取第一条重读，没有重读取需求最小的。没有快照时按原队列 | `sim/stack/scheduler_admission.py`（`snapshot_scheduler.patch`） |
| 重读分散 | `--heavy-spread` 取 off、5、10、100 之一。只对新到的重读生效。候选必须与最佳原分的 KV 命中相同。5 和 10 表示原分不超过最低分的 1.05 倍和 1.10 倍，100 不设上限。在其中选等待重读条数少的 worker | `scheduling/selector.rs`、`pending_score.rs`、frontend 的 `main.py` |
| 路由计分 | α = 0.1 | 配置键 `routing_accounting.waiting_factor` |

两处入口限制：

- `--heavy-spread` 在 Python 入口、frontend 和 Rust 三处都只接受 off、5、10、100。要搜任意百分比，必须改 Rust 并重建。
- `--release-on` 只接受 `first_token`。

### 2.5 上一轮自动调优的情况

流程（代码事实）：设计稿 v0.2。实现在 `lql_1125_tuning` 的 `scripts/tuning/`，包括守护进程、WSL 候选运行器、冻结评价器、静态门禁、角色定义、看板。候选运行器 `wsl/run_tuning.py` 逐步复刻当时的 `run_4w25.sh`，再叠加候选的覆盖层。当时的入口只有 light、tfs、a_cap1 三个固定臂。

运行结果（性能观察）：2026-11-25 启动，2026-11-28 停。跑完 9 代，643 轮回放，建了 23 个候选，没有冠军。两个候选通过了筛选和确认，其中一个在 10 GB/s 压力负载上因为完成时间回退被淘汰。第 10 代因下面的缺陷停在提案阶段。

今天核对出、尚未修的三处缺陷（代码事实）：

- `tuning/report.py` 的 407、859 行和 `tuning/search.py` 的 1013 行引用 `config.TIER2`。这个字典实际定义在 `scope.TIER2`，`config` 里只有 `TIER2_RUNG`。停滞阶梯升到第 3 级才触发，所以前 9 代没有暴露。
- `tuning/search.py` 980 行的 `Finalizer.step()` 用 `setdefault` 取收尾状态，而初始状态里 `final` 已经是空字典，于是抛 `KeyError: 'step'`。「停止并收尾」走不完，守护进程停在 `stopping` 反复重试。
- `needs_human` 状态没有退出路径。主循环只在 `paused` 状态下响应「继续」，`NEEDS_HUMAN.md` 里写的操作无效。

对上一轮经验教训的沿用：

- 流程自身的缺陷消耗过候选。本次要求前置工作里修掉已知缺陷，并为每个缺陷补一条走到那里的流程测试。
- 两路并行回放对 408 有系统性偏差（TTFT 高 7.7%）。回放并行度保持 1。
- 账本事件表在入口里只保留最近 10000 条。开了带宽账本或快照选队的轮次，校验改读完整日志，不受这个上限影响；light 和普通 TFS 的参考轮在 720、770 条的负载上会不会碰到，要在第 0 代看。
- 候选在 10 GB/s 压力负载上的完成时间回退是上一次淘汰候选的原因。带宽加权的规则在低带宽下怎么表现，本轮要重点看。

### 3.2 第二档：停滞时按阶梯放开

规则层面的改动，在上一轮的核心范围之内。例如：

- 用实测速率或观测到的拉伸，代替理论需求来记账和选队。
- 账本按 worker 分桶，或加公平性约束。
- 等待队列的老化和防止饿死。
- 快照的候选顺序和过期处理。
- 分散规则本身：任意百分比；比较等待 token 数而不是条数；加「等待条数相差至少 N 条才改选」的门限。这些在 Rust 里，每个候选要独立的构建目录。

上一轮第二梯队的三项保持不变：逐层预取深度、等待队列的基础排序、路由评分的 Rust 侧。

放开的顺序建议先「分散规则本身」，再上一轮的三项。理由见第十一节第 7 条。顺序由用户确认。

### 3.3 不纳入

- 存储带宽模型与分配规则。
- 计算耗时模型。
- benchmark 输入与到达时刻。
- 客户端、汇总脚本。
- vLLM 与 Dynamo 的内核实现，只通过现有钩子接入。例外是第二梯队里路由评分和重读分散所在的 Rust 代码。
- 校验脚本 `scripts/check_read_admission.py`。候选不能改它。

校验脚本要单独说明（代码事实）：它现在把默认规则写死了，例如断言 `is_heavy_read` 等于「超过均分份额且达到分位线」，断言许可只在「账本为空，或在持加本条不超过预算」时获批。候选一旦改这些规则就会被判失败。所以 P3 要把它改成按同一份配置计算，之后冻结。

## 四、评价协议（冻结）

沿用设计稿第十节，变化处标「新增」。

- **基线。** 默认策略 `light`，同一提交、同一入口步骤、串行。普通 TFS 另测，作参考。
- **出厂参考（新增）。** 出厂配置在默认参数下的各档：`bandwidth`、`snapshot-light`、`snapshot-tfs`，以及能重建时的 `spread5`、`spread10`、`spread100`。第 0 代各测几轮，登记为只读的参考候选，不参与晋升。
- **指标。** 平均 TTFT 和完成时间，沿用 `scripts/four_worker/summary.py` 的定义。其余只作诊断：P95 TTFT、轻读和重读各自的平均 TTFT、SLO 达成率、首层 KV 等待、拒绝次数、因分散改选的次数。
- **排序分。** 每个负载的改进分是两个指标相对基线的改进百分比各占一半。总分是各负载改进分的均值与最小值各占一半。
- **轮数。** 筛选每个负载 2 轮，确认补到 5 轮，差距小于噪声时自动加到最多 15 轮。冠军更替看 5 轮对 5 轮以上。最终报告用冠军与基线各 10 轮、交替进行的新数据。
- **统计。** 单侧 95% 置信，方差取自基线历史。噪声带按第 0 代在五个新负载上的实测重新确定。
- **并行。** 回放并行度为 1。
- **漂移。** 每 10 轮插 1 轮 light 对照，偏离历史带 3 个标准差就重测基线。
- **初始冠军。** 空。没有冠军时，新候选的父候选是出厂参考里总分最高的一档。有冠军后是现任冠军。
- **晋升。** 旧规则，加上第一条目标里的新增下限。出厂参考怎么对照，见第十一节第 1 条的建议。

每轮必须过的硬检查不变：仓库自带的 `verify` 和 `check_read_admission.py`，请求数、读取字节、模型计算总量与基线逐值相等。三份方案的验收项已经写在这些校验里，例如许可账本的记账前后一致、排空后在持带宽为 0、开工记录每条请求只登记一次。

## 五、通用性要求

与上一轮相同，下面只写和本轮有关的说明。

- **G1 一套参数跑全部负载。** 候选代码不得读取负载名、类标签、请求 ID、trace 内容、文件路径、环境变量。范围清单里已有的禁用词（`agentx`、`mooncake`、`synthetic_` 等）已经覆盖三个新负载的目录名，不用新增。
- **G2 尺度不变。** 链路带宽和所有需求同乘一个系数，决策不变。均分份额按 worker 数算，天然满足。新增参数必须保持这一点。
- **参数登记。** 冠军附敏感性分析，说明哪些参数起作用。
- **G4 留出验证。** 压力负载由五个冻结输入重新派生，只放沙箱：带宽 10 和 50 GB/s，到达密度减半和加倍，需求分布取全重、全轻、多零读、双峰、连续，实例数 2 和 8。实例数变化时均分份额跟着变，这是检验它的好机会。合成 trace 的混合负载只能取单一来源的请求并保持原顺序，否则过不了栈内的核对。冠军在压力套上不得有超出噪声的回退。留一法照旧。
- **G5 解释。** 预测的数据特征没出现，就标为未解释收益。
