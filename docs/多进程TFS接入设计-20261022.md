# 多进程 TFS 接入设计

## 目标

将已有 `AdmissionController` 接到真实多进程 DV 的请求路径，而不是仅在负载生成器中排队。保持现有 prefill_time 模型、真实 Dynamo 路由、vLLM Scheduler、KV 分配和存储带宽公式。当前分支已有未提交的多进程和 prefill_time 接入，继续在此基础开发，不提交/推送、不升级依赖。

## 路径与信息边界

`HTTP 客户端 → TFS HTTP 服务 → 原始 Dynamo frontend → 原始 worker/EngineCore → SimExecutor`。

独立服务提供 `/v1/completions`，复用 `sim/admission.py` 的分类、slack 排序、配额、老化和释放规则。`immediate` 与 `tfs` 走同一代理路径。`/v1/models` 透传，`/sim/admission` 提供事实记录。当前只验证 completion、stream=true、max_tokens=1；不添加完整 PD 协议或 decode 模型。

服务按请求真实到达时建立画像。输入为 prompt token 数、公开远端命中估计和固定配置，不读取未来 trace、实际 worker 队列或存储余量。客户端通过 `_sim_admission` 提交仿真请求 ID、预计远端 token 数和评价类别；代理转发前移除此扩展字段。估计与实际命中分开记录。服务不要求目标 worker 空闲。

## 请求关联与反馈

服务为每个请求生成 UUID，使用固定 Dynamo 1.5.0 已支持的 `x-dynamo-request-id` header 将 UUID 传到 worker 的 `context.id()`，再进入 EngineCore request_id。此 header 在该版本已标记 deprecated；这里只用于固定版本仿真关联，不宣称是新的生产扩展协议。拒绝不认识的关联 ID，不能猜测匹配另一个请求。

EngineCore 通过独立 Unix socket 回传事实事件，不改上游引擎代码：

- Connector 的外部读提交成功后：`load_submitted`，含尝试号和实际字节。
- Executor 领取 storage 完成集合后：`load_completed`。
- 首次实际执行、且未提交外部读：`no_external_load`。
- 代理观察到真实首个内容 token：`first_token`；正常响应完成：`request_finished`。

放行前先 reserve、mark_submitted。此时 worker 未知，先记录 -1，首个引擎事件绑定真实 worker，随后不允许换 worker。所有事件保留物理时刻、接收时刻、可见时刻；可见时刻至少为接收时刻和配置延迟之后。事件 ID 去重，KV 完成必须对应已登记提交。

`release_on=first_token` 默认；`load_done` 使用实际完成/no-load 反馈。配额释放不能依赖客户端填的预计读取量、公式预计完成时间或服务端私有存储快照。

客户端断开时，已放行的上游请求继续排空并按实际反馈释放，不伪造引擎完成。排队中的断开请求可从队列撤销。无法确认上游完成的传输错误应记录并停止新准入，不能乐观释放在途请求。正常失败响应、重复事件、延迟反馈和 no-load 需要单元测试。

## 实验与验收

新增可复现启动/回放脚本，顺序运行 immediate、TFS 首 token 释放、TFS KV 完成释放。使用相同混合负载、相同画像与存储参数，保留合成前缀来源。真实启动至少两个 worker 及其 EngineCore，不人为规定 batch=1。

验收：请求全部成功；中央确实扣留重请求；每次正常批准不超过当时配额；实际 KV 提交不早于放行；实际 KV 完成有提交记录；lease 最终全部关闭；多 worker 被使用；记录真实 batch 和中央等待/引擎时间，不预设 TFS 必须更快。全量测试与既有 prefill 公式回归均应通过。所有进程由本次启动脚本回收，结果保存至新目录。
