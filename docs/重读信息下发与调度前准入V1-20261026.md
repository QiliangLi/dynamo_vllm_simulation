# 重读信息下发与调度前准入 V1

本版本将申请额度的位置从 Dynamo 前的网关，移到 vLLM 的 `schedule()` 内。
网关继续维护全局账本。网关转发请求时不占用读取额度。
目标是减少 HTTP、前处理和实例等待期间的额度空占。

这是 CPU 多进程实验实现。Dynamo 原生路由、vLLM 引擎和 KV 分配器仍实际运行。
模型计算与外部存储仍由仿真器执行。本次没有运行收益矩阵。

## 1. 分支与启用方式

本地外层仓库和 DV 子仓库均使用 `codex/storage-read-admission-v1`。
DV 的 `79c6fea` 保存分支创建时已有代码，后续提交实现本功能。

默认仍使用旧网关准入。新增参数 `--admission-placement scheduler` 才启用 V1。
此参数同时设置 `classification=arrival` 和 `aging_enabled=false`。
V1 要求 `mode=tfs`、`release_on=first_token`、`scheduler=upstream`。

在已完成固定版本环境安装的 Linux 包目录中运行功能检查：

```bash
.venv/bin/python scripts/validate_read_admission.py \
  --output results/read_admission_layer_check --kv-mode layer_pipeline
.venv/bin/python scripts/validate_read_admission.py \
  --output results/read_admission_bulk_check --kv-mode bulk
```

两个命令必须顺序执行，输出目录必须不存在。每次使用两个 worker、12 个合成请求、
120 GB/s 共享池和 K=10。额度设置为 1，以验证拒绝与重试。这不是生产容量定标。

对已有输入启用：

```bash
PYTHONHASHSEED=0 .venv/bin/python scripts/run_tfs_stack.py \
  --config configs/mooncake_first_seen_layerwise.json \
  --trace configs/mooncake_first_seen.jsonl \
  --output results/read_admission_mooncake --workers 8 \
  --mode tfs --release-on first_token --admission-placement scheduler
```

命令沿用所选配置的块大小、命中模型和存储模型。它不会自动修改输入或带宽。
这是运行示例，本次未运行该八实例 Mooncake 命令。

## 2. 下发字段

网关根据已到达请求建立画像，并生成以下字段：

```json
{
  "storage_hint": {
    "version": 1,
    "is_heavy_read": true,
    "estimated_remote_read_bytes": 1024,
    "threshold_version": 7
  }
}
```

`is_heavy_read` 是准入判断。字节量用于校验和记录，不代表本版按字节分配额度。
`threshold_version` 指向生成判断时的阈值版本。字段类型、版本和完整键集合必须有效。
网关拒绝调用者伪造同名传输标记。worker 缺少标记时直接报错，不默认为轻读。

重读判断在请求到达网关时冻结。后续 P75 阈值更新不会修改已下发的判断。
全局并发额度仍按历史画像更新。额度下降时不撤回已发额度，等已有请求自然释放。
已有重读请求也不会因阈值上升而从占用账本中消失。

这与旧版动态重分类有区别。后续比较准入位置收益时，应给网关对照臂也设置
`classification=arrival`，避免同时改变分类口径。旧配置缺省仍是 `dynamic`。

## 3. 字段经过的链路

当前固定版本的 Rust HTTP 预处理器不透传任意 `extra_args`。
因此 V1 使用它已有的 `nvext.annotations` 传输字段，不重新编译 Rust：

```text
网关生成 storage_hint
  → nvext.annotations 中的 storage_hint_v1:<base64 JSON>
  → 原生 Dynamo HTTP 预处理与路由
  → PreprocessedRequest.annotations
  → Python worker 的 build_sampling_params 适配
  → 恢复 request.extra_args.storage_hint
  → SamplingParams.extra_args.storage_hint
  → vLLM InputProcessor / EngineCoreRequest / Request
  → Scheduler.add_request 校验
  → schedule() 读取
```

适配器保留原 builder 已生成的 `extra_args`，包括路由提示。
它不把字段放进 prompt 或 cache salt，也不通过私有画像表替代请求传输。
这是一条明确的测试传输适配。生产实现可以直接扩展 Rust HTTP 字段透传。

## 4. vLLM 的申请位置

```text
遍历 waiting / skipped_waiting 请求
  → 原有状态、LoRA检查及本地缓存查询
  → ReadGate.allow()，读取已有hint并申请额度
  → 原有外部KV命中查询
  → 原有token预算、分块及空间预检查
  → 原有 allocate_slots()
  → 原有 connector.update_state_after_alloc()
  → 原有组批和执行
```

hint标记轻读或预计外部读取字节为零：不发送额度RPC，继续原调度流程。
重读请求每次申请一条并发额度。申请成功后才进行外部KV查询和后续KV分配。
外部查询仍决定实际命中，不增加命中结果缓存，也不修改查询消息或存储服务。
额度不足的请求本轮不进入外部KV查询。
已有读取额度的请求不重复申请。

若返回 `full`，该请求进入原生 `skipped_waiting`，本轮继续检查后续请求。
本轮后续需要申请额度的重读请求直接跳过，轻读仍可继续。
这里没有对整个调度循环执行 `break`。
原有 token、batch 和 KV 空间约束仍可提前结束调度。

后续轮次会重试。默认 `retry_interval_wall_s=0.002`，用于限制全局查账频率。
这是壁钟时间，不乘 K；它不是保证在 2 ms 后恰好执行的定时器。
本版不做等待时长排序、不做超时插队，也不保证持续轻读流量下的防饥饿。

## 5. 全局账本与回滚

EngineCore 通过原生 Dynamo Runtime 的 TCP 请求面发送 `acquire` 或 `rollback`。
2026-10-27 后续版本默认使用 `dynamo`；首版 TCP JSON-lines 和 Unix 保留为显式对照。
网关在单个事件循环中执行检查与扣账，中间没有 `await`。
不同 worker 竞争同一份额度，不各自维护独立的全局余量副本。

申请携带请求身份、worker、加载次数、申请键和完整 hint。
网关核对已登记身份、worker 和冻结 hint，成功后返回唯一 `permit_id`。
同一申请键重复提交只返回原结果，不重复扣款。已回滚申请键不能重新发额度。

外部查询暂不可用、实际外部命中为零、后续预算/空间预检查退出，或
`allocate_slots()`返回`None`时，vLLM退还本次刚申请且尚未提交读取的额度。
回滚只允许发生在尚未提交读取时。同一回滚重复执行不会重复减账。
下次分配使用新申请键。若读取在前一轮已经提交，后续 KV 分配失败不能退还旧额度。

## 6. 完成与异常处理

connector 和执行器继续发送真实发生的加载提交、逐层提交及加载完成事实。
重读的加载提交必须能对应有效额度。加载完成本身不释放 V1 的额度。

网关从实际上游 HTTP 流观察首 token 后释放额度。正常完成事件幂等兜底。
本版沿用现有首 token 事实通道，**没有新增 FPM 释放通道**。
因此本版只后移申请位置，没有把释放位置提前到读取完成。

客户端断开时，现有 producer 继续排空已经发给上游的请求。
若通信超时、连接断开或上游执行状态不确定，则运行失败并停止新的额度申请。
不能把通信失败当成 `full`，也不能猜测读取已结束后擅自释放。
本版没有服务重启恢复或自动租约过期机制。

## 11. 准入通信改为 TCP（2026-10-27）

本节保留首版 TCP JSON-lines 的实现与命令。当前默认传输已由第 12 节替代。

默认准入通信现为 JSON-lines over TCP。每个 EngineCore 保持一条连接，
启用 TCP_NODELAY；请求与响应按换行分帧。申请、回滚和加载事实反馈共用此连接。
规则仍由同一个账本服务处理；不同连接上的申请在服务端原子检查与扣账。
额度钩子仍位于外部 KV 查询前，沿用当前重读判定、额度规则和首 token 释放。

标准 runner 自动在 127.0.0.1 上申请空闲 TCP 端口。服务启动后写出
`admission.rpc.json`，runner 将实际地址交给各 worker。
状态快照和申请响应记录实际 transport，独立审计核对它与配置一致。
`admission.rpc_transport` 缺省为 `tcp`；
`--admission-transport unix` 仅用于显式回放旧通信方式，不是网络失败的回退。

对照与功能验证命令：

```bash
.venv/bin/python scripts/validate_read_admission.py --output results/tcp_layer --transport tcp --kv-mode layer_pipeline
.venv/bin/python scripts/validate_read_admission.py --output results/tcp_bulk --transport tcp --kv-mode bulk
.venv/bin/python scripts/validate_read_admission.py --output results/unix_layer --transport unix --kv-mode layer_pipeline
```

依次执行，输出目录必须不存在。本机 TCP 回环经过 TCP/IP 协议栈，但不经过物理网卡
和交换机。此检查不能给出生产跨机延迟，也不能保证 TCP 一定比 Unix 明显更慢。
记录中的 RPC 耗时为真实壁钟往返时间，未除以 K；没有人为加延迟。

准入服务可以单独绑定网络地址：

```bash
.venv/bin/python -m sim.stack.admission_service \
  --config /path/to/config.json --upstream http://DYNAMO_HOST:28765 \
  --feedback-endpoint tcp://0.0.0.0:28767 --port 28766 \
  --event-log /path/to/admission.events.jsonl
```

worker 设置 `SIM_STACK_ADMISSION_ENDPOINT=tcp://账本服务IP:28767`。
连接地址应为可达 IP 或主机名，不使用监听通配地址 0.0.0.0。
`SIM_STACK_ADMISSION_TIMEOUT_S` 控制单次连接/收发超时，缺省 5 秒；标准 runner
从 `admission.rpc_timeout_wall_s` 传入。结果不确定时关闭连接并抛错，不自动重放申请。
此接口面向可信实验网络，尚未实现 TLS、认证或服务重启恢复。

跨机时不能直接相减两台机器的 monotonic 时间。本协议携带时钟域标识：
同一 Linux 启动与时间命名空间使用原始事件时间；不同或未知时钟域使用账本收到
事件的时间，并记录 `timestamp_basis=receiver_observation`。
后者是观察时刻，不能解读为设备事件实际发生时刻。发送方原值仅作诊断保留。
反馈事件 ID 加入连接 UUID，避免不同机器 PID 相同造成错误去重。

本次替换的是准入和反馈 RPC。存储模拟器的 IPC 与完整栈的本机启动方式未扩展。
网络准入端点可以远程连接；完整多机 Dynamo/vLLM/存储部署尚未验收。
新的运行记录见包内 VALIDATION；前述 2026-10-26 数据仍属于 Unix 版本。

## 12. 复用 Dynamo Runtime（2026-10-27 后续）

当前默认 `admission.rpc_transport=dynamo`。固定 Dynamo v1.5.0 的 Runtime 提供
TCP 请求面、连接复用、请求/响应分帧和 MessagePack 编解码。
独立准入服务注册账本端点；EngineCore 使用 `client.direct(request, instance_id)`
直接调用。该调用在固定版本中禁止更换目标实例。此路径不经过推理前端/路由器，
也不经过 vLLM 外部 worker 进程转发。

账本仍位于独立 `admission_service` 进程，和原 HTTP 接收、登记、hint 生成、
转发及首 token 释放共用同一个 `AdmissionState`。不是每个端点新建一份账本。
Runtime 将处理函数投递到服务已有的 Python 事件循环；检查和扣账期间不执行
`await`。多个引擎竞争同一份额度。仍只支持单账本实例，不能用普通负载均衡
扩成多个各自拥有完整额度的副本。

`schedule()` 保持同步。EngineCore 在初始化阶段创建一个常驻通信线程与事件循环，
在线程内创建 Runtime、发现端点、核对身份并完成一次 ping。
调度线程提交协程后同步等待结果。这只是同步/异步接口适配，不让调度循环继续执行。
等待申请期间，当前轮次后面的轻请求也会等待。原重读/full/回滚/2ms 重试规则不变。
同一客户端的控制和反馈仍串行发送。线程在引擎正常关闭或通信失败时清理。

runner 给每次运行生成唯一端点名。就绪记录包含 `instance_id`、`ledger_epoch`、
`server_pid`、`request_plane=tcp`、`codec=msgpack`。
客户端在初始化时固定该实例 ID 和账本启动标识，并在每个响应上核对它们。
服务发现变化、身份错误、超时或响应不完整均使客户端关闭，禁止自动重连、改投
其他账本或重放申请。账本重启后的恢复仍未实现。原幂等申请键仍保留。

申请日志的 RTT 从 `ReadGate.allow()` 调用客户端前开始，到完整响应返回后结束。
因此包含线程交接、Python/Rust 接口、编码、传输、账本处理及响应流收尾。
不包含初始化时的发现/ping，且不除以 K。该指标不能直接称为纯网络延迟。
跨机时钟域和 `receiver_observation` 规则沿用第 11 节。

标准功能验收命令（依次运行；输出目录须不存在）：

```bash
.venv/bin/python scripts/validate_read_admission.py --output results/runtime_layer --transport dynamo --kv-mode layer_pipeline
.venv/bin/python scripts/validate_read_admission.py --output results/runtime_bulk --transport dynamo --kv-mode bulk
.venv/bin/python scripts/validate_read_admission.py --output results/tcp_baseline --transport tcp --kv-mode layer_pipeline
```

手动启动时，服务和 EngineCore 需访问相同的 Runtime 发现后端。
单机可使用相同的 `DYN_DISCOVERY_BACKEND=file` 和 `DYN_FILE_KV`；跨机需配置双方
可访问的 etcd 或 Kubernetes 发现。本次完整栈只验收单机 file 发现。
服务示例（省略已有配置文件生成步骤）：

```bash
export DYN_DISCOVERY_BACKEND=file DYN_FILE_KV=/path/to/one-run/discovery
export DYN_REQUEST_PLANE_CODEC=msgpack DYN_SYSTEM_PORT=-1

  --feedback-endpoint dyn://tfs-demo.ledger.control \
  --feedback-ready-file /path/to/one-run/admission.rpc.json \
  --event-log /path/to/one-run/admission.events.jsonl
```

worker 使用 `SIM_STACK_ADMISSION_ENDPOINT=dyn://tfs-demo.ledger.control`，并从上述
就绪文件传入 `SIM_STACK_ADMISSION_INSTANCE_ID` 和 `SIM_STACK_ADMISSION_LEDGER_EPOCH`。
标准 runner 自动传入这些值。`SIM_STACK_ADMISSION_TIMEOUT_S` 缺省为真实壁钟 5 秒。
EngineCore 的 Runtime 关闭自身系统健康端口，避免占用从外部 worker 继承的同一端口。
Runtime 自己管理其网络连接与后台线程，额外开销需要计入实际测量。

本项替换的是通信机制。额度钩子仍在外部 KV 查询前，存储模拟器和逐层执行方式不变。
新路径不承诺比轻量 JSON-lines 更快；完整栈与回归的实测见 VALIDATION。
