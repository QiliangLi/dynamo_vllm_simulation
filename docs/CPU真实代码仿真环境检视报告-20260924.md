## 0. 结论摘要

**技术路线成立，P0 骨架质量高、声明诚实；但以"直接开展存储感知调度策略研究"衡量尚未到位，且有三处需求语义偏差需要先决策。**

1. **"真实代码 + 仿真执行"的核心主张属实**（核实见 §2）：真实 Dynamo 1.5.0 Rust `SelectionService`、真实 vLLM 0.20.2 `Scheduler/KVCacheManager/BlockPool`、按文件加载的真实 Ascend rc1 `BalanceScheduler`，NPU 计算与存储 I/O 由带排队、带宽竞争和异步完成语义的事件模型替代。因果闭环已验证：慢存储链路使平均 TTFT 从 5.36 ms 升至 252.65 ms，且等待真实经过了 vLLM 的 `WAITING_FOR_REMOTE_KVS` 状态机。
2. **按设计文档自己的分级，交付物是 P0（调度核心实验台）**。对"路由 / admission / KV 就绪因果"类研究已经可用；但策略研究所需的挂载点实例（Dynamo 自定义 Rust scorer、vLLM 动态 admission、StorageSnapshot 消费者）一个都还没建，存储模型与策略文档 09-17 的 ASU/Path/分类模型差距很大（§4）。
3. **三处需求语义偏差需用户决策**（§5）：①"推理引擎层真实"目前止于 Scheduler 核心，不含 EngineCore/ModelRunner，逐层 I/O 重叠研究在此粒度上做不了；②"包括 vLLM-Ascend 适配"目前只有 BalanceScheduler 一个文件，AscendStore/平台插件体系未接，自研 `SimConnector` 替代了 Ascend 真实存储边界；③策略文档的"中央队列 + 完整 prefill 批 + 单实例单活动批"模型与真实 vLLM 连续批处理/chunked prefill 语义不同，二者必须择一对齐。
4. 工程治理（版本 SHA 固定、源码指纹、doctor、验收断言、边界声明）显著优于一般原型，适合作为演进底座，**不需要推倒重来**。主要工程注意点：仅 Linux x86_64 验证过（当前开发机是 macOS，本机不可直接跑）、Dynamo 1.5.0 与 vLLM 0.20.2 是自定义桥接组合而非官方适配组合（§6）。

## 1. 需求基线

用户需求（沟通记录原文归纳）：

- R1 调度器层用**真实 Dynamo 代码**；
- R2 推理引擎层用**真实 vLLM v0.20.2 代码，包括 vLLM-Ascend v0.20.2rc1 适配**；
- R3 全部运行在 **CPU** 上；
- R4 需要 NPU 实跑的、需要接存储的，**mock 成仿真**（保留完成语义与资源竞争）；
- R5 目的：**调度策略修改（例如考虑存储状态）完全基于真实代码**，比自建仿真框架不失真。

策略文档定义的研究目标（09-17 为准，09-13 为其前序）补充的具体要求：

- 存储拓扑：D 个 ASU、每盘 256 Path、每盘 40 GB/s；SS/LS/SL/LL 四类请求的 Path 分组 96/96/32/32、组基础份额 20/12/4/4 GB/s（B0 规则），保底+借用+权重的 B1 规则；
- 三层协同策略空间：中央组批/错峰/启动（S0/S1）、NPU 组内选 Path（P0/P1）、ASU 带宽分配（B0/B1）；
- 逐层执行语义：执行前不读、本层计算开始时提交下一层读取（一层 lookahead）、KV 写回与暂存池背压；
- 观测模型：带版本/延迟/噪声的 StorageSnapshot，策略只能读观测投影而非真值；
- 四目标（M / SLO 满足率 / 平均 TTFT / 归一化 TTFT）、X∈{2,4,8} 配比扫描、E26–E31 实验矩阵。

### 2.1 确实真实的部分

### 2.2 仿真/替换的部分（声明与实现一致，无夸大）

- **执行层**：`schedule()` 读真实 SchedulerOutput，按线性模型 `T=α+β·N_prefill+γ·N_decode` 定虚拟完成时间，合成 `ModelRunnerOutput`（engine.py:163-191）；输出 token 恒为 100、`ignore_eos`、按 max_tokens 停止（engine.py:67, 174）。无 EngineCore、无 ModelRunner、无数值计算——与设计文档 §4"当前不实例化完整栈"一致。
- **设备**：`VLLM_TARGET_DEVICE=empty` 安装 + `CpuPlatform` 仅覆盖设备发现（engine.py:9），不装 torch_npu/CANN。
- **KV 元数据**：单层 `FullAttentionSpec(1 head, head_size 1)` 合成 spec；`kv_bytes_per_token=131072` 是独立存储参数，与 OPT 假 config 无推导关系（configs/demo.json 与 configs/model/config.json 并存，设计文档 §11 已声明需实测校准）。
- **Dynamo 记账 fence**：`Router.settle()` 用宿主 wall-clock 轮询等 native 记账收敛（router.py:20-41），该等待不计入虚拟时间（设计文档 §9 已声明）。

### 2.3 发现的实现细节问题（不推翻结论，但应知晓）

1. **`ascend_balance` 的单 rank 伪造**：engine.py:160 用 `balance_queue[0].fill_(len(running))` 把本 worker 运行数填进平衡队列，多 DP rank 的真实跨 rank 均衡逻辑并未执行。balance 模式目前的结论力 ≈ 默认路径（VALIDATION.md 三行 TTFT 完全相同可佐证）。
2. **一行 Ascend 补丁**：`patched/ascend_balance.patch` 在异步 KV 等待分支补 `request.num_computed_tokens = num_computed_tokens`。这是交付过程发现的真实上游疑点（否则反复加载无法推进），修复在 CPU 复现成立，但**未经 NPU 验证、未反馈上游**。建议向 vllm-ascend 提 issue 确认，避免研究建立在一个未与上游对齐的私有行为差异上。
3. **硬编码验收断言**：`check_results.py:19` 断言 `free_blocks == num_blocks - 1`（null sentinel），上游行为变化时会误报；属可接受的冒烟断言，但扩展实验时要改。
4. **平局随机性**：Dynamo 原生 picker 同代价候选存在随机平局，复跑汇总值相同但 worker 标签可能对调（VALIDATION.md 已声明）。做策略对照实验前，应先按设计文档 §9 落地确定性 `(cost, stable_worker_id, dp_rank)` picker，否则小样本策略差异可能被平局噪声淹没。
5. **p95 计算**：`sorted(ttfts)[ceil(0.95·n)-1]`（run.py:166）是简化分位数，12 请求无统计意义——交付物已自我声明，仅提醒实验阶段更换。
6. **存储放置哈希**：`location()` 用 `sha256(block+disk_id)` 取最大 digest 选盘（storage.py:41-50），功能上等价于静态一致性映射，但不是策略文档 09-17 §4.1 要求的带虚拟节点的哈希环（v=256），且 Path 由 hash 固定、**不可被策略选择**——这是与 P0/P1 选路研究直接相关的缺口（见 §4.2）。

## 4. 与策略文档研究目标的差距（按重要性排序)

### 4.1 策略挂载点全部缺失 —— 最关键差距

策略文档 09-17 的研究对象是 S/P/B 三层策略，当前实现三层都没有可改的入口实例：

| 策略层 | 策略文档要求 | 当前实现 | 缺口 |
|---|---|---|---|
| S（中央组批/错峰/启动） | S0 贪心 / S1 盘向量+窗口感知候选生成，含有限启动延迟 | Dynamo `select_and_reserve` 逐请求负载选择，无组批动作、无错峰动作、无启动延迟动作 | 需按设计文档 §15 编译自定义 Rust policy（Filter/Scorer/Picker），或先在桥接层模拟（见 §8 建议） |
| P（NPU 组内选 Path） | P0 最短队列 / P1 预计完成时间，含观测滞后与客户端账本 | Path 由 `location()` 哈希固定，无选择变量 | 需把 path 从数据结构常量改为策略决策点，并建观测投影 |
| B（ASU 带宽分配） | B0 按活跃 Path 均分 / B1 组保底+权重+上限 | 单一规则：活跃路径均分盘带宽 × 共享链路压缩（storage.py:61-74） | B0 无分类组份额（20/12/4/4），B1 不存在；"带宽分配作为动作"未建模 |

同时，策略文档的核心观测机制——带 epoch/延迟/噪声、只暴露观测投影的 StorageSnapshot——当前只有一个 5 字段的简化 `snapshot()` 原型且无人消费。这是"考虑存储状态"研究的输入端，缺了它一切存储感知策略都无从谈起。

### 4.2 存储模型粒度差距

当前 `sim/storage.py`（115 行）与策略文档 09-17 §4 的 ASU 模型逐项对照：

| 能力 | 09-17 要求 | 当前实现 |
|---|---|---|
| 盘放置 | 哈希环 + 虚拟节点 v=256，ring_version | sha256-max 静态映射（等价稳定性，无环/版本概念） |
| Path 分组 | 四类分组 96/96/32/32，固定 | 无分组，256 path 同质 |
| 组基础份额 | 20/12/4/4 GB/s + 空闲均分（B0） | 活跃 path 均分整盘 40 GB/s + path 1 GB/s 上限 + 全局 10 GB/s 共享链路 |
| 请求分类 | h>80000 / u>512 四类，边界样本 | 无分类概念 |
| 读写 | 读写共享 40 GB/s、写暂存池、F_i/F_i^persist 双完成语义 | **只读池**，`save_kv_layer` 直接 raise（connector.py:50-52） |
| 逐层 I/O | 层 ℓ 计算时提交 ℓ+1 读取，`t_start,l = max(t_finish,l-1, max KV-ready)` | 整个请求的全部远端块收齐才恢复调度，无层概念 |
| 观测 | 版本/延迟/噪声/置信度，真值隔离 | 无延迟无版本的同步快照原型 |

其中**写回缺失**和**逐层 I/O 缺失**对策略文档的研究问题影响最大：SL/LL 类请求"读少写多"、错峰与写暂存背压都是其核心研究对象。设计文档 §12 已将逐层模型列为"后续必须单独实现"，判断正确，但要认识到这不是锦上添花而是策略文档主问题的前提。

### 4.3 trace 与指标体系

- 当前 demo.jsonl 为 12 个合成请求（重复 token 构造人为前缀共享）；策略文档要求 h=0~128000、u=1~8192 的测量网格、四类代表配比、真实 tokenizer 的 trace。无此负载，E28–E31 无法开展。
- 四目标中当前只输出 M/平均 TTFT/p95/SLO attainment 的雏形；归一化 TTFT（需独占基线 T⁰）、分组损害、写债务、控制开销等指标字段均无。

## 5. 三处需要用户决策的语义偏差

这三处不是缺陷，而是"交付物定位"与"用户需求字面"之间的偏差，建议逐条拍板后再投入 P1：

1. **引擎层深度**：用户说"推理引擎层就用真实的 vLLM 代码"，交付止于 Scheduler 核心（合成 ModelRunnerOutput，每步一个聚合计算事件）。设计文档 §1 明确论证了这是推荐路线（全栈 Ascend Python 路径 no-op 化会成为"半个 Ascend 运行时仿真器"），本检视认同该论证。**建议接受该边界**，把完整 EngineCore（设计文档 §18.1 SimExecutor 方案）留作 P3；但若研究必须含逐层 I/O 重叠（策略文档的一层 lookahead），则至少要把执行边界从"每调度步"细化到"每层"，这属于 P2 的核心工作。
2. **Ascend 集成深度**：用户说"包括 vLLM-Ascend 适配"，交付只有 BalanceScheduler。AscendStore 后端（设计文档 §5 列出的 `ascend_store/backend/backend.py` 真实边界）未接，KV 传输协议走的是自研 SimConnector。若研究目标是"Ascend 存储路径上的调度策略"，应把 SimConnector 的行为对齐 Ascend 真实 backend 的接口与生命周期（注册、传输句柄、完成确认），否则策略迁回 vllm-ascend 时接口面会失真。若研究只关心通用调度问题，当前深度可接受，但需在论文/报告中如实表述。
3. **调度语义模型**：策略文档 09-13/09-17 的系统模型是"中央唯一等待队列 + 完整 prefill 批 + 单实例单活动批 + 执行前不读"；真实 vLLM 是连续批处理 + chunked prefill + 每 worker 独立调度 + 抢占。**用真实代码做实验台，实验语义必然遵循 vLLM 而非策略文档的理想模型**。两条对齐路径：(a) 修策略文档，把研究模型升级为 vLLM 语义（推荐——这正是"基于真实代码更不失真"的本意）；(b) 在真实 scheduler 上实现"完整批 + 中央组批"语义，即设计文档 §16 的 scheduler_cls 继承/patch 路线——这本身是一次不小的真实代码修改，需明确它也是被研究的对象之一。此决策影响后续所有实验的可比性，应在 P1 之前确定。

## 6. 工程与版本注意事项

1. **平台**：仅在 Linux x86_64（Python 3.12、glibc 2.39）验证；本仓库当前开发机为 macOS ARM。需要准备 Linux 机器/容器后再复跑验收。首次 bootstrap 需访问 GitHub/PyPI/download.pytorch.org，国内网络需代理（README 已说明）。
2. **版本组合**：Dynamo 1.5.0 官方组合是 vLLM 0.28.0；本工程以"绕开整套 vLLM adapter、显式桥接 SelectionService"的方式接 vLLM 0.20.2。这是自定义集成边界，**不可视为官方兼容组合**；将来若要接完整 Dynamo 服务栈（frontend/HTTP/worker 接口），要么升级 vLLM 到 Dynamo 支持版本，要么自担 adapter 兼容成本。Dynamo 版本是 ChatGPT 代选的（用户未指定），如生产环境另有版本，应尽早换版重验。
3. **依赖裁剪**：requirements.lock + `--no-deps` 是裁剪过的实验环境，`pip check` 会报缺失生产依赖；新启用任何 vLLM 可选路径前要审查其导入链（设计文档 §2 已提示）。
4. **可复现性缺口**：Dynamo 同代价平局随机（§2.3.4）尚未解决；报告未含完整 provenance（自定义 patch/trace/seed 哈希清单）——正式实验前按设计文档 §19 扩充。

## 7. 与既有自建仿真框架的关系

策略文档 09-17 §12.7 提到旧框架（`sim/cq/`、E1–E25 实验体系，在本仓库之外）。建议定位为**两条互补线**而非替代关系：

- 旧框架：抽象模型研究（策略文档的理想系统模型、S/P/B 因子矩阵、精确求解/证书）继续有效，尤其适合 §10 的离线最优与下界计算——真实代码实验台做不起穷举。
- 新实验台（本交付物）：承担"策略在真实 Dynamo/vLLM 代码上的落地验证与迁移性证明"。E26 的解析校验/对拍可先在旧框架做，E31 的"真实 trace + 配置迁移"则必须在新实验台做。
- 两边共用的存储模型参数（40 GB/s、256 path、分类份额）应提取为单一配置源，避免两套环境各自漂移。

## 8. 建议的后续路线（优先级排序）

对齐设计文档 P1–P3 与策略文档 E26–E31，按"对研究结论影响 × 工作量"排序：

1. **【先决】拍板 §5 的三个语义决策**（引擎深度、Ascend 深度、调度语义模型）。无此决策，P1 的实现方向无法确定。
2. **【环境】准备 Linux x86_64 环境，复跑 bootstrap + doctor + 集成断言**，确认交付可复现；顺手把 ascend_balance 一行补丁提给 vllm-ascend 上游确认。
3. **【P1-策略挂载】打通最小策略链路**（对应设计文档 §15/§16 与策略文档 S 层）：
   a. 先在 vLLM 侧做动态 admission（waiting 请求是否启动远端读取、在途字节/路径并发上限）——纯 Python，改 `scheduler_cls` 继承即可生效，是验证"存储状态→真实调度"的最短路径；
   b. 再编译第一个真实 Rust `StorageAwareScorer`（从 `custom-policy-example` 起步），并把 `Storage.snapshot()` 升级为带 epoch/延迟的观测投影接入 scorer 输入；
   c. 落地确定性 WorkerPicker，消除平局随机。
4. **【P1/P2-存储模型】存储模型向策略文档 09-17 对齐**：分类 Path 分组与组份额（B0）→ 可选 Path（P0/P1 决策点 + 观测账本）→ KV 写回与暂存池 → 逐层 I/O（最后做，工作量最大，依赖 §5.1 的层粒度决策）。
5. **【P2-校准】`kv_bytes_per_token` 从目标模型推导；计算时间模型用实机 SchedulerOutput+NPU event 采样拟合**（无 NPU 时先声明合成系数并固定）；构造带真实前缀共享结构与四类配比的 trace。
6. **【P3-按需】完整 EngineCore（SimExecutor）、PD 分离、多 rank、取消/失败**——仅当研究问题涉及服务协议或 PD 时投入。

工作量参照设计文档 §21：P1 约 1–2 人周，P2 约 2–4 人周（依赖测量资源），P3 更长。该估计与本检视的缺口清单规模相符。
