# 01 问题定位：cap 为什么塌缩，代价多大

日期：2026-11-17。数据来源：库存报告与 all-wsl-r1 原始事件，无新运行。

## 1. cap 计算链路（实现事实）

完整栈 `FrozenAdmission`（`sim/stack/read_admission.py`）继承
`AdmissionController`（`sim/admission.py`），cap 计算只有一份：

```python
# sim/admission.py on_arrivals()
xs = sorted(r.profile.pressure_Bps for r in self.records.values())  # 历史，含已完成
raw = xs[floor(quantile * (len(xs)-1))]          # quantile=0.75
theta = (raw if raw > 0 else min(positive))       # zero_rule
cap = max(1, floor(reference_bandwidth_Bps / theta))
```

- `pressure_Bps = read_bytes / compute_s`（`sim/reference_time.py`），
  语义是"读与计算完全重叠所需的读带宽"，是需求峰值而非实际占用。
- θ 的双重职责：既是分类线（`is_heavy`: pressure ≥ θ），又是 cap 分母。
  分类线希望 θ 高（切出最重的少数），cap 分母希望 θ 低（代表典型占用）。
  一个 P75 同时伺候两个目标，结构性冲突。
- 判满位置：`sim/stack/read_admission.py` acquire() 中 `held >= cap` 拒绝。
- 正式窗口排除预热历史（runner：`warm history excluded`），θ 样本从零积累。

## 2. 稳态 cap 与拒绝风暴（性能观察，all-wsl-r1 单盘）

从 `admission.events.jsonl` 统计（tfs-a01 / tfs-a1，432 次 threshold_updated）：

| case | cap 中位数 | denied 次数 | grants | 拒绝/授予 |
|---|---|---|---|---|
| mooncake_abc_90 | **3** | 3289 / 1959 | 171 | **19x / 10x** |
| mooncake_abc_100 | 4 | 3195 / 2058 | 170 | 19x / 12x |
| mooncake_abcd_90 | 4 | 441 / 852 | 166 | 3x / 5x |
| mooncake_abcd_100 | 4 | 723 / 618 | 166 | 4x / 4x |
| mooncake_random_90 | 8 | 970 / 1444 | 174 | 6x / 8x |

12 个逻辑实例下 cap=3~4，重读最多 3~4 个并发，其余全部在调度器侧
反复申请-拒绝（默认 2ms 重试节流）。

## 3. cap 轨迹与等待代价（abc_90 tfs-a01 事件重放）

- 轨迹：t=0 时 θ 命中零带 → cap 数亿（实际无限制）；t≈3.3s 收紧到 4；
  t≈4.1s 起稳定 **3**（θ 稳态 ≈2.5e10 B/s = 25 GB/s）。
- cap≤4 期间拒绝 3288 次。
- 171 次授予的等额度时间（request_arrived → admission_reserved）：
  **中位 329ms，p90 3491ms，最大 4657ms**。
- 对照该臂 mean TTFT 1063ms、p95 3269ms：排队时间主导 TTFT。

结论：问题不是"早期 cap 从 1 起步"（此前假设，已证伪），而是
**历史积累后 θ 被重读带 P75 顶到 25 GB/s，cap 收敛到 3 并卡死后续重读**。

## 4. 收益-代价失衡的既有表现（性能观察，库存报告）

- mooncake_random_90 四臂（20261102-192844）：tfs-a01 mean TTFT 930ms
  优于 direct 1200ms，但完成时间 7455ms 劣于 direct 6965ms——排队抵消竞争收益。
- 多盘 abc_90（20261102-214828）：tfs-a1 SLO 2.2% 低于 direct 3.3%。
- 原版 lease（round1）：abc_90 mean TTFT 2194ms、完成 10451ms，
  大幅劣于计数臂——lease 自身也有排队问题，不是现成答案。

## 5. 物理约束（诚实边界）

abc_90 负载存储饱和度 86%（run_summary saturated_pct）。准入不创造带宽，
只在排队位置之间转移。改进目标：找到净收益为正的 cap 区间，
不是消灭排队。

## 6. 改动的唯一焦点

分类口径、释放时机、EDF、反馈模式全部不动。只改 cap 的数值来源。
