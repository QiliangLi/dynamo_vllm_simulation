# 02 想法定稿

日期：2026-11-17。每个想法给出：假设、设计、预期、风险、验证方式。
实现细节见 [03-实现记录.md](03-实现记录.md)。

## 共同边界

- 分类线（θ=全体 P75 pressure，arrival 冻结）不动。
- release_on=first_token、EDF、direct_sum 反馈、EDF 排序不动。
- 只改 cap 的数值来源；legacy 行为作为默认值完全保留，通过配置切换。

## 想法A：cap_measured —— 实测占用速率作分母（主力）

### 假设

cap 塌缩的根因是分母用 pressure（读算完全重叠的峰值需求），
严重高估重读在持额窗口内的实际带宽占用。实际占用
= read_bytes / (授予 → 首token 的持额窗口)，包含计算时间摊薄，
典型值远小于 pressure（abc 稳态 θ=25 GB/s，而实测口径估计在数 GB/s 级）。

### 设计

- 分类线不变（θ）。
- cap 分母 d：
  - 已完成重读样本数 ≥ `cap_measured_min_samples`（默认 12）：
    d = median(rate_i)，rate_i = estimated_read_bytes / (first_token_s − reserved_s)，
    i 遍历历史中已释放额度的重读。
  - 样本不足：回退 d = θ（即 legacy 行为）。
- cap = max(1, floor(B_ref / d))，d 同时截断 d ≥ 1 B/s 防除零。
- 负反馈自校正：cap 放宽 → 并发重读增多 → 竞争摊薄使持额窗口变长 →
  实测 rate 下降 → cap 收紧。无需 AIMD 外环。

### 一个被否决的中间版本（记录以溯源）

最初提议 d = median(heavy 子集 pressure)。推导发现 heavy = {p ≥ θ}
意味着 median(heavy) ≥ θ 恒成立，该版本只会让 cap 更小，方向相反，否决。
正确分母必须离开 pressure 口径，改用实测占用。

### 预期

- abc_90：cap 从 3 升到 ~15-25 量级（90 GB/s ÷ 数 GB/s）；
  等额度 p90 从 3.5s 显著下降；mean TTFT 下降；完成时间不劣于 legacy。
- 存储侧竞争回升但受 max_min_fair 约束，不失控。

### 风险

- 早期样本 <12 时仍走 legacy（前段卡），影响有限（正式窗口前几秒）。
- 不同重读类型混合时 median 偏斜；首轮用 abc（同类为主）验证。
- 震荡：cap 放宽 → 样本更新 → cap 变化，可能抖动；median 缓解，
  若仍抖动再上滞回（列为想法C）。

### 验证

- 单测：legacy 等价性（未开 measured 时逐事件一致）、回退路径、
  median 计算、除零保护。
- 冒烟：--smoke --arm tfs-a01。
- 探索轮：abc_90 单臂 tfs-a01（measured），与 01 文档库存 legacy 数据比方向。
- 结论轮：同轮 direct + tfs-a01(measured) + tfs-a1(measured)。

## 想法B：fixed cap 扫描 —— 定界

### 假设

若存在固定 cap 值显著优于动态 cap=3，则证明"cap 过低"是主要矛盾，
并为想法A的目标区间提供锚点；若所有固定值都不好，则问题不在 cap 高低，
需重新审视。

### 设计

`admission.cap_fixed_int` 直接固定 cap（跳过动态计算）。扫描 3/6/9/12/18。
abc_90 单臂 tfs-a01 探索轮。

### 预期

最优固定 cap 出现在 9~18（带宽/实际占用的一阶估计），且 TTFT 单调或
驼峰改善。

### 风险

固定值对负载不通用——它本来就是定界工具，不是交付方案。

## 想法C：收紧护栏（滞回）—— 备用

### 假设

想法A的负反馈可能产生 cap 震荡（放宽→收紧→放宽）。

### 设计（仅在A出现震荡时实现）

cap 收紧时步长受限（新 cap ≥ 旧 cap × 0.5），放宽不受限；
或对 d 做 EMA。默认不启用。

## 想法D：overdraft 弹性超发 —— 兜底

### 假设

即使 cap 合理，瞬时突发仍可能把最老重读卡过久；给超龄重读一条
受控旁路可以削掉等待长尾。

### 设计

- `admission.overdraft_wait_s`（默认 0 = 关闭）。
- 账本在 acquire 判满时：若该请求等待（now − arrival_s）≥ 阈值且当前
  已无更老的重读在等，允许超额发放一条，日志记 over_cap=True
  （read_admission.acquire 已有 over_cap 字段）。
- 超发不加第二层限制：cap 本身经想法A修正后，超发只是尾部保险。

### 预期

p90/p95 等待与 TTFT 长尾下降；mean 变化小。

### 风险

超发过多时退回竞争状态；观察 over_cap 事件计数控制。

## 配置与入口汇总

| 键 | 默认 | 说明 |
|---|---|---|
| admission.cap_policy | legacy | legacy / measured / fixed |
| admission.cap_fixed_int | （无） | fixed 时的固定值，正整数 |
| admission.cap_measured_min_samples | 12 | measured 回退阈值 |
| admission.overdraft_wait_s | 0 | 弹性超发等待阈值，0 关闭 |

- benchmark 调参入口：`BENCH_TFS_JSON` 环境变量（JSON），只作用于
  tfs-a01 / tfs-a1 臂，仿 BENCH_LEASE_JSON 先例。
- 所有新键必须过 normalize_config 校验；legacy 缺省行为与现状逐字节一致。
