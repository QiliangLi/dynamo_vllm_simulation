## 0. 一句话结论

1. **组批规则**：V1 引擎没有"组好一个批贯穿始终"的概念。每个引擎步（`schedule() → 前向 → update_from_output()`）动态重组合批：先给 RUNNING 队列逐请求分配 token（decode 每请求 1 个、分块 prefill 继续 chunk），再用剩余 token 预算从 WAITING 队列准入新请求，两类请求进同一次前向。`max_num_seqs` 只是 RUNNING 并发上限，`max_num_batched_tokens` 是逐步共享的 token 预算，另有 KV 空间、抢占、前缀命中、PD 远端 KV 门控等条件决定成员进出（§2）。
2. **推演可行性**：组批规则是**状态机的转移函数**（内部状态 → 本步批），不是"可观测输入 → 批"的映射。**离线/仿真下可精确推演**——条件是占有状态机的全部输入与驱动事件（引擎侧到达时刻、KV 状态、输出长度、PD 传输完成时刻、每步耗时），本仓库的仿真桥正是这么做的；**在线真实部署中，Dynamo 路由器仅凭规则不可行**——上述输入几乎全部只存在于引擎进程内，且无纠偏反馈，误差开环累积（§3）。
3. **接口**：要到"每时每刻并发执行集合"，正解是让引擎**每步推送 StepBatch 事件**（数据在 `SchedulerOutput` 里现成，只差导出通道）；输出流带出的生命周期时间戳（已有、`log_stats` 门控）可作低成本过渡，prometheus 计数与快照查询只能对账（§4）。

## 1. 术语：两个"调度器"

| 称呼 | 指什么 | 本文角色 |
|---|---|---|
| 引擎内调度器 | vLLM V1 `Scheduler`（每个推理实例进程内） | 组批的**执行者**（§2 描述它） |
| 外部调度器 / 路由器 | Dynamo 网关 / 选择核心（独立进程） | 组批的**推演者**（§3–4 分析它能不能算出来） |

"每时每刻并发执行的推理请求"的精确定义：对引擎 $e$，第 $k$ 步的执行批 = 该步 `SchedulerOutput.num_scheduled_tokens` 的键集，即 `prev_step_scheduled_req_ids`（`scheduler.py:913-915`）。两条相邻步事件之间批组成不变——所以"每时每刻"等价于"每步"。

## 2. vLLM V1（v0.20.2）组批规则

### 2.1 决定批构成的参数

| 参数 | 语义 | 默认值 | 代码 |
|---|---|---|---|
| `max_num_seqs` | RUNNING 队列容量 = 并发 sequence 上限（调度器内叫 `max_num_running_reqs`） | API server 场景 256（H100 类 1024） | `scheduler.py:106`；`arg_utils.py:2210-2225` |
| `max_num_batched_tokens` | 单步 token 总预算，RUNNING 与 WAITING 准入**共享**；校验要求 ≥ `max_num_seqs` | API server 场景 2048（H100 类 8192） | `scheduler.py:371,107-111`；`config/scheduler.py:273-278` |
| `enable_chunked_prefill` | 预算不够时是否把 prompt 切 chunk | True | `config/scheduler.py:84-90` |
| `long_prefill_token_threshold` | 单请求单步最大 chunk（0=不额外限制） | 0 | `scheduler.py:413-414,678-680` |
| `policy` | `fcfs`（按 `arrival_time` 排序）/ `priority` | fcfs | `request.py:297-298`；`scheduler.py:479-488` |
| `scheduler_reserve_full_isl` | 准入前校验全序列能放进 KV | True | `scheduler.py:744-756` |
| `kv_role`（PD） | `kv_producer` / `kv_consumer` / `kv_both`，逐实例配置 | — | `config/kv_transfer.py:41` |

### 2.2 单步两阶段调度（核心算法）

引擎主循环每步执行 `schedule() → 前向 → update_from_output()`。`schedule()`（`scheduler.py:352-958`）分两阶段：

```
schedule():
  token_budget = max_num_batched_tokens                        # scheduler.py:371

  ── 阶段一：扫 RUNNING（scheduler.py:387-565，按队列序）──────
  for req in running:
      n = num_tokens_with_spec - num_computed_tokens           # decode=1(+spec)
      n = min(n, long_prefill_threshold, token_budget,
              max_model_len-1-num_computed_tokens)             # 408-421
      new_blocks = allocate_slots(req, n)                      # 464-471
      if new_blocks is None:          # KV 不够 → 抢占循环
          FCFS:   preempt = running 队尾                        # 504
          PRIORITY: preempt = 最低优先级                         # 479-488
          抢占效果: free KV、num_computed_tokens=0、            # _preempt_request
                    回 waiting 队首、记 PREEMPTED 事件          # 965-985
          若本请求自身被抢占 → break
      批.add(req, n); token_budget -= n

  ── 阶段二：准入 WAITING（scheduler.py:567-859）─────────────
  # 本步发生过抢占 → 整段跳过（防抖动，568）
  while waiting 非空 and token_budget > 0:
      if len(running) == max_num_seqs: break                   # 571-573
      req = 队首（FCFS: skipped_waiting 与 waiting 归并看，1580-1590）
      if req 在 blocked 状态（等远端KV/等grammar/等流式输入）: 跳过   # 582-592,1567-1572
      if LoRA 超限: 跳过                                        # 596-607
      computed = 本地前缀命中 + connector 外部命中               # 614-646
      if load_kv_async:        # PD: 远端 KV 异步加载
          只分配 KV 块；req → WAITING_FOR_REMOTE_KV；跳过       # 799-818
          （不入 running、不进批，等 finished_recving 放行，2074-2089）
      n = num_tokens - computed; n = min(n, threshold, budget) # 677-692
      if 非 chunked 且 n > token_budget: break                  # 684-690
      if 全序列放不进 KV（reserve_full_isl）: break              # 744-756
      if allocate_slots(...) is None: break                     # 758-776
      req 入 running；批.add(req, n)；记 SCHEDULED 事件          # 820-840
  return SchedulerOutput（本步执行批 = num_scheduled_tokens 键集）

update_from_output()（scheduler.py:1303-1566）:
  各 req: num_computed_tokens += 本步 n；追加输出 token
  EOS/stop/length/abort → finished → 出 running、释放 KV
```

**不变量**（`scheduler.py:862-872` 断言）：`len(running) ≤ max_num_seqs`；`Σ本步token ≤ max_num_batched_tokens`；本步执行批 ⊆ running（个别 running 请求可能因预算耗尽/PP 未完成等原因本步被跳过）。

### 2.3 规则要点（对应常见误解）

1. **`max_num_seqs=8` 不是合批目标，是并发上限。** ≤8 个请求同批 prefill 仅在"全部在同一调度步前到达 + prompt 总 token ≤ 预算 + KV 充足无抢占"时成立；否则分步准入（预算耗尽即 break）、长 prompt 被 chunk 切开跨步。
2. **批是逐步重组的。** decode 稳态下每步把所有 running 请求放进同一批（各 1 token/步）看似"整齐"，但成员随完成/抢占/新准入逐变化，且 decode 是逐 token 迭代，不存在"一次执行完"。
3. **PD 分离下是两套独立调度器、两套独立参数**，"batch size 8" 设在哪侧只约束哪侧：
   - **prefill 实例**（`kv_producer`）：规则同上；prefill 完成 → `request_finished` 交 connector 发送，`finished_sending` 后才释放 KV 块（`scheduler.py:2131-2134`），请求随即退出、批快速轮换；
   - **decode 实例**（`kv_consumer`）：新请求先经 `get_num_new_matched_tokens` 发现外部 KV（如 NIXL `do_remote_prefill` 返回 `(count, True)`，`nixl/scheduler.py:264-292`），**只分配块并置 `WAITING_FOR_REMOTE_KV`，不进批**；worker 侧逐请求报告 `finished_recving` 后才提升回 WAITING、下一步直接 decode（`scheduler.py:2074-2089, 2107-2130`）。KV 传输逐请求完成 ⇒ decode 批的准入天然错峰——这正是 AB 带宽实验研究的对象。传输失败且策略为 `recompute` 时还会回退本地重算。

### 2.4 组批时间线示意

```
 引擎步:      k      k+1     k+2     k+3    ...
 执行批:  {A,B,C}  {A,B,C} {A,B,C,D} {B,C,D}     ← D 中途到达（k+2 准入），
             ▲                        ▲            A 在 k+3 完成（EOS）离批
          A 首个 chunk             D 与 C 的 decode
          与 B、C decode            同一次前向
          同一次前向                （共享 token 预算）
```

每一步的批都由 §2.2 的两阶段算法现场决定；步与步之间批组成不变。

## 3. 外部调度器能否据此推演"每实例并发执行集合"

### 3.1 离线 / 仿真：可以，且本仓库已在做

把"知道规则"升级为"运行规则"：以真实调度代码为核心做事件驱动模拟，需要的完备输入清单：

| # | 驱动输入 | 在仿真中的来源 |
|---|---|---|
| 1 | 引擎侧逐请求到达时刻 + token 序列 | 输入 trace |
| 2 | 引擎配置（两个上限、chunk、threshold、policy） | configs |
| 3 | 逐请求生成结果（何时 EOS/stop） | trace 的输出长度 |
| 4 | KV 池大小与逐块状态、前缀缓存逐出历史 | 进程内真实 `kv_cache_manager` 维护 |
| 5 | PD：逐请求 KV 传输完成时刻 | 存储模型（带宽/排队） |
| 6 | 每步前向耗时（映射到壁钟/虚拟钟） | 层时间模型 |

本仓库 `sim/engine.py` 进程内驱动真实 vLLM v1 `Scheduler` 对象、`run.py` 事件循环供虚拟时钟，`events.jsonl` 里的 waiting/running 字段（`sim/run.py:170-181`）就是推演结果。**要点：可行性来源不是"知道规则"，而是"占有状态机的全部输入与驱动事件"。**

### 3.2 在线真实部署：仅凭规则不可行

路由器可见的事件只有：自己转发的请求（时刻、prompt）、流回的 token（首 token、结束），加上记账投影（`active_requests`、`potential_prefill_tokens`，见 20261009 文档 §3）。用它驱动 §2.2 的状态机，缺的输入是结构性的：

| # | 缺失观测量 | 归属（代码） | 推演后果 |
|---|---|---|---|
| 1 | 引擎侧到达时刻（`arrival_time` 在 Request 构造时打点，`request.py:93`） | 引擎进程 | 路由器只见转发时刻，隔着网关→传输→API server→processor 的排队抖动；FCFS 排序与首步准入整体错位 |
| 2 | 步时钟与每步前向耗时 | 引擎主循环 | 不知道"到现在发生了多少步"，"每时每刻"无法对齐壁钟；`async_scheduling` 下步 k+1 组批与步 k 执行重叠（`async_scheduler.py`），时序更不可外推 |
| 3 | `num_computed_tokens`（chunk 进度） | 引擎 | chunk 边界与预算消耗推错 |
| 4 | KV 占用与 `allocate_slots` 结果 → 抢占是否发生（`scheduler.py:464-514`） | 引擎，运行时事件 | 批成员与重算轨迹推错 |
| 5 | 前缀缓存命中（`get_computed_blocks`，块哈希 + LRU 逐出历史，`scheduler.py:614-662`） | 引擎 | 即便路由器知道 token 序列，命中数仍取决于引擎**当前缓存了什么** |
| 6 | PD：逐请求 KV 传输完成（`WAITING_FOR_REMOTE_KV` 放行时刻） | worker 侧 connector | decode 批准入时刻推错——恰是错峰研究关心的量 |
| 7 | 生成内容决定 FINISHED 时刻（EOS/stop） | 模型采样 | 请求何时离批不可知，只能假设 max_tokens → 系统性高估并发 |
| 8 | spec decode 逐步接受率（若启用） | 引擎 | 每步 token 前进量随机 |

并且**误差是开环的**：没有任何反馈通道告诉路由器"上一步推错了"，一次偏差（一个抢占、一次缓存命中、一步时序）会通过状态机传播放大。Dynamo 的记账投影只能对齐最粗粒度的"在途集合"：

```
在途集合（记账可见） ⊇ running（含 chunk 未完/等 KV 已分配者） ⊇ 本步执行批
        ↑ 差集 = 排队 + 等远端 KV + blocked          ↑ 差集 = 本步被跳过者
                     两层差集对路由器都不可见
```

**结论：在线推演只能得到上界近似（在途集合）与保守容量估计，得不到逐时刻并发执行集合。** 缺的不是规则知识（§2 已完备），而是驱动状态机的实时事件流。

### 3.3 一个直接佐证

本仿真之所以能在 `events.jsonl` 里给出每步 waiting/running，是因为胶水层就"住"在引擎旁边、拿得到 §3.1 表全部六项输入。把同一套推演搬到真实部署的路由器进程里，第 1–7 项输入立即全部失效——这说明差异的本质是**观测通道**，不是算法。

## 4. 要实现"调度器处获取每时每刻并发执行集合"，需要什么接口

### 4.1 三档方案

| 档 | 方案 | 原理 | 能否达标（"每时每刻"+身份级） |
|---|---|---|---|
| 1（推荐） | **StepBatch 事件流（push）**：引擎每步发布批组成事件 | 数据在 `SchedulerOutput` 现成，加导出通道 | **能**，且是真相直读、零推演 |
| 2 | 原子快照查询（pull）：HTTP/gRPC 拉取 running/waiting 快照 | 新增查询端点 | 不能：拉取周期 staleness + 步循环竞态；适合对账与初始同步 |
| 3 | 输出流带出（过渡）：解析 token 流上的生命周期时间戳 | 复用 `log_stats` 事件 | 不能：只有边沿没有每步批组成（见 4.3），但近乎零成本可先行 |

### 4.2 档 1 设计要点：StepBatch 事件

```
StepBatchEvent {
  engine_id, model,
  step_seq: uint64,        # 引擎内单调递增 → 跨进程定序用
  ts: float,               # 引擎单调钟；跨实例不可比（只用于步间隔）
  scheduled: [{rid, num_tokens}],   # = SchedulerOutput.num_scheduled_tokens
  admitted:   [rid],                # 本步新进 running
  preempted:  [rid],                # 本步被抢占回 waiting
  finished:   [rid],                # 本步完成离批
  # 可选聚合：running_count, waiting_count, num_free_kv_blocks
}
```

- **挂点**：`schedule()` 组装完 `SchedulerOutput` 之后（`scheduler.py:923-958`），此时全部字段现成，无额外计算。
- **通道**：vLLM 已有 `kv_events` 的 ZMQ publisher 先例（`kv_event_publisher`，`scheduler.py:140-143`），可类比新增 `batch_events_endpoint`；Dynamo 形态下由 worker 组件在 token 流之外旁路 NATS topic 发布，路由器订阅。
- **定序与语义**：按 `(engine_id, step_seq)` 全序；"每时每刻并发集合" = 相邻两条事件之间的 `scheduled` 键集。不需要跨实例对钟——路由器关心的是各实例内部的批演化，跨实例比较用 step 计数即可。
- **PD 补充**：decode 实例的 `finished_recving`（`scheduler.py:2122-2130`）应并入同一事件流（或等价地由下一条事件的 `admitted` 体现），否则路由器仍不知道 KV 传输何时放行；`finished_sending` 属 prefill 侧资源语义，非并发集合必需。
- **开销**：每步一条消息、O(max_num_seqs) 个请求 ID 的序列化，相对毫秒级前向可忽略；若仍嫌多，可在"批组成发生变化"时才发全量、否则发心跳，但会稀释"每时每刻"语义。

### 4.3 现有存量接口盘点（为什么不够）

| 存量 | 内容 | 位置 | 缺口 |
|---|---|---|---|
| `EngineCoreEventType`（QUEUED/SCHEDULED/PREEMPTED，单调时间戳） | 请求级生命周期边沿 | `vllm/v1/engine/__init__.py:128-152`；记录点 `scheduler.py:821,1761,982` | 只有边沿，无每步批组成；PREEMPTED 不产生输出 token，没有携带载体；`log_stats=True` 才记录 |
| `RequestStateStats`（queued/scheduled/first_token 时间戳）随 `RequestOutput.metrics` 回流 | 前端/网关可从输出流解析 | `vllm/v1/metrics/stats.py:202-221`；`output_processor.py:176` | 同上：到不了 chunk 进度与逐步成员变化；时间戳为引擎单调钟 |
| prometheus `vllm:num_requests_running` / `waiting` | 计数 gauge（running 的 documentation 即 "Number of requests in model execution batches"） | `vllm/v1/metrics/loggers.py:452-470` | 只有数量没有身份；抓取式，staleness ≥ 抓取间隔 |
| `get_request_counts()` | (running, waiting) 计数 | `scheduler.py:1737-1739` | 进程内接口，未导出 |
| KV 事件流（`kv_events`） | 前缀块存储/逐出事件 | `scheduler.py:140-143` | 对象是缓存块不是批 |
| Dynamo 记账投影 | 每 worker `active_requests` + `potential_prefill_tokens` | 20261009 文档 §2-3 | 在途集合的投影，与 running/本步批隔着两层不可见差集 |

### 4.4 建议组合

1. **主通道**：档 1（StepBatch 事件流 + PD `finished_recving`），一步到位满足"每时每刻、身份级"。
2. **过渡**：档 3 先行——网关解析输出流上的 `RequestStateStats`，把推演从"纯开环"升级为"边沿纠偏"（每请求至少对齐 SCHEDULED/首 token 两个锚点），误差有界化。
3. **对账**：档 2 快照 + 已有 prometheus 计数，做事件流的丢失检测与重启重同步（事件流需配 step 序号水位，断流后从快照补齐）。

## 6. 与本仓库研究路线的关系

- **P1 观测链路**（检视报告 §8：vLLM 动态 admission 状态 → `Storage.snapshot()` 投影 → Rust scorer）正是 §4.2 档 1 的仿真对应物：仿真胶水层天然"住在引擎旁"，所以 `events.jsonl` 拿得到每步 waiting/running；真实部署要拿到同样信息，就要新建 StepBatch 事件流这条旁路。
- **错峰研究**（E26–E31、AB 实验）关心的 decode 批准入时刻由 `WAITING_FOR_REMOTE_KV` 放行决定；档 1 中的 `finished_recving`/`admitted` 字段即其在真实部署的对应观测量。
- **表述边界**：本文 §2 可作为"真实系统组批语义"引用；§3 的结论与 20261009 文档一致——路由器对引擎内部只有记账投影没有真相，这不是仿真的简化假设，而是真实 Dynamo 的既有边界；要突破它属于新建能力（P1），不是打开现成开关。
