# Dynamo 分级命中画像接入

开发分支：`codex/dynamo-tier-admission-20261104`。基线：`10e227e`。
本模式不改变现有 benchmark 默认行为，不更新上游，也不替换已安装的 Dynamo 扩展。

## 请求流程

```text
普通 HTTP 请求 → 网关只登记 ID、到达时间和输入长度
  → Dynamo 原生分级索引查询
  → prepare：按候选实例生成画像、冻结重读标记和 storage_hint / EDF
  → scorer：读取各候选标记，对当前重读请求的新增负载应用 α
  → 原生 picker → 完整资源 booking → 绑定选中请求的等待重读账本
  → commit：确认选中画像，直接复用 prepare 阶段生成的标记
  → 随请求下发 → vLLM Scheduler 申请中央额度
  → Connector 核对实际命中 → allocate_slots → 原有逐层读算
  → 首 token 释放额度
```

2026-11-04 时序修正：上一版在 picker 和 booking 之后才分类，标记只能影响后续请求。
现在 prepare 位于分级查询之后、第一次 scorer 之前。不同候选实例可以得到不同的命中量和轻重分类。
scorer 同时保留既有等待重读折扣，并对当前候选的新增 prefill/decode 成本应用 α。
只折扣当前请求的增量，不把实例总分整体乘以 α；活动请求项不新增折扣。
完整资源 booking、容量检查和 picker 保持原生实现。α=1 时当前增量不打折。
默认 trace 模式仍沿用既有等待重读计分，不自动引入当前候选折扣。

画像回调由 Dynamo 内部发起。Python 估时和中央额度账本仍在原服务进程中。
内部回调使用每轮身份校验的本机 HTTP，5 秒超时，分 prepare 和 commit 两次调用。
worker 的额度 RPC 继续使用原配置的 Dynamo Runtime/TCP/Unix 传输。
commit 只确认选择和提交历史，不重新生成标记，不重新分类。
prepare 失败时不进入 scorer；commit 失败时 native guard 清理已建立的 booking。

P75 分类对每个候选使用“已提交历史 + 当前请求放到该候选”的压力序列。
候选画像互为替代，不把多个候选都写入历史。只有选中画像在 commit 时进入历史一次。
即使并发请求在此期间更新历史，当前请求仍保留 prepare 时的分类。
`threshold_version` 记录预分类序号；`tier_profiles_prepared.history_version` 单独记录所用历史版本。
原生候选标记按请求 UUID 和 worker/rank 保存，scorer 和 booking 读取同一份标记。
请求选择调用结束时清理这份临时标记，长期等待/获准状态仍由原评分账本维护。

## 命中量的准确口径

固定上游提交为 `b83b1d9304ebfc624709ac46db32b1b6f1ff1615`。
在原生 `OverlapAnalysis` 完成查询后，使用同一份 signals 为各候选调用 `selected_worker_tiers`。
不再次查询索引，不使用加权 cached_tokens；picker 后不再生成分类。

- `gpu_blocks`：GPU 前缀块数。
- `host_pinned_blocks`：GPU 加 HostPinned 延伸后的累计前缀。
- `disk_blocks`：再加 Disk 和 External 延伸后的累计前缀。

注意：该上游快照把 Disk 与 External 合并；不能声称它是纯本地磁盘命中。
本版的读取估计为 `(disk_blocks - host_pinned_blocks) × block_size`，
并按 vLLM 需要计算最后一个 prompt token 的规则裁剪。
计算估时使用全部已缓存前缀，存储压力仅使用低层缓存新增读取量。
原有 bulk/逐层流水的参考服务时间公式保持不变。
HostPinned 传输成本未新增建模，不能用本模式评估 CPU 传输瓶颈。

分级索引必须由实际缓存事件维护。没有事件时，索引只会给出零或不完整命中。
本版不新增真实存储事件生产器、缓存数据传输或具体盘号查询。
选中实例快照会聚合多 DP rank，因此本版明确只支持每 worker 一个 DP rank。
这与现有模拟实例粒度一致，不等同于计算公式中的 DP 参数。

## 启用

在 Linux 包目录构建独立扩展；目录必须不存在：

```bash
python scripts/build_weighted_dynamo.py --source /path/to/pinned/dynamo \
  --output /new/build --tier-admission --release --jobs 4
```

新配置设置 `admission.profile_source=dynamo_tier`、`router_mode=kv`，
以及既有的 `scheduler/arrival/tfs/first_token/aging_enabled=false` 条件。
使用共享缓存池的真实查询，不接受 `cache_model=first_seen` 的逐请求命中绑定。
`run_tfs_stack.py --profile-source dynamo_tier --routing-python-path /new/build/python`
可覆盖配置；其余参数沿用原入口。启动器启用事件索引，保留原实验的零 overlap 评分权重，
从而不同时引入另一项路由评分策略变化。
固定上游原本把事件订阅与正的 overlap 评分权重绑定；本 overlay 仅在新模式下
解除这项绑定。零评分权重时仍订阅事件，不把索引缺失默认为缓存没有命中。

调用者可以不提供 `_sim_admission`。测试回放只在其中保留 ID。
新模式拒绝客户端传入命中量、类别、估时和保留的 storage_hint/EDF 标记。

## 一致性边界

索引命中不是 KV 已加载。Connector 仍查询实际缓存、安排加载并保持层屏障。
允许 Connector 的实际外部读取量与画像存在偏差。`tier_lookup_mismatch` 记录预计和实际字节数，
不会仅因偏差而报错、退额、修改画像或调整 α 评分。准入继续使用路由时冻结的画像，
KV 分配、读取和计算使用 Connector 实际查询结果。
原有实际无外部读取、分配失败等资源回收路径仍执行；它们不属于按偏差重新分类。
例如预计为轻读、实际为重读时，本版仍按原画像放行，暂不补申请额度。
淘汰后的自动重分类和相应账本修正尚未实现；重复路由回调改变已冻结画像仍不支持。
本版用于验证信息来源与控制链，不能称为完整生产适配。

等待重读账本在原生完整 booking 成功后绑定；prepare 不占中央额度，也不提前创建资源 booking。
额度、首 token 释放和旧模式均沿用现有策略。

## 历史验证：前移修正前

- 359 项完整 Python 回归通过，其中 11 项覆盖新画像、普通 HTTP 请求、配额和命中分歧。
- 固定 Dynamo 源码应用 overlay 后，原生扩展编译通过。最终功能小测使用 dev/debug=0 构建。
- 两实例、八请求全部完成。六条 Disk 命中请求各 1024 token，两条无命中请求各 0 token。
- Connector 实际读取总量为 201,326,592 字节，与 Dynamo 画像一致。
- 重读额度峰值为 1。六笔额度均在首 token 释放，末态无占用。
- α=0.1 的六条重读均完成 registered/bound_waiting/activated/closed，原生候选评分中观测到四次折扣。
- 同一扩展关闭新模式后，旧画像路径的两实例、十二请求小测通过；八条重读的额度和评分账本均归零。

测试采用 K=20 放大壁钟、两波到达，以保证后续请求在重读等待期间进入原生 picker。
这不是固定 benchmark 或性能对照。最初单波 K=4 的八请求也全部执行通过，
但所有实例选择早于画像回调，未观测到折扣候选评分，因此保留为未满足完整验收的预试。
另保留两个失败预试：测试 worker 重复注册连接器；零评分权重导致索引未维护，
后者被当时的严格命中核对拦截。最终补齐索引创建和事件订阅两处启用条件。
原始构建、失败日志和小测记录保留在本机 audits/dynamo-tier-admission-20261104。

## 历史验证：命中偏差小测

在相同小测命令上增加 `--event-hit-fraction 0.5`，让事件索引只上报存储实际前缀的一半。
该参数只作用于验证程序，不修改存储缓存内容或 HTTP 请求。
验收分别核对画像预计量、实际读取量、偏差日志和请求完成状态，不再要求两者相等。
默认不传此参数时仍验证一致命中及 α 候选评分。

2026-11-04 后续实测：该偏差小测八条请求全部完成，六条各预计 512 token、实际 1024 token。
记录六个偏差请求，实际总读取量仍为 201,326,592 字节；六条重读的额度和评分账本最终归零。
本次 44 项针对性回归通过：画像 12 项、调度前准入 12 项、空闲强制准入 20 项。
这些结果只验证允许偏差的执行语义，不用于判断估时准确度或性能收益。
