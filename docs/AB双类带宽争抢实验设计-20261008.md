## 1. 工况定义（源自 E26 大纲 §1）

| 参数 | 值 |
|---|---|
| NPU/worker 数 m | 32，Dynamo 真实负载感知路由（cache-blind） |
| 模型层数 L | 8（本仓库无层概念，L 折入总量） |
| A 类请求 | 输入 128K token（命中前缀）、重算 256 token；**每层读取 175.65 MB、每层计算 6.02 ms** |
| B 类请求 | 输入 32K token、重算 4096 token；**每层读取 38.5 MB、每层计算 28.59 ms** |
| 存储总带宽 | 120 GB/s 共享链路（所有 worker 的读取挤这一条，FCFS/处理器共享分摊） |
| batch size | 1（每 worker 同时只算一条） |
| 配比与规模 | A:B = 1:2；本实验每轮 32A+64B、2 轮 = 192 条（E26d 缩减规模），轮距 1.0 s |

**绑定量（执行口径）**：对调度有意义的量是**每类总读字节与总计算时间**——A 读 8×175.65 MB = 1.4052 GB、算 8×6.02 ms = 48.16 ms；B 读 8×38.5 MB ≈ 0.30798 GB、算 8×28.59 ms = 228.72 ms。派生：每轮总读 64.68 GB → 120 GB/s 下排空下限 0.539 s（b=1.0 s 为轻间歇档）；4.1 条并发 A 流即打满 120 GB/s；32 worker 同时读 A 的需求 934 GB/s（7.8× 容量）。

## 2. 计算与读取的映射：虚拟 token 标定（语义说明，不得隐瞒）

本仓库计算模型为单一全局线性系数（`engine.py`：`duration = step_overhead + prefill×prefill_token_s + decode×decode_token_s`），按字面重算 token 数（A 256 / B 4096）无法同时命中两类计算时间（需要 188.1 µs/token vs 55.84 µs/token 两个互斥系数）。

**采用 E26 大纲 §3 同款方法**：虚拟 token 数 + 重标定系数，以 (每类总计算, 每类总读取) 为准，允许 token 数偏离字面值：

| 量 | A 类 | B 类 | 与大纲字面值的偏差 |
|---|---|---|---|
| remote_prefix（token） | 130,816（= 8,176 块） | 28,672（= 1,792 块） | 字面 128K−256 / 32K−4096，**完全一致** |
| 读字节（×kv_bytes_per_token=10,741.744 B） | 1.4052 GB | 0.307985 GB | <0.01% |
| 重算 u′（token） | **862**（字面 256） | 4,096（字面，不变） | A 虚拟化 |
| 计算时间（×prefill_token_s=55.83984375 µs） | 48.134 ms | 228.72 ms（精确） | A −0.05% |
| prompt 长度（token） | 131,678 | 32,768 | A +0.5%，B 精确 32K |
| output_tokens | 16 | 16 | 大纲无 decode 概念；只影响 finish 不影响 TTFT |

- `prefill_token_s = 0.22872 s ÷ 4096 = 55.83984375 µs`（B 精确命中；B 占 2/3 请求且为计算主导类，选 B 精确、A 虚拟化）。
- `decode_token_s` 取同系数（任意选择，已披露）；`step_overhead_s=50 µs` 沿用 demo（17 步/请求 ≈ +0.85 ms，<0.4%）。
- **语义说明**：A 的重算 token 从 256 虚拟化为 862，使线性模型命中用户给定的每层计算时间——语义故事变了（token 数不再字面等于 128K/256），但对调度有意义的全部量（每类读字节、每类计算时间、T0 量级、读取协议行为）精确匹配大纲给定值。此为大纲 §3 方法的直接移植。

## 3. 本仓库结构差异（先验披露，非实现缺陷）

1. **无逐层 I/O**：请求收齐全部远端块才恢复调度（检视报告 §4.2 既知差距）。单条理想 TTFT = 全量读 + prefill：A ≈ 11.71+48.13 = 59.8 ms、B ≈ 2.57+228.72 = 231.3 ms（E26 引擎有逐层流水，T0_A=49.62 ms 只含首层读）。
2. **异步 KV 加载不占 running 槽**（已核实 `upstream/vllm/.../scheduler.py:798-818`，WAITING_FOR_REMOTE_KVS 请求放回等待队列）→ `max_num_seqs=1` 等价于大纲 n_max=1，且多条请求可同时等远端读（"并发 A 洪水"口径 = 全系统同时处于远端等待的 A 数，对应 E26d 的 concA）。**真实 vLLM 允许 worker 在 A 等读期间算 B**——E26 里要靠 MPC 推演才获得的"B 算与 A 读重叠"错峰形态，在本仓库可能自然出现，是本实验重点观察项。
3. 读不去重（检视报告 §4.2）：本实验每请求 token 内容唯一，不存在共享块，无影响。
4. Dynamo 同代价平局随机（检视报告 §2.3.4）：worker 标签可能对调，汇总不变。

## 4. 配置与负载（configs/ab.json + scripts/gen_ab_trace.py）

```json
{"workers":32,"scheduler":"ascend_default","policy":"fcfs","block_size":16,
 "num_blocks":65536,"max_model_len":139264,"max_num_seqs":1,"max_num_batched_tokens":8192,
 "enable_prefix_caching":true,
 "storage":{"disks":2,"paths_per_disk":256,"disk_Bps":120000000000,
            "shared_link_Bps":120000000000,"path_Bps":2000000000,
            "read_latency_s":0.00005,"kv_bytes_per_token":10741.744},
 "compute":{"step_overhead_s":0.00005,"prefill_token_s":0.00005583984375,
            "decode_token_s":0.00005583984375},
 "ttft_slo_s":1.0}
```

- **带宽瓶颈唯一化**：2 盘×120 GB/s（聚合 240）、512 路×2 GB/s（路径上限不绑定）→ 有效每路 234.375 MB/s、Σ=120 GB/s，共享链路是唯一瓶颈（对应大纲"所有卡的读取挤这一条"）。
- **容量**：最坏 6 请求/worker × 8,230 块 = 49,380 < `num_blocks`=65,536；A′(862)/B(4096) 重算均 ≤ `max_num_batched_tokens`=8192，单步 prefill。
- **ttft_slo_s=1.0** 为宽松全局值（report 的全局达标率无分析意义）；**按类 SLO 在分析脚本**：默认 α=4 × 单条理想 TTFT → SLO_A≈239 ms、SLO_B≈925 ms（对齐 E26 的 deadline=arrival+α×T0 口径）。

**trace 生成器** `scripts/gen_ab_trace.py`：

- 参数 `--order block|interleave --rounds 2 --burst-s 1.0 --n-a 32 --n-b 64 --smoke`（smoke=8A+16B×1 轮）；输出 `results/traces/`（gitignored，192 请求×最长 131K token 的 JSONL 约 70–150 MB，只入库生成器不入库产物）。
- 每轮 96 条同刻到达（arrival_s = r×burst_s），顺序由 id 字典序决定：
  - **block 臂**（E26d D3 复刻）：32 条 A 在前、64 条 B 在后 → FCFS 首波派整块 A，直面洪水；
  - **interleave 臂**（大纲 D2 轮内交错）：(A,B,B)×32 → 首波天然混批。
- 每请求 token 内容唯一：`token[j] = (req_ordinal×7919 + j) % 32000`（7919 与 32000 互素，首 token 即互异，链式块哈希全程互异）——避免 vLLM 本地前缀缓存命中吞掉远端读、洪水消失。

## 5. 分析（scripts/ab_analyze.py）

读 `results/<name>/{report.json,events.jsonl}`，按 id 末字符分 A/B 类：

- 每类：n、TTFT mean/p50/p95/max、按类 SLO 达标率（默认 4×单条理想）、读字节（Σ external_tokens × kv_bytes_per_token）；
- **并发远端等待时间线**：从 `step_complete.waiting_remote` 快照重建全系统"同时处于 WAITING_FOR_REMOTE_KVS"的每类请求数 → 峰值/p90/时间加权均值（E26d concA 口径的等价量）；
- 全局：makespan、throughput、bytes_read、每 worker compute/stall/idle 合计。

## 6. 执行步骤与风险

1. **冒烟**（8A+16B×1 轮）：过 `tests/`、`scripts/check_results.py`；确认无死锁、迭代数远低于 10 万守卫。
2. **全量两臂**：`results/ab_block_b1.0`、`results/ab_interleave_b1.0`（同 config、同到达时刻，仅 id 顺序不同）。
3. **对比读法**：block 臂预期 32 条 A 同时等读（链路 ~32 路分摊、A 类 TTFT 显著劣化）；interleave 臂首波混配是否缓和；异步加载下"B 算与 A 读重叠"是否自然形成错峰。**如实记录，不预设结论**。
4. **风险**：
   - 全量约 75 万次块读完成事件；同刻完成大量合并（512 路同速率），预计迭代数千次；若触发 10 万次 event-loop 守卫（`run.py:89`）→ 降为 1 轮并在结果中披露，不改 `sim/` 核心；
   - 仿真墙钟预计分钟级/臂（纯记账，无数值推理）。
