# 三实例服务器配置的 CPU 仿真

同事首次运行服务器 `synthetic_abc` 仿真，请按[服务器负载与仿真运行指南](服务器SyntheticABC与仿真运行指南.md)执行。包含安装、原始到达回放及 α=1/dev 对照。

用此入口在仿真中筛选 workload。默认策略直接走 Dynamo KV 路由和 vLLM。TFS 策略额外启动 central，启用 Dynamo 的画像与等待计分，以及 vLLM 端的读额度检查。两组使用同一份请求形状、预置前缀和到达时间。

| 部件 | 取值 |
| --- | --- |
| Dynamo | 从工作区维护的服务器 1.2.0 源码重新编译。frontend 和 worker Python 组件来自同一次构建的源码目录，使用 KV 路由及 fastokens |
| vLLM | 现有 CPU 环境的 v0.20.2 EngineCore、AsyncScheduler 和 KV 分配。3 个 worker，每实例最多 1 条请求，调度 token 预算 50000，上下文 98000，块大小 128，关闭设备前缀缓存 |
| TFS | 复用仿真账本与准入钩子，接入服务器版元数据入口和 1.2.0 的 Dynamo RPC。使用 FCFS 和等待评分系数 0.1 |
| 计算 | MiniMax TP2、batch 1、16 层的 `prefill50k_total16_v2`，画像预算 50000。将拟合时间均分到 16 层 |
| 存储 | 6 个独立盘，共享 25 GB/s 链路，单盘预算 25/6 GB/s。KV 大小 65536 字节/token，按层提交，当前层等待前提交下一层 |
| 回放 | 两组发送 `kv_transfer_params.enable_phase2_dump=false`，在连接器检查实际收到的布尔值 |

配置位于 `dynamo_vllm_cpu_sim/configs/minimax_server_3w.json`。OD 仿真将缓存块分配到 6 个盘，再按盘和共享链路推进读取。散列放置、每路径上限 1 GB/s、100 µs 启动延迟属于仿真假设。每实例先使用约 5900 个 KV 块，按历史日志每 rank 约 23.06 GiB、每块每 rank 约 4 MiB 估算。拿到当前实例的实际容量后用 `--num-blocks` 覆盖。服务器最新发布目录的完整源码、实际盘间分布、链路效率与在线故障行为仍需真机核对。

仿真使用轻量 tokenizer 生成与服务器 catalog 等长的 prompt，从 trace 预置存储并通过 ZMQ 发布 DISK 事件。这个入口测热缓存 replay，启动成本和实际 prepare 写入时间留在测量区间之外。NPU 前向、网络/RDMA、TP 保存确认和物理盘分别由计算模型与存储模型取代。结果用于筛选实验，硬件 TTFT 和收益仍需上机测量。

## 构建与启动

在 Linux 或 WSL 中进入本仓库根目录后执行。首次运行先按包内 README 准备 CPU 环境（`bash scripts/bootstrap.sh`，在包内执行），并安装 Rust 1.96.1。旧入口仍使用 Dynamo 1.5；本入口将仓库内 `source_dev/dynamo` 的 1.2 源码独立编译，不覆盖环境中的 1.5。

```bash
REPO="$PWD"
DV="$REPO/dynamo_vllm_cpu_sim"
PY="$DV/.venv/bin/python"
BUILD="$HOME/.cache/dynamo-server-sim/build-1.2"
RESULTS="$HOME/.cache/dynamo-server-sim/results"
DEPLOY="$REPO"

export RUSTUP_TOOLCHAIN=1.96.1
export PYTHONHASHSEED=0 HF_HUB_OFFLINE=1 VLLM_PLUGINS=""
cd "$DV"

"$PY" scripts/apply_ascend_patch.py
bash scripts/build_server_dynamo.sh "$DEPLOY/source_dev/dynamo" "$BUILD" "$PY"
"$PY" -m pip install --target "$BUILD/python" --no-deps \
  "nixl==0.10.1" "nixl-cu12==0.10.1"
```

构建在 Linux 文件系统进行。如已有 Swagger UI 缓存，可以在构建前把 `SWAGGER_UI_DOWNLOAD_URL` 指向本地 `file:///.../v5.17.14.zip`。同一源码已经构建完成时，可复用 `$BUILD/python`。NIXL Python 包供 1.2.0 worker 导入，KV 读取由仿真连接器执行。

先用 pilot24 检查三实例。输出目录取新路径。

```bash
"$PY" scripts/run_server_benchmark.py \
  --server-dynamo "$BUILD/python" \
  --catalog "$DEPLOY/benchmark_tools_20261116/catalogs/pilot24.json" \
  --output "$RESULTS/server-pilot24"
```

默认先跑 default，再跑 tfs。驱动按本轮目录创建文件发现和存储 socket，依次启动存储、TFS central（仅 TFS 组）、三个 worker、Dynamo frontend，等待登记并回放。每组结束后清理本轮进程组。两轮依次运行，共用本机 HTTP 28765/28766 及 worker 管理端口 29111—29113。可用 `--mode default` 或 `--mode tfs` 单独调试。输出包含 `config.json`、运行源码路径、模型核验、逐请求 HTTP 结果和读层日志。

## Benchmark 筛选

先以同一 ABC catalog 对照原始到达与周期突发。周期突发保持 H/U 和类别数量，重复五轮。每轮 1 秒内发 36 条，随后 2 秒内再发 36 条。两阶段各含 12 条 A、12 条 B、12 条 C。缩放到达时间可用 `--arrival-scale`，例如 `1.2` 将所有间隔放大 20%。

```bash
"$PY" scripts/run_server_benchmark.py \
  --server-dynamo "$BUILD/python" \
  --catalog "$DEPLOY/benchmark_tools_20261116/catalogs/synthetic_abc.json" \
  --arrival-pattern periodic-abc \
  --output "$RESULTS/server-periodic-abc"
```

查看输出目录的 `comparison.json`。先核对两组完成数和读入字节一致，再比较分类及突发、恢复阶段的 P95 TTFT。结合 `storage.final.json` 的逐层 IO、`layer_check.json` 的计算及等待时间、`admission.events.jsonl` 的许可事件，检查突发之后队列是否排空，以及限流期间是否出现有请求等待却无计算的实例。用 `--wall-time-scale 2` 可复核 CPU 和进程通信开销的敏感性，结果仍按模型秒报告。

## 首轮 WSL 验证

三实例 pilot24 的 default/TFS 各完成 24 条。原始和周期两种 ABC 到达序列各完成 360/360 条，四组均读取 315,076,116,480 字节。ABC 每组各有 240 个读前缀请求、3840 次按层读取、360 个单请求计算 step。TFS 发放和释放许可后排空账本，画像中的版本、模型哈希和命中 token 数通过核验。

| 负载 | 策略 | 整体 P95 TTFT | A / B / C P95 TTFT | 回放结束 |
| --- | --- | ---: | --- | ---: |
| 原始到达 | default | 4.75 s | 5.08 / 4.66 / 4.40 s | 17.29 s |
| 原始到达 | TFS | 8.74 s | 9.42 / 2.03 / 1.78 s | 18.21 s |
| 周期突发 | default | 1.51 s | 1.60 / 1.49 / 1.32 s | 16.08 s |
| 周期突发 | TFS | 2.93 s | 3.66 / 0.68 / 0.50 s | 17.36 s |

以周期突发作为下一轮筛选的起点。其到达阶段可重复比较，突发期预计需求为 31.5 GB/s，恢复期降至 15.8 GB/s。当前一轮观察到 B/C 尾延迟下降、A 尾延迟上升，三个实例的在途读层峰值两组均为 6。需要进一步检查许可等待、实际读层并发和计算空闲分布，再决定哪组负载上机。

单轮结果保存在本机 `$BUILD/pilot-final`、`$BUILD/original-final` 和 `$BUILD/periodic-final`。前一次使用 1024 KV 块的探索运行保存在 `$BUILD/periodic1`，默认组出现 4 个全 worker 忙的 503。上表使用 5900 块的后续运行。

## α 与无限额度对照

`--alpha` 控制等待重读计分，默认 0.1，范围 [0,1]。`--dev` 取消 TFS 的重读额度上限，保留画像、许可通信、记账和反馈。两个开关只改运行参数，不要求重编译 Rust。用 `--alpha 1 --dev` 观察当前 TFS 控制路径相对 default 的开销；这不代表所有策略行为完全相同。

```bash
"$PY" scripts/run_server_benchmark.py \
  --server-dynamo "$BUILD/python" \
  --catalog "$REPO/benchmark_tools_20261116/catalogs/pilot24.json" \
  --alpha 1 --dev --output "$RESULTS/pilot24-dev-alpha1"
```

输出目录须未被使用。每组的 `config.json` 保存有效 α 和 dev 设置。`comparison.json` 给出各类成功数量、平均和 P95 TTFT、回放完成时间与读字节量。

## 服务器 benchmark

`benchmark_tools_20261116/` 是此前交付服务器的 benchmark 本地维护版。它只构建负载、发送请求和统计结果，不启动服务、不选择策略。部署侧额外修改未通过本次发布核对。服务器运行命令见该目录 README；模拟器通过 `--catalog` 读取同一目录的请求形状和到达时间，使用本地 tokenizer 构造等长输入，不声称 token 内容与真机完全一致。

```bash
# 在已启动服务的服务器 drt_dev 中执行；另一策略只改 label。
python3 -u benchmark_tools_20261116/benchmark.py run \
  --benchmark synthetic_abc --endpoint http://127.0.0.1:8000/v1/completions \
  --prepare-concurrency 3 --concurrency 360 \
  --replay-phase2-dump off --label default
```

prepare 写入前缀，replay 关闭新增 KV 保存；必须有 Dynamo 参数透传和 OD connector 的请求级开关补丁。HTTP 成功本身不能证明 OD 持久化或实际命中。
