FPM 与 Metric 统计从逐轮工作量，到对外可见的指标

FPM 保留一轮计算中的工作量、队列画像与耗时关联；原生 /metrics 提供状态、累计计数和统计分布。比较两者时，先对齐统计对象、记录时机与导出方式。

FPM / 主动推送

一条消息对应一轮工作画像。统计形成与消息到达之间可能存在排队和传输延迟。

调度快照 → 输出后汇总 → 消息推送

/metrics / 外部拉取

先更新内存注册表，再等待外部抓取。两次抓取之间的逐轮关联不会完整保留。

统计输入 → 注册表 → HTTP 抓取

先记住三个边界

  • 已有上下文 ≠ 缓存命中。此前 Chunk 的计算结果会成为下一轮上下文，但不会因此新增一次缓存命中。
  • 内部能拿到 ≠ 原生指标已导出。SchedulerIterationDetails 等内部结构不能直接算作 /metrics 的公开能力。
  • 上下文 Token 数 ≠ 实际网络传输量。传输耗时、字节数和失败信息应看相应 Connector 统计。

阅读方式：先看结论，再沿目录逐层展开。字段定义可折叠，末尾对照表可按关键词筛选。

产生与发布时机

相同点：都是forward粒度的信息

两者很多数据都在每轮执行完成后更新，主要区别在于：FPM 主动推送消息，/metrics 等外部来读取。

FPM 的路径是：

schedule()
    留下本轮调度结果，记录时间
        ↓
update_from_output()
    非空计算轮完成后，汇总本轮工作量、当前等待队列、耗时
        ↓
放入后台发布队列
        ↓
后台线程序列化 → ZMQ → Dynamo 事件通道 → 消费者

因此，FPM 的统计形成与实际发出不是同一时刻：调度线程生成统计，后台线程随后发送，中间可能有排队和传输延迟。

原生 /metrics 的路径是：

update_from_output()
    生成 SchedulerStats 等调度统计
        ↓
vLLM 前端处理输出
    计算 Token、TTFT、ITL、完成请求等统计
        ↓
PrometheusStatLogger.record()
    更新内存中的 Gauge / Counter / Histogram
        ↓
外部请求 GET /metrics
    返回此时注册表中的指标值

所以，指标内部更新不需要等待下一次 HTTP 抓取；但消费者要发起读取，才能拿到更新后的值。

顶层数据结构

FPM 对外发送的是一个完整的 ForwardPassMetrics 对象：

ForwardPassMetrics字段定义
class ForwardPassMetrics:
    # 消息身份
    version: int                  # FPM 数据格式版本
    worker_id: str                # Dynamo Worker 标识
    dp_rank: int                  # 数据并行 Rank
    counter_id: int               # 发布消息的递增序号

    # 本轮时间
    wall_time: float              # 本轮耗时估计，单位秒

    # 两组业务数据，下一层展开
    scheduled_requests: ScheduledRequestMetrics
    queued_requests: QueuedRequestMetrics

可以先把它读成：

一条 FPM
├── 谁发的、哪一条
├── 这一轮用了多久
├── 这一轮调度了什么工作
└── 输出处理时，还有什么工作在排队

vLLM 这边，没有一个与之对称、直接发给 /metrics 的统一 Metrics 对象。原生 Prometheus 统计入口接收三个统计对象：

# PrometheusStatLogger 的实际入口签名
def record(
    self,
    scheduler_stats: SchedulerStats | None,
    iteration_stats: IterationStats | None,
    mm_cache_stats: MultiModalCacheStats | None = None,
    engine_idx: int = 0,
):
    ...

它的顶层组织方式是：

PrometheusStatLogger.record(...)
├── engine_idx
│   └── 这些统计属于哪个 Engine
│
├── SchedulerStats
│   └── 调度状态、资源状态、缓存和后端统计
│
├── IterationStats
│   └── 本次输出处理中的 Token、请求延迟、完成请求统计
│
└── MultiModalCacheStats
    └── 多模态缓存查询和命中统计

record() 用这些数据更新 Prometheus 注册表，HTTP /metrics 再读取注册表。因此，这三个对象是指标的输入，不是 HTTP 返回的数据结构。

FPM：调度与队列

FPM 的 scheduled_requests 展开后，全部是数值字段：

ScheduledRequestMetrics字段定义
class ScheduledRequestMetrics:
    # 本轮 Prefill 工作
    num_prefill_requests: int      # 本轮 Prefill 请求数
    sum_prefill_tokens: int        # 本轮新计算的 Prefill Token 总数
    var_prefill_length: float      # 这些请求的完整 Prompt 长度总体方差
    sum_prefill_kv_tokens: int     # 这些请求在本轮计算前已有的上下文 Token 总数（前缀存+前面已经完成的chunk）

    # 本轮 Decode 工作
    num_decode_requests: int       # 本轮 Decode 请求数
    sum_decode_kv_tokens: int      # 这些请求已有的上下文 Token 总数
    var_decode_kv_tokens: float    # 这些请求上下文长度的总体方差（直接读取num_computed_tokens）

FPM 的另一组 queued_requests：

QueuedRequestMetrics字段定义
class QueuedRequestMetrics:
    # 被归入 Prefill 类的等待请求
    num_prefill_requests: int      # 等待请求数
    sum_prefill_tokens: int        # request.num_tokens 总和
    var_prefill_length: float      # 上述请求长度的总体方差

    # 被归入 Decode 类的等待请求
    num_decode_requests: int       # 等待请求数
    sum_decode_kv_tokens: int      # request.num_computed_tokens 总和
    var_decode_kv_tokens: float    # 上述数值的总体方差

当前 Dynamo 实现按以下规则分类：

waiting 队列：
    PREEMPTED                         → queued Decode
    其他                              → queued Prefill

skipped_waiting 队列：
    WAITING_FOR_REMOTE_KVS            → queued Decode
    其他                              → queued Prefill

Metrics：三个统计入口

SchedulerStats：

SchedulerStats字段定义
class SchedulerStats:
    # 当前调度状态
    num_running_reqs: int                  # 当前 Running 请求数
    num_waiting_reqs: int                  # 等待但未被归入 deferred 的请求数
    num_skipped_waiting_reqs: int          # 因约束或阻塞而 deferred 的请求数
    kv_cache_usage: float                  # KV Cache 使用率，0～1

    # 内部 DP 协调信息：不是直接导出的 Prometheus 指标
    step_counter: int
    current_wave: int

    # 缓存统计
    prefix_cache_stats: PrefixCacheStats
    connector_prefix_cache_stats: PrefixCacheStats | None
    kv_cache_eviction_events: list[KVCacheEvictionEvent]

    # 后端功能统计
    spec_decoding_stats: SpecDecodingStats | None
    kv_connector_stats: dict[str, Any] | None
    ec_connector_stats: dict[str, Any] | None
    perf_stats: PerfStats | None

    # LoRA 状态：适配器名称 → 请求数
    waiting_lora_adapters: dict[str, int]
    running_lora_adapters: dict[str, int]

    # 内部详细统计：当前原生 Prometheus logger 不直接导出
    iteration_details: SchedulerIterationDetails | None
    cudagraph_stats: CUDAGraphStat | None

这个对象把当前状态和本次上报的统计增量放在一起。例如：

  • num_running_reqs、kv_cache_usage 是状态快照。
  • prefix_cache_stats.queries/hits 是本次更新带来的缓存统计，后续累加到 Counter。
  • kv_cache_eviction_events 是本次收集到的事件，后续进入 Histogram。

IterationStats：

IterationStats字段定义
class IterationStats:
    # 本次输出处理的时间
    iteration_timestamp: float

    # 本次输出中观察到的 Token 和事件
    num_generation_tokens: int                 # 本次新增的输出 Token 数
    prompt_token_stats: PromptTokenStats       # Prompt Token 来源统计
    num_preempted_reqs: int                    # 本次观察到的抢占事件数
    num_corrupted_reqs: int                    # 本次计入的异常请求数

    # 本次得到的延迟样本
    time_to_first_tokens_iter: list[float]     # 首 Token 延迟样本
    inter_token_latencies_iter: list[float]    # 相邻输出间隔样本

    # 本次收集到的请求参数样本
    max_num_generation_tokens_iter: list[int]
    n_params_iter: list[int]

    # 本次完成的请求
    finished_requests: list[FinishedRequestStats]

    # 只读属性，不是另一份独立计数
    # num_prompt_tokens == prompt_token_stats.total

这里的 Iteration 指一次 EngineCoreOutputs 的输出统计，不要直接把它理解成 FPM 的逐轮计算工作量。

比如：

FPM.sum_prefill_tokens
    这一轮实际调度了多少 Prefill Token

IterationStats.prompt_token_stats.computed
    本次输出处理中收到的请求级 Prefill 统计，
    其中有多少 Token 被归为本地计算

在 Chunked Prefill 下，这两者的记录时机和粒度不同。

MultiModalCacheStats ：

MultiModalCacheStats字段定义
class MultiModalCacheStats:
    reset: bool       # 是否发生缓存重置
    requests: int     # 本次统计涉及的请求数
    queries: int      # 查询的多模态数据项数
    hits: int         # 命中的多模态数据项数

注意这里按多模态数据项计数，不是按文本 Token 计数。原生 Prometheus logger 使用其中的 queries 和 hits 更新相应 Counter。

嵌套字段与后端统计

IterationStats 的两个子对象

PromptTokenStats 回答的是：这些 Prompt Token 从哪里来？

PromptTokenStats字段定义
class PromptTokenStats:
    computed: int                 # 本地新计算的 Prompt Token
    local_cache_hit: int          # 本地前缀缓存命中的 Prompt Token
    external_kv_transfer: int     # 从外部 KV 传输得到的 Prompt Token

    cached_tokens: int            # local_cache_hit + external_kv_transfer
    total: int                    # computed + cached_tokens

它与 FPM 的差别是：

PromptTokenStats：
    新计算 / 本地缓存 / 外部 KV
    → 按来源分类

FPM ScheduledRequestMetrics：
    本轮新计算量 / 本轮已有上下文
    → 按本轮计算工作分类

例如，前一个 Chunk 刚计算好的 2048 个 Token，在下一轮会进入 FPM 的 sum_prefill_kv_tokens，但不会因此成为一次新的 local_cache_hit。

FinishedRequestStats 回答的是：某个已完成请求一共经历了什么？

FinishedRequestStats字段定义
class FinishedRequestStats:
    # 身份与结束情况
    request_id: str | None
    finish_reason: FinishReason
    is_corrupted: bool

    # 请求规模
    num_prompt_tokens: int
    num_generation_tokens: int
    num_cached_tokens: int
    max_tokens_param: int | None
    num_preemptions: int

    # 请求生命周期耗时，单位秒
    e2e_latency: float                  # 到达 → 请求结束
    queued_time: float                  # 首次排队 → 首次调度
    prefill_time: float                 # 首次调度 → 首 Token
    decode_time: float                  # 首 Token → 末 Token
    inference_time: float               # 首次调度 → 末 Token
    mean_time_per_output_token: float   # Decode 时间 / 首 Token 之后的输出数

这些是请求级数据，可能跨越很多个 Forward Pass。原生 Prometheus logger 将它们汇入计数器和直方图，并不会把 request_id 作为这些指标的标签逐请求导出。

SchedulerStats 的缓存部分

PrefixCacheStats / KVCacheEvictionEvent字段定义
class PrefixCacheStats:
    # 继承自 BaseCacheStats
    reset: bool
    requests: int                # 本次普通请求数
    queries: int                 # 本次查询的 Token 数
    hits: int                    # 本次命中的 Token 数

    # 对曾被抢占的请求单独统计
    preempted_requests: int
    preempted_queries: int
    preempted_hits: int


class KVCacheEvictionEvent:
    lifetime_seconds: float            # Block 生命周期
    idle_seconds: float                # 淘汰前的空闲时长
    reuse_gaps_seconds: tuple[float, ...]  # 各次复用之间的时间间隔

其中：

SchedulerStats.prefix_cache_stats
    → 本地前缀缓存统计

SchedulerStats.connector_prefix_cache_stats
    → 外部 KV Connector 的前缀缓存统计

SchedulerStats.kv_cache_eviction_events
    → 被采集到的 KV Block 淘汰事件列表

原生 Prometheus logger 对 PrefixCacheStats 直接读取的是 queries、hits；并不是结构里的每个字段都会变成一个公开指标。后端功能相关的子结构如下：

SpecDecodingStats / PerfStats / DebugPerfStats字段定义
class SpecDecodingStats:
    num_spec_tokens: int                  # 配置的投机 Token 数
    num_drafts: int                       # 草稿批次计数
    num_draft_tokens: int                 # 提出的草稿 Token 数
    num_accepted_tokens: int              # 被接受的草稿 Token 数
    num_accepted_tokens_per_pos: list[int] # 各草稿位置的接受计数
    num_draft_tokens_per_pos: list[int]    # 各草稿位置的提出计数


class PerfStats:
    num_flops_per_gpu: int                # 每 GPU 的 FLOPs 估计
    num_read_bytes_per_gpu: int           # 每 GPU 的内存读取字节估计
    num_write_bytes_per_gpu: int          # 每 GPU 的内存写入字节估计
    debug_stats: DebugPerfStats | None    # 内部计算细节，不直接导出


class DebugPerfStats:
    calc_duration: float
    num_prefill_requests: int
    num_decode_requests: int
    context_breakdown: dict[str, int] | None
    num_flops_per_gpu_breakdown: dict[str, int] | None
    num_read_bytes_per_gpu_breakdown: dict[str, int] | None
    num_write_bytes_per_gpu_breakdown: dict[str, int] | None

这些功能需要相应配置才能产生有效数据。特别是 PerfStats 的字节数是内存访问估计，不能当成网络传输字节数。

Connector 统计使用字典，字段由具体后端决定：

# SchedulerStats 中：
kv_connector_stats: dict[str, Any] | None  # KV 传输/缓存后端统计
ec_connector_stats: dict[str, Any] | None  # Encoder Cache 传输后端统计

以 NIXL 的统计数据部分为例：

NixlKVConnectorStats.data
├── transfer_duration          # 传输时间样本
├── post_duration              # 提交传输的时间样本
├── bytes_transferred          # 传输字节数样本
├── num_descriptors            # 描述符数量样本
├── num_failed_transfers       # 失败统计
├── num_failed_notifications
├── num_failed_handshakes
└── num_kv_expired_reqs

这才是与实际 KV 传输时间、传输量、传输失败直接相关的统计。FPM 中的 sum_decode_kv_tokens 并不包含这些信息。最后，SchedulerStats 中还有两组内部有、但当前原生 Prometheus logger 不直接导出的结构：

SchedulerIterationDetails / CUDAGraphStat字段定义
class SchedulerIterationDetails:
    iteration_index: int
    num_ctx_requests: int          # 本轮 Context/Prefill 请求数
    num_ctx_tokens: int            # 本轮 Context/Prefill 调度 Token 数
    num_generation_requests: int   # 本轮 Generation/Decode 请求数
    num_generation_tokens: int     # 本轮 Generation 调度 Token 数
    elapsed_ms: float              # 该计时区间的 CPU 侧耗时
    num_encoder_inputs: int
    num_encoder_output_tokens: int
    is_dummy: bool                 # 是否为 DP dummy iteration


class CUDAGraphStat:
    num_unpadded_tokens: int
    num_padded_tokens: int
    num_paddings: int
    runtime_mode: str

这部分很关键：如果比较的是“vLLM 内部能拿到什么”，它已有部分与 FPM 接近的逐轮数据；如果比较的是“原生 /metrics 对外提供什么”，这些内部字段不能算作已经提供。 它们目前主要走详细日志等路径。

对外输出与信息损失

FPM 基本保留消息中的数值和结构：

ForwardPassMetrics
    │
    ├── scheduled_requests
    ├── queued_requests
    └── wall_time 等顶层字段
    │
    ▼
序列化为一条消息
    │
    ▼
后台发布 → ZMQ → Dynamo 事件通道
    │
    ▼
消费者解码回 ForwardPassMetrics

Metrics 会进行字段选择和统计转换。下面是对应实际代码的简化表示：

# Gauge：用最新状态覆盖
num_requests_running.set(
    scheduler_stats.num_running_reqs
)

num_requests_waiting.set(
    scheduler_stats.num_waiting_reqs
    + scheduler_stats.num_skipped_waiting_reqs
)

kv_cache_usage_perc.set(
    scheduler_stats.kv_cache_usage
)

# Counter：把本次增量加到累计值
generation_tokens.inc(
    iteration_stats.num_generation_tokens
)

prefix_cache_hits.inc(
    scheduler_stats.prefix_cache_stats.hits
)

# Histogram：把样本加入桶、总和、样本数
for ttft in iteration_stats.time_to_first_tokens_iter:
    time_to_first_token_seconds.observe(ttft)

for req in iteration_stats.finished_requests:
    e2e_request_latency_seconds.observe(req.e2e_latency)

对外就变成这种形式，而不是返回 SchedulerStats 对象。下面数值只是格式示意：

vllm:num_requests_running{model_name="...",engine="0"} 8

vllm:generation_tokens_total{model_name="...",engine="0"} 12345

vllm:time_to_first_token_seconds_bucket{...,le="0.1"} 20
vllm:time_to_first_token_seconds_sum{...} 12.5
vllm:time_to_first_token_seconds_count{...} 100

所以，字段经过这一层转换后：

FPM 也不是无损日志：当前实现可能因队列满而丢消息；wall_time 是输出到达间隔等方式得到的估计；全零心跳是发布线程超时后构造的消息，不能当成重新采样得到的真实空队列。

另外，本地两份代码的等待队列接口不完全配套：Dynamo 仍读取 skipped_waiting，本地 vLLM 已使用新的队列结构。因此，实际联调前需要适配，不能直接假设两边等待总数一致。
